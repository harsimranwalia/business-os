## Pre-build verification against live state

`ENG-022` (tenant-isolation fix) shipped since this ticket's design pass —
re-read `brand-portal/utils.ts` at build time per the design's own
instruction. Live reality differs from what the design assumed:
`verifyRestaurantAccessLegacy` was never renamed to `requireRestaurantAccess`
— both functions coexist, `requireRestaurantAccess` is new and throws.
`feedback.ts`/`customers.ts` now use it; `offers.ts` still uses
`verifyRestaurantAccess` (object-return) but with corrected argument order.
Used `verifyRestaurantAccess` + explicit `.hasAccess` check in
`acquisition.ts` (matching `catering.ts`'s exact idiom) rather than
`requireRestaurantAccess`, because the design's Interfaces table requires a
`{success:false, error:'Access denied to this restaurant'}` JSON response —
a thrown exception would hit `index.ts`'s generic 500 handler instead,
violating that contract.

Live schema (via the newly-linked `supabase` CLI, read-only,
`bmnmnejwdxbcqinqkwko`): all seven attribution columns on `customers` match
the design exactly. `orders.customer_id` is `NOT NULL` (design assumed
nullable, for a "guest order" path) — doesn't weaken AC3, the other two
`direct_unknown` paths are independent of it. Full detail, including the
missing `customers(restaurant_id, created_at)` index (routed to
`proposals.md`, not bundled): `agents/database/migrations/ENG-020-*.md`.

## A real bug the disposable-container migration test caught

The first version of `get_acquisition_breakdown` failed on every
invocation: Postgres has no hash/merge-join strategy for a multi-column
`IS NOT DISTINCT FROM` `FULL JOIN` condition. Not data-dependent — it broke
against an empty table too. Fixed by coalescing each join column to a
`chr(1)` sentinel (plain, hash-joinable `=`, still null-safe). Full
verification detail, fixture data, and the corrected SQL:
`agents/database/migrations/ENG-020-marketing-roi-attribution-reporting.md`.
