## A correctness bug caught and fixed before it shipped

First draft of `readBalance` computed the sum from the same
`order by earned_at desc limit 500` list returned as `entries` — correct
today (zero rows) but silently **wrong** the moment any diner/restaurant
pair ever exceeded 500 entries, since the sum would only cover the most
recent 500 rather than all of them. AC10 requires the exact sum of every
entry. Split into two queries: one narrow (`select('points')`, no limit)
for the true sum, one bounded (`limit(500)`) for the display list only.
Regression test (`readBalance: the sum reflects every entry, not just the
capped display list`) seeds 505 rows and asserts `balance === 505` while
`entries.length <= 500`.

## PR body (for release-readiness to use verbatim)

**What it does:** Persists CloudWaitress's own order id going forward
(`cw_order_id`). Un-ignores `order_completed_updated` (credits via
`credit_order_if_eligible`), `order_cancelled_updated`/`order_cancel`
(unconditional `status='cancelled'`, never touching the ledger) — both
contained so a loyalty-side failure can never fail the webhook itself.
Adds `loyalty-auto-complete`, a cron-invoked edge function that credits any
order whose 24h window elapsed with no report. Adds
`record_dine_in_earn`/`get_loyalty_balance` to `brand-portal`, gated by
`requireRestaurantAccess`.

**What it deliberately does not do:** No webhook signature verification —
out of scope (see "Acting on ENG-048's own security gate forward-notes"
above; this is a pre-existing gap on every event this handler processes,
not something this ticket introduces, and fixing it is an auth-model change
the design explicitly excludes). No change to `order_new`'s own behaviour
beyond the new column. No redemption, no admin/support surface, no
Walletly migration (all out of scope per the PRD's own non-goals).

**Uncertainties / what to review hardest:** The wrong-tenant test (added
in the second commit) proves the handler never trusts
`webhookData.restaurant_id`, but doesn't (and can't, at this layer) close
the underlying webhook-authentication gap — worth confirming the security
gate treats these as two separate, correctly-scoped findings rather than
one. The `responses.ts` split is mechanical (re-exports, zero behaviour
change, diffed error-count-before/after to confirm) but touches a file four
other handlers still import from — worth a second look that
`walletly.ts`/`kitchenhub.ts`/`brevo.ts`/`cloudflare-pages.ts` are
genuinely unaffected.
