## A live-data mismatch that would have made Open Now silently inert

Before wiring anything, sampled two real rows: `select id, opening_hours from
restaurants where opening_hours is not null and array_length(opening_hours,1)
> 0 limit 2` (`bmnmnejwdxbcqinqkwko`, read-only). Both are arrays of
`{day, open, close}` objects (24h `HH:MM` strings), not the `weekday_text`
list (`"Monday: 9:00 AM - 5:00 PM"`) the source parser's own docstring assumes
and `toWeekdayLines` requires (its only array branch filters for
`typeof line === 'string'` — an object array filters to `[]`, then `null`, so
`getOpenState` would return `{isOpen: null, label: null}` for every row,
unconditionally).

`_shared/googlePlaces.ts`'s own header explains why both shapes can exist:
opening-hours writes were done four different, disagreeing ways before that
module centralized them — "some paths stored the structured `{ day, open,
close }` form while others stored Google's raw display strings." A straight,
unmodified port would have compiled, type-checked, and passed review while
silently never excluding or labelling a single closed restaurant in
production — exactly the failure class that hides behind a fail-open design
(ADR-010's own "never excludes on unknown" principle, applied here to data
the parser can't even recognize as hours at all).

**Fix, in `_shared/openingHours.ts`'s own `toWeekdayLines`:** detect an array
whose elements all satisfy `isStructuredHoursEntry` (`typeof entry.day ===
'string'`) and map each to a `"Day: hours"` line
(`structuredEntryToLine` — `isClosed` → `"Closed"`, `h24` → `"Open 24 hours"`,
else `"${open} - ${close}"`) before the existing, unmodified string-line
parsing runs. Imports `OpeningHours` from `_shared/googlePlaces.ts` as the
type (single source of truth for that shape, not a re-declared duplicate).
The original `weekday_text`-string path is untouched and still works (tested
below) — this is additive recognition of a second input shape, not a rewrite.

**Likely affects `restaurant-marketplace`'s own client-side copy too**
(`RestaurantDetail.tsx`'s `getOpenState` call, a different repo, already
shipped, out of this ticket's diff) — not fixed here, not confirmed in a
browser this pass. Filed: `agents/eng-manager/proposals.md`, 2026-09-07.

## PR body (for release-readiness to use verbatim)

**What it does:** Gates `handleRestaurantDiscovery`/`Fallback` by channel
(`p_channel` on the RPC, matching `.eq()` on the fallback) using `ENG-044`'s
new columns/parameter. Adds a ported, Deno-native `getOpenState` (`_shared/
openingHours.ts`) that computes a closed-status label and drives the
`open_now` exclusion, post-fetch, for both discovery paths (ADR-010).
`handleRestaurantDetail` gains the three `has_*` flags in its response.

**What it deliberately does not do:** No change to
`admin-portal/handlers/restaurants.ts` (already passes new fields through)
or to the pre-existing, independent `orderingLink` filter. No over-fetch
compensation for `open_now`'s page-size shrinkage (ADR-010's accepted
trade-off). No fix to `restaurant-marketplace`'s own client-side copy of this
parser (different repo, proposed separately, not this diff's to fix).

**Uncertainties / what to look at hardest:** The `_shared/openingHours.ts`
shape-adapter (`isStructuredHoursEntry`/`structuredEntryToLine`) is new logic
this ticket added on top of the ported parser, not itself part of the
original client file — it's the one piece here that isn't a straight port,
because a straight port would have silently never worked against this
repo's own live data (see the finding above). 9 unit tests cover it directly;
worth reviewing against the two live sample rows quoted in this notebook
entry if in doubt.
