## Decisions made at build time that the design didn't fully spell out

**Access-check convention for `broadcasts.ts`.** The design's own Interfaces
text says "gated by `requireRestaurantAccess`... reconfirmed against
`offers.ts`/`catering.ts`" — but reading those two files directly shows they
actually call the older, boolean-returning `verifyRestaurantAccess`, not the
throwing `requireRestaurantAccess` (which `ENG-022` added and only
`customers.ts`/`website.ts`/`hiring.ts`/`feedback.ts` use, and those four
*throw* all the way to the router's generic 500 on denial — not the
`{success:false,error}` shape this ticket's own Outcome text explicitly
requires). Resolved by using `requireRestaurantAccess` (the newer, harder-to-
forget-the-check helper, matching what the design literally names) but
wrapping every action's body in its own try/catch (matching `offers.ts`'s
per-function shape) so a thrown denial still returns `{success:false, error}`
rather than bubbling to a 500. This is a new synthesis, not a copy of either
existing convention verbatim — flagged here so review knows it was a
deliberate reconciliation, not an oversight.

**The dispatcher's atomic claim needed a schema change ENG-037 didn't ship.**
The design calls for "claims a bounded batch... atomically... not a plain
SELECT then UPDATE." `broadcast_campaign_recipients.status` only had
`pending/sent/failed/skipped_opted_out/cancelled` — no state that means
"claimed, outcome not known yet." Using any existing terminal value as a
placeholder before the real outcome is known would lie about that outcome if
the process crashes mid-flight. Added migration
`20260904150000_broadcast_recipients_claimed_status.sql`, widening the status
check constraint to add `claimed`. The migration's own comment documents the
one known gap this leaves: a row stuck at `claimed` (crash between claim and
resolve) has no automatic recovery sweep — named, not solved, same treatment
ADR-019 already gives its own cancelled-order gap. Claim implementation:
`selectDueRecipientCandidates` (plain, non-locking SELECT, bounded to 200) +
`claimRecipients` (a single conditional `UPDATE ... WHERE status = 'pending'
... RETURNING`) — supabase-js's query builder has no way to express `LIMIT`
inside an `UPDATE`, so the two-call split is what makes "bounded batch" and
"atomic claim" both achievable; the `UPDATE`'s own re-checked predicate is
what actually prevents a double-claim, not the earlier SELECT. Verified this
really is atomic by mutation-testing it: temporarily dropped the
`.eq('status','pending')` line, ran `dispatch.test.ts`'s overlapping-tick
test, watched it fail (3 rows double-claimed instead of 0), restored the
line, watched it pass again.

**Folded ENG-037's own review findings F1/F2 into this same migration.**
Grepping for cross-references before editing (step 6b) surfaced
`agents/principal-engineer/reviews/ENG-037.md`'s closing line: "Both are
additive (a new index, a new constraint) and can land in `ENG-038` or a
follow-up." F1 (missing index on `broadcast_campaign_recipients.step_id`,
an unindexed cascade-delete FK) and F2 (`broadcast_campaigns.scheduled_
send_at` nullable with nothing tying it to `status`, even though every
non-`draft` status presumes a real send time) were both judged non-blocking
on `ENG-037` specifically because no code that existed yet could trigger
either gap — `create_broadcast`/`update_broadcast` (this ticket) are
exactly that code, so adding both now closes the gap at the same moment the
triggering code ships rather than after. Verified both tables still empty
live before adding either (a `check` constraint added to a non-empty table
would need every existing row to already satisfy it). Added as a second
commit (`4f0dccf`) rather than amending the first, since it's a distinct,
separately-attributable change.

**Sign/verify for the unsubscribe token lives in `_shared/`, not duplicated.**
`ADR-015`/`ADR-017` chose independent per-directory copies for the
service-role-bearer *auth check* specifically because that check tolerates
two directories drifting slightly (each is a narrow, self-contained gate).
An HMAC sign/verify pair is a different shape: `outgoing-communications`
mints the link, `broadcast-unsubscribe` verifies it, and if the two ever used
different encodings the whole mechanism breaks silently for every customer.
`_shared/apiKeys.ts` is the exact precedent for this — a genuinely shared
hash/verify pair, not a duplicated check — so the new
`_shared/broadcastUnsubscribe.ts` follows that model. Needs a new
`BROADCAST_UNSUBSCRIBE_SECRET` env var, provisioned manually — same
operational-prerequisite shape as ENG-037's `service_role_key` Vault secret,
named in the migration's own comment there. No expiry on the token
(unsubscribe links should stay permanently valid; "expired" in the design's
response table is treated as unreachable, not built).

**Live schema verified via the newly-linked `supabase` CLI, not guessed.**
`customers.last_order_at` (timestamptz, confirmed live) backs the
`inactive_days` audience filter — the PRD only said "the underlying data
already exists" without naming the column. `communication_log` and
`orders.promos` were NOT re-verified — `ENG-037`'s own board log already
confirmed `orders.promos` is `jsonb[]` keyed by `"code"`, and this ticket's
own Notes explicitly said not to re-derive that. `get_broadcast_report`'s
ROI query fetches a restaurant's post-campaign orders and filters/sums in
JS (this codebase's own established idiom — `catering.ts`'s dashboard
stats, `brands.ts`'s report processing — never an `unnest`/RPC), scoped by
`restaurant_id` + `created_at >= campaign.scheduled_send_at`. That cutoff is
the *campaign's* own send moment, not each drip step's own (which ADR-019
names as the more precise option) — a deliberate simplification: the
campaign-level cutoff is a strict superset (can only over- not
under-attribute a few early orders on a later drip step), and nothing in
this ticket's own test/acceptance surface exercises per-step precision.

**`recipientCountsByCampaign` runs one indexed head-count query per campaign
on the current page** (bounded by `page_size`, clamped to 100), rather than
pulling recipient rows to count client-side. `broadcast_campaign_recipients_
campaign_id_idx` (ENG-037's migration) makes each cheap; flagged in case a
reviewer reads "a query per item" as an N+1 smell — it's bounded by
pagination, not by table size.

## Pre-existing bug found, not fixed here

`services/sms.ts`'s real `SMSData` takes `message`, not `body`; all three
existing lifecycle-offer SMS call sites (`sendWelcomeOffer`/
`sendEveryOrderOffer`/`sendFirstOrderOffer`) pass `{to, body}`. Verified live
(`deno run` against this tree) that this doesn't crash the request — it's
caught by `sendSMS`'s own try/catch and returns `{success:false, error:
"Cannot read properties of undefined (reading 'length')"}`, logged as
`communication_log.status = 'failed'`. This **corrects** an existing 2026-09-03
proposal row (architect, `services/sms.ts`) that claimed SMS sends were
logging fake `status: 'sent'` successes — not true for this reason; appended
the correction to that row rather than filing a disconnected duplicate, plus
an XS sub-item (rename `body` -> `message` at the three call sites). My own
new `broadcast_message` consumer action uses `message` correctly.

## PR body (for devops's release-readiness hop to use verbatim)

**Title:** Add broadcast composer API, dispatch poller, and unsubscribe
function (ENG-038)

**Body:**
Adds the backend surface for restaurant marketing broadcasts (ENG-019):
- `brand-portal` gains 8 actions for composing/sending/reporting on
  one-time and drip campaigns, tenant-scoped on every query.
- `broadcast-dispatch`, a new `pg_cron`-invoked function, promotes scheduled
  campaigns, enrolls their consent-filtered audience, and dispatches due
  sends with an atomic per-recipient claim (new migration: adds a `claimed`
  status to `broadcast_campaign_recipients`).
- `broadcast-unsubscribe`, a new public function, resolves an HMAC-signed
  link and flips the customer's consent.
- `outgoing-communications` gains a `broadcast_message` consumer action.

Depends on `ENG-037` (merged, PR #15) for the underlying schema and cron job.
Also folds in `ENG-037`'s own code-review findings F1/F2 (missing
`step_id` index; a check constraint tying `scheduled_send_at` to `status`),
both explicitly named there as safe to land in this ticket. Requires a
`BROADCAST_UNSUBSCRIBE_SECRET` env var provisioned before real campaigns
send (same shape as ENG-037's `service_role_key` Vault secret requirement).

Test plan: `deno test --no-check` on `brand-portal/broadcasts.test.ts` (6/6)
and `broadcast-dispatch/dispatch.test.ts` (4/4); no regression on
`brand-portal/offers.test.ts` (9/9).
