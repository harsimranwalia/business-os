## Uncertainties / what to look at hardest

**`types.ts`'s diff is much larger than this ticket's own three columns.**
Regenerating pulled in real, already-live schema that this repo's copy of
the file had never caught up to — other tickets' columns
(`claim_status`/`claimed_at`/`claimed_by_user_id`, `stripe_acct_id`, several
`brand-portal`-table fields among others) appear as new in the diff purely
because they were never regenerated in here after shipping, not because
this ticket touched them. This is the generator's honest, direct read of
the live schema (`supabase gen types typescript` talks to the project
directly; it has no way to fabricate a column), so the fix is exactly what
the design asked for — regenerate, don't hand-edit — but the resulting diff
is worth flagging for review since its size doesn't match the feature
alone. Filed as an observation (`observations.md`, this date) — a repo-
hygiene gap (this file drifting stale between the tickets that actually
touch schema), not a defect in this ticket's own work, and not something
this ticket's own scope extends to fixing beyond taking the regenerated
output as-is.

**Row placement (Order Food / Dine In / Catering grouped at the top of the
card) is a judgement call, not a spec line-item.** The design says "add two
new Switch rows... matching the six existing rows' exact markup" but doesn't
specify position. Grouping the three FoodSwipe-channel flags together
(rather than, say, appending the two new rows at the card's end) reads as
the more usable layout for staff and mirrors the PRD's own three-channel
framing, but review should confirm this doesn't conflict with a layout
expectation set elsewhere that this ticket's own Notes didn't carry
forward.

## PR body (for release-readiness to use verbatim)

**What it does:** Adds two new Switch rows (`has_order_food`, `has_catering`)
to the "Restaurant Features" card in `RestaurantDetails.tsx`, and repoints
the existing Dine In switch from the old `dine_in` column to `has_dine_in`
— per `ENG-044`'s own live-schema finding (`dine_in` real and live,
backfilled forward, so this is a repoint, not a fresh addition).
Regenerates `src/integrations/supabase/types.ts` from the live schema.

**What it deliberately does not do:** No new API call — the existing
`PUT /admin-portal/restaurants/:id` already accepts and persists arbitrary
keys, and `handleSave` sends the entire `restaurant` state object, so the
new/repointed fields are wired through with zero additional code. Doesn't
touch the database — the old `dine_in` column stays in place, unused
(`ENG-044`'s own Notes name a follow-up cleanup ticket to drop it once this
ships). Doesn't touch `restaurant-marketplace` or `aiorders-api` (`ENG-045`/
`ENG-047`'s own scope).

**Uncertainties / what to look at hardest:** `types.ts`'s diff is larger
than this feature alone would suggest — see this notebook's own
Uncertainties section above for why (pre-existing drift, not new schema
this ticket introduced) and confirm nothing in the extra churn looks wrong
rather than merely stale. Row placement for the two new toggles (grouped
with Dine In at the top of the card) is a layout judgement call, not a
spec requirement — flag if a different placement was expected.
