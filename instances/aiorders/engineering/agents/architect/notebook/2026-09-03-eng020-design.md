# 2026-09-03 — ENG-020, design pass

Design: `agents/architect/designs/ENG-020-marketing-roi-attribution-reporting.md`.
ADRs: `ADR-011` (host function), `ADR-012` (where classification runs).
The design carries the Approach, Alternatives, Risks and AC walk-through; this
is process, dead ends, and the corrections that didn't change the design.

## Where the handed-over research was wrong, and how

Same instruction as ENG-016's pass — a full evidence packet, to be checked
rather than trusted. Six corrections came out of reading `origin/main`; three
changed the design, three did not.

**Changed the design:**

- **`analytics` has no auth check at all.** The PRD, the ticket Notes and
  `observations.md` all name `analytics/database.ts` as the extension point,
  all correctly, and none of the three looked at `index.ts`. It reads
  `restaurantId` from the body, builds a service-role client, and never touches
  the `Authorization` header. AC5 therefore could not be met there without
  either a half-guarded function or a P0 fix bundled into a P2 feature. This
  is the single fact that moved the whole design to `brand-portal` (ADR-011).
  Worth noting *why* it stayed hidden: `supabase/functions/README.md` keeps an
  explicit "no auth check at all" list — and `analytics` isn't on it. The one
  document `aiorders-api/CLAUDE.md` tells every engineer to read first says the
  function is fine by omission.

- **`utm_source`/`utm_medium`/`utm_campaign` are not columns on `customers`.**
  The PRD, the ticket Notes and `observations.md` row 100 all state that five
  capture paths write those onto the customer row. They don't. All five build a
  nested `first_touch`/`last_touch` object and post it to `crm`, which persists
  `first_touch_source`/`_medium`/`_campaign`/`first_referrer`/`first_touch_at`/
  `last_touch_source`/`last_touch_at` and nothing else. The same callers also
  send a `utm_data: {utm_source, utm_medium, ...}` object — `git grep utm` over
  `supabase/functions/crm/` returns zero hits, so it is accepted and dropped on
  the floor. The channel mapper is written against the seven columns that exist.

- **`first_touch_source` is polluted with capture-surface names, and organic
  search isn't in it at all.** `config-site-builder/src/utils/userTracking.ts`
  only sets it from a UTM (`|| utmParams.utm_source`), so every non-UTM
  visitor stores nothing; the capture endpoints then backfill the field with a
  *form name* (`|| source || "offers-signup"`, `"email-signup"`,
  `"catering-form"`, `"online-order"`). So the column's values are a mix of
  real sources and sentinels, the platform disagrees with itself on spelling
  (`online-order` written, `online_order` branched on in
  `autopilot/marketing/welcome.ts`), and the only signal for the biggest real
  channel is `first_referrer`. This is what makes the mapping a precedence
  chain rather than a lookup, and is the whole argument in ADR-012.

**Didn't change the design, but the packet is wrong:**

- **The mock "Analytics" page is not in the nav, not routed, and not imported.**
  `observations.md` row 101 calls it "the page literally named 'Analytics' in
  the brand portal's nav" and the PRD calls it "the one page whose name suggests
  otherwise." On `origin/main` `src/pages/analytics/Index.tsx` appears in
  neither `App.tsx` nor `Sidebar.tsx` and nothing imports it — dead code an
  owner cannot reach. The observation's real concern ("it reads as real to an
  owner") does not currently apply, because no owner can open it. Still worth
  not reusing the *name*; downgraded from a live honesty problem to a cleanup
  ticket.

- **`aiorders-api` does have a working test invocation, and a test precedent.**
  `projects.md` shows every command column empty for this repo, which reads as
  "nothing to run." `observations.md` row 200 already recorded the working
  invocation (`DENO_NO_PACKAGE_JSON=1 deno test --node-modules-dir=none` from
  the function's own directory), and `admin-portal/handlers/loyalty-config.test.ts`
  is a real, committed Deno test file that gets the access-check function
  exported specifically so it can be tested without a DB. That file is the
  reason `channels.ts` is split out as a pure module — the pattern already
  exists here, it just isn't in `projects.md`.

- **QR and marketplace channels cannot be populated by anything today.** The
  PRD's channel list includes "QR/in-store" and "marketplace-migrated."
  `url-shortener`'s `get_or_create_restaurant_qr` (ADR-005/ENG-014) computes
  `destination_url` from the restaurant's own `website` column and appends no
  UTM, and `git grep` finds nothing anywhere that writes a QR-tagged source. A
  QR scan is indistinguishable from a bookmark. AC1's *binding* text doesn't
  enumerate channels — the list is in the PRD's Proposed change prose — so this
  is not an unsatisfiable AC, but it is named in the design rather than quietly
  shipping two buckets that will always read zero.

## A cross-domain finding sharper than the risk it belongs to

The PRD's cross-domain risk cites `user-tracking.js`'s README saying the
ordering-side wiring is a per-deployment task. True, and `INSTALLATION.md`
confirms it's a manual install with a hardcoded `restaurantId`. But there's a
second, more concrete defect underneath it: **the two implementations disagree
on cookie scope while sharing a cookie name.** The standalone
`public/tracking/user-tracking.js` sets `user_tracking` with
`domain=.<registrable domain>` (its `CookieUtil.set` builds the `domain` flag
explicitly); the React implementation the restaurant sites actually run
(`src/utils/userTracking.ts`) calls `Cookies.set` with `expires`/`sameSite`/
`secure` and **no `domain`**, so it is host-scoped. Same name, two scopes, on
the two halves of a stitch whose entire purpose is sharing state across
subdomains. Filed in the design as a follow-on ticket — it would improve this
report's coverage without changing a line of it.

## Two dead ends worth remembering

**Doing the whole thing with PostgREST aggregates and no migration.** This was
the better answer on the department's own "smallest thing" rule: it would have
kept `touches_data: false`, needed no `database` hop, and `database.ts` already
proves PostgREST aggregate functions are enabled on this project
(`select('total_revenue:total_amount.sum(), ...')`). It needed grouping across
an *embedded* resource (`orders` → `customers`), which I could not verify works
on this project from the repo alone. Rejected on failure mode rather than on
capability: a mis-grouped aggregate returns plausible numbers, and this is a
report whose only product is trustworthiness. Recorded in ADR-012 because it's
the alternative most likely to be re-proposed by someone optimising for "no
migration."

**Splitting AC3's bucket into separate "Direct" and "Unknown."** Started here,
because conflating a real signal (tracked visit, no referrer, no UTM) with an
absence of signal (pre-tracking customer, guest order) felt like exactly the
dishonesty AC4 exists to prevent. Worked out that the data can't support the
split: after the `userTracking.ts` finding above, a row with no source and no
referrer is *equally* consistent with a bookmarked visit and with tracking
never having been installed. Two buckets would have been a guess wearing a
label. One honest bucket plus an always-visible coverage percentage says more
true things. The instinct was right and the implementation would have been a
lie — worth remembering as a shape.

## The thing I expect to be wrong

**ADR-011 deviates from the PRD's stated Proposed change**, which named the
`analytics` function as the extension point in two places and had it confirmed
in the ticket's Notes as "confirmed by reading the code, not assumed." I'm
confident on the criteria — AC1–AC5 name a portal, an owner, a breakdown, a
range and server-side rejection, and none names a function — and the decision
journal's read of this approver ("extend the existing surface") arguably favours
`brand-portal`, which is the portal's *actual* backend for every other
owner-facing read. But this is the one place a reader who trusts the PRD over
the design will object, so it's stated in the design's Approach, in ADR-011's
own Decision section, and flagged in the pass report rather than buried.

Second candidate: **`touches_data: true` on a ticket the PRD costed as "no new
data model."** Both are true — no table, column or row changes; the migration
adds one read-only function — but it does put `database` in the chain and adds
a deploy-ordering step to an M. If the EM would rather this ship without a
migration, the PostgREST-aggregate dead end above is the path, and it needs a
live-schema check to de-risk rather than more reading.

  conceptual, not textual: ENG-019 owns coupon-redemption revenue, ENG-020 owns
  traffic-source revenue, both on the same portal, both approved the same
  evening. Two revenue-attribution surfaces that will eventually need to agree

  blocker for either.
