## The pattern is now at two occurrences, not three

`pg_default_acl` on this project's `public` schema names `anon`/
`authenticated`/`service_role` directly with `EXECUTE` at function-creation
time — a separate mechanism from the `PUBLIC` pseudo-grant that a bare
`REVOKE ... FROM PUBLIC` never touches. `ENG-048` (`credit_order_if_eligible`)
found this the hard way — applied the reviewer's own recommended
`FROM PUBLIC`-only fix, tested it, found it insufficient, then named both
roles explicitly. This ticket's two functions are the same root cause, same
project, same fix shape, confirmed independently (production catalog query
plus a disposable-replica reproduction) rather than assumed from `ENG-048`'s
precedent alone. That's two tickets, three functions, one root cause — short
of the three-*occurrences* bar this role's own charter sets for promoting
something into `engineering-standards.md`, so not proposed there yet. Worth
watching: if the wider sweep (`proposals.md`, 2026-09-07 principal-engineer
row, sizing note added this pass) turns up a third independent function with
the same gap, that's the third strike, and the standard should name this
project's `pg_default_acl` behavior explicitly rather than relying on every
future migration's author rediscovering it.

design's own decision. Scoped this ticket to exactly the two functions
security confirmed live-exploitable — matches the AC's, the Outcome section,

closing two functions that are exploitable *today* while auditing ten that
might not need anything at all.
