## 1. The correction that changed the design: the PRD's write mechanism doesn't exist

The PRD's Risks section and the ticket Notes both say the same thing: that
`restaurant-portal` already reads and writes `restaurant_website` directly, that
`src/pages/hiring/Index.tsx` is the precedent, and that the open question for the
architect is therefore *"is the RLS on `restaurant_website` really permissive
enough for the owner's own JWT?"* The PRD is careful about it — it calls the
claim "evidence, not proof" and explicitly hands it over.

The claim is false, and it fails in a direction that makes the ticket *easier*,
not harder.

`hiring/Index.tsx` contains **no `.from(` call at all**. Every read and write is
`supabase.functions.invoke('brand-portal', { action: 'get_jobs' | 'update_jobs' })`.
I checked the whole file, then grepped `restaurant-portal` for direct
`restaurant_website` access from `origin/main`: there is none, anywhere in
`src/`. The only surfaces that touch that table with a raw client are
`aiorders-admin-hub` (staff tool) and the edge functions themselves.

The actual precedent is one directory over: `src/pages/website/Index.tsx` — the
Website page, tabs Catering and Careers, calling `get_website_content` /
`update_website_content`, handled in
`aiorders-api/supabase/functions/brand-portal/website.ts`.

Why this matters rather than being a pedantic correction:

- **The question the PRD handed me becomes moot.** If the write goes through a
  service-role edge function with a code-side ownership check, then
  `restaurant_website`'s RLS is not the boundary and does not need to be
  confirmed. Which is lucky, because I checked and it *cannot* be confirmed:
  `git grep` for `CREATE POLICY` / `ENABLE ROW LEVEL SECURITY` against that table
  across both repos' migration histories returns **nothing**. Same untracked-schema
  gap ADR-006 recorded for `brands`. Had I taken the PRD's framing at face value
  and designed a direct client write, I would have built the feature on a policy
  nobody can read, and the security gate would have had no way to evaluate it
  either.
- **The change gets smaller.** `website.ts` hard-codes
  `const EDITABLE_PAGES = ['catering', 'careers'] as const` as an allow-list, and
  `restaurant_website.faqs` is a **top-level column** on the same table (sibling
  to `catering`/`careers`/`story`/`menu`/`locations`/`seo`). So the entire write
  path is: one array entry, one line in the returned `content` object, one
  exported type. No new action, no router case, no migration — which is *more*
  conservative than the PRD's own cost note ("no new backend endpoint or edge
  function anticipated") rather than less.
- **AC4 and AC5 become true by construction rather than by mechanism.** I traced
  all three consumers of that column: the bot
  (`ai-search-openrouter` does `.select('menu, deals, discounts, locations, faqs')`
  per `restaurant_id`), the public site (`config-site-builder`'s `Home.tsx` /
  `LocationPage.tsx`), and the staff editor (`aiorders-admin-hub`'s
  `RestaurantAIWebsite.tsx`, `.upsert({..., faqs})`). One column, three readers,
  one new writer. There is nothing to synchronise, so there is nothing to get
  wrong.

One trap the PRD *did* correctly flag and I want restated because it is easy to
fall into: `CateringPageContent.faqs` is a **different field** — a nested array
inside the `catering` jsonb column, catering-landing-page only, typed
`CateringFaq` in `restaurant-portal/src/types/website.ts`. I named the new type
`WebsiteFaq` specifically so a future reader cannot conflate them, and listed
`CateringPageForm.tsx` in the design's Components table as an explicit **no
change** row for the same reason.

## 2. The `verifyRestaurantAccess` question — answered, and already ticketed

The orchestrating session flagged that `website.ts` appears to call
`await verifyRestaurantAccess(...)` without checking the result, and asked me to
settle it exactly. I did, and then found the more useful half of the answer.

**It is a real, live bug on `origin/main`.** `brand-portal/utils.ts` defines
`verifyRestaurantAccess` returning `Promise<AccessVerificationResult>` —
`{ hasAccess, accessType?, brandId?, error? }` — and it **never throws** on
denial; the denial path is `return { hasAccess: false, error: 'Access denied to
this restaurant' }`. A separate, `@deprecated`-annotated
`verifyRestaurantAccessLegacy` is the throwing variant. `website.ts` imports the
non-throwing one and discards its return at both call sites. So a caller holding
any valid brand-portal JWT can read and write any restaurant's `catering` and
`careers` today.

I then surveyed all nine handlers in the directory. Two distinct bug families:

| Shape | Files |
|---|---|
| Correct — `const access = await verify(...); if (!access.hasAccess) ...` | `catering.ts`, `menus.ts`, `restaurants.ts`, `onlineOrders.ts` |
| Calls it, discards the result | `customers.ts`, `hiring.ts`, **`website.ts`** |
| Wrong argument order `(supabase, user.id, restaurant_id)` **and** truthiness-checks the returned object (always truthy) | `feedback.ts`, `offers.ts` |

**But this is not a finding — it is `ENG-022`.** That ticket
("Fix broken restaurant-scoped access check on 5 brand-portal handlers —
cross-tenant PII/write exposure", P0, `aiorders-api`) names exactly these five
files and exactly these two bug shapes in its own Problem statement. It is at
`state: blocked`, `owner: approver`, `blocked_on: approver`, with PR #9 open on
`fix/ENG-022-brand-portal-tenant-isolation` (`aiorders-api@d5078c5`). I diffed
that branch: it introduces a throwing `requireRestaurantAccess` wrapper in
`utils.ts` and swaps both `website.ts` call sites plus the import. I ran
`git merge-base --is-ancestor` against `origin/main`: **not merged**.

So the honest answer to "does my design inherit a live access-control bug" is:
yes, and it is already owned, already built, and waiting on a human to merge.
That produced three things in the design rather than a fix:

1. **A recommended `depends_on: [ENG-022]`, stated but not written.** ENG-021
   adds a *new owner write capability* to the one handler whose gate is open, and
   the column it writes is rendered publicly and emitted as schema.org markup.
   Shipping in the wrong order widens a known P0. But `depends_on` is a board
   sequencing field and the orchestrating session's instruction scoped my
   frontmatter edits to `links.design`, `links.adrs`, `touches_*`, `updated` — so
   I recommended it in the design's Risks section and in my report rather than
   writing it myself. Rollout step 0 states the precondition.
2. **A sibling-branch staleness note.** This is *not* the same situation
   `ENG-020`'s design handled. ENG-020 only had to pick the right *call shape* in
   a new file, so it could truthfully say "does not depend on ENG-022 merging —
   the correct shape works before and after." ENG-021 **edits `website.ts`
   itself**, one of ENG-022's five files. That is a direct textual collision, so
   the design instructs the build hop to branch from `origin/main` after ENG-022
   merges, or from ENG-022's branch if it must start earlier — and to re-read
   `website.ts`/`utils.ts` at build time rather than trusting the source quoted
   in the design doc.
3. **A deliberate non-fix.** Repairing it here would be automatic review failure
   #7 (unrelated refactor bundled into a feature) and would conflict with an open
   PR. Named in Out of scope.

Worth noting for whoever reads this later: `observations.md` (2026-09-03) already
records that `ENG-022`'s build hop ran `deno check` on this directory apparently
for the first time and found 19 pre-existing errors, 9 of them the `TS2345`
wrong-argument-order errors from `feedback.ts`/`offers.ts` — the compiler had
been flagging this bug all along. One of the remaining 10 is a supabase-js
generic-inference error in `website.ts` caused by
`.select(EDITABLE_PAGES.join(', '))`. Adding a third key does not change that
error's shape or count; the design says so explicitly so the build hop neither
fixes it nor is blamed for it.

## 3. The RLS asymmetry, and why the design has two different data paths

I expected to justify a single consistent access pattern and ended up justifying
a split. The split is the interesting part, so it became ADR-013.

I read the literal policy text rather than trusting the PRD's summary:

- **`ai_conversations`** — `restaurant-portal/supabase/migrations/20250903152559_*.sql`
  has a real `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` plus
  `CREATE POLICY "Restaurant managers can view their restaurant conversations"
  FOR SELECT USING (user_has_restaurant_access(auth.uid(), restaurant_id::uuid))`.
  I chased `user_has_restaurant_access` into
  `aiorders-api/.../20250729143357_initial_restaurant_rls.sql`: `SECURITY DEFINER`,
  `EXISTS (SELECT 1 FROM restaurant_managers WHERE user_id = ... AND restaurant_id = ...)`.
  Correctly scoped, exactly matching AC1's grain.
- **`restaurant_website`** — zero tracked policies in either repo. Unknowable.

So ADR-006's rule ("don't make RLS the boundary where you can't verify it")
applies to one of these tables and not the other. Following it *per table* yields:
read directly under RLS; write through the edge function. Which looks like
inconsistency until you notice it is the same rule applied twice.

I nearly wrote it the uniform way — a new `get_ai_conversations` brand-portal
action for the read — and rejected it for a reason I only saw after doing the
handler survey in §2: routing the read through `brand-portal` would move the
guarantee off a policy whose text I had just read and onto
`verifyRestaurantAccess`, which is currently defeated in five of nine files in
that very directory. For *this* table, RLS is the better-verified boundary. That
is genuinely counterintuitive relative to ADR-006's headline and is why the ADR
spells out the per-table reasoning rather than citing the precedent and moving on.

**The one thing I could not close, and how the design handles it.** No tracked
migration *creates* `ai_conversations` — only the RLS migration exists. So
nothing proves the RLS migration was ever applied to the live project. If RLS is
off there, default `authenticated` grants make the whole table readable and AC1's
server-side half is unmet. I had no DB access this pass. Rather than assume, I set
`touches_data: true` and gave `database` a read-only verification task with an
explicit stop condition — if RLS is not enabled, **stop and report**, and the
read path inverts to the `brand-portal` action I otherwise rejected (named as the
contingency in both the design's Alternatives table and ADR-013). Same move
`ENG-020`'s design used to make `database` confirm column names against the live
project before writing a migration.

That is also why `touches_data: true` despite there being **no schema change of
any kind**. It felt wrong at first — the template frames the Data section around
migrations, and there is no DDL here. But `database` is the agent with live-project
access, the verification is genuinely load-bearing for AC1, and the alternative
(`touches_data: false`) means nobody is tasked with it and it silently doesn't
happen — the exact "discovered in QA" failure the skill warns about. The Data
section opens by saying plainly that it is a verification task, not a schema task,
so `database` isn't hunting for a migration that isn't there.

## 4. `touches_models: false` — the call and the argument for it

Real question, not a rubber stamp. The FAQ text an owner writes flows into the
bot's prompt context. Does widening the set of principals who can author prompt
context count as touching models?

Six of `ai-architecture-standards.md`'s seven required subsections are unchanged
by construction — no model call is added, removed, rerouted or reconfigured; no
placement, model choice, fallback, output contract, eval, cost limit or kill
switch moves. The seventh, prompt/context provenance, does change: the author set
widens from AIOrders staff to restaurant owners.

I set it `false`, and the argument is empirical rather than definitional:
`ai-search-openrouter` builds its context from `menu, deals, discounts,
locations, faqs` — and the same owner **already** edits menus and offers through
this same portal (`menus.ts`, `offers.ts` are owner-facing brand-portal actions).
So the owner is already an author of four of the five context inputs. Adding the
fifth widens nothing structurally new, and its blast radius is their own
restaurant's bot, which they already control by four other routes. Writing seven
subsections where six say "unchanged" would be exactly the padding the skill
names as a failure mode.

I did not want that reasoning to vanish into a boolean, so it is stated as a Risk
in the design with the evidence attached. If prompt-injection hardening is ever
wanted, it belongs to the bot's ticket and covers all five inputs.

## 5. PII — deciding it rather than escalating it

The PRD explicitly refused to resolve this by omission and asked for it to be
looked at plainly. Checked against the skill's step 8 definition of a one-way
door: no new datastore, no vendor, no auth-model change, no public contract, no
data model to migrate, no recurring cost. Reversible in every direction — the
whole decision is display-layer properties over rows nobody is modifying. So:
decide it, record it, move on. ADR-014.

The substance I want preserved from the reasoning:

- The owner is **already** the authorised reader. The tracked policy granting
  exactly this has existed since 2025-09-03 and nothing has ever used it. This
  ticket doesn't widen the reader set; it builds the first surface for a grant
  already written for this purpose.
- The custodial shape is the same as a phone call to the restaurant. Withholding
  the question doesn't protect the customer; it means the message reached nobody.
- **Redaction would be the wrong first move**, and I want the specific reason on
  record because "add a PII filter" always sounds like an unambiguous
  improvement. It fails in both directions at once: it over-redacts the case that
  justifies the page ("my son is allergic to peanuts, is the pad thai safe?" is
  precisely what a naive filter mangles and precisely what an owner needs to
  read), and it under-redacts, since most identifying detail in natural language
  matches no pattern. Worse, partial masking implies the remainder was checked.
- So the protection is five structural constraints, not text transformation: no
  new copy anywhere; never in a URL; never in a log line or error payload; user
  turns only (assistant replies never rendered — which AC6 wanted independently);
  no export.

The URL one is the constraint I'm most pleased with, because it fell out of a
design choice I was making anyway. The "Add to FAQs" hand-off needs to carry the
question from `/questions` to `/website`. The obvious implementation is
`?question=<encoded>` — and that writes customer free text into browser history
and every upstream access log, which is the standards' "no PII in log lines" rule
broken through a side door that no reviewer would look at. `navigate('/website',
{ state: { faqDraft } })` costs the same number of lines and keeps it in memory.

The no-export decision is recorded explicitly *because* it is an absence. Nobody
asked for an export button, and an export is the single change most likely to
turn an authorised view into a data-loss event — an uncontrolled copy on a laptop,
outside the RLS boundary, forever. I'd rather a future reader find "deliberately
omitted, here's why" than read the gap as an oversight to helpfully fill.

## 6. Smaller calls worth a sentence each

**Bounding the query.** Volume is unverifiable from the repos (the PRD flagged it;
I had no DB tool). Rather than guess a number and design around it, I bounded at
100 sessions so the design is correct at 3 sessions or 30,000, and asked
`database` to return the real distribution as verification item 3 — with a
**named review trigger** in the design: under ~20 max sessions, "Load older" is
dead weight and should be dropped; over ~1MB per page of `messages`, the bound
moves down. Pagination is **keyset** (`.lt('updated_at', cursor)`), not offset,
because the bot upserts rows continuously and an offset window would skip and
duplicate rows under a live writer.

**Nullable timestamps are a real edge, not a hypothetical.** Both `updated_at`
and `created_at` are `string | null` in the generated types, even though the bot's
`saveConversationContext` always writes `updated_at`. So: order with
`nullsFirst: false`; a null-dated row is the undatable tail and cannot be a
cursor, so "Load older" hides rather than re-fetching the same page forever. That
one is in the Failure behaviour table because it's the kind of thing that becomes
an infinite spinner in production.

**`messages` is unvalidated jsonb.** No schema enforcement anywhere. The
normaliser has to be total: non-array `messages` yields zero rows; malformed
elements are skipped; an unparseable message `timestamp` falls back to the
session's `updated_at`; nothing throws. Written as a table in Interfaces so it's
testable rather than implied.

**Not copying `feedback/Index.tsx`.** Its `queryFn` catches errors, toasts, and
`return []` — which makes a failed query render identically to a restaurant with
no activity. That is exactly the confusion AC2 exists to prevent, so the new page
throws from `queryFn` and renders a distinct error state with retry. Noted in the
Alternatives table so it reads as a decision, not as inconsistency with the
neighbouring page.

**Two editors, one column — last write wins.** AC5 asks for one source of truth
and gets it; the price is that `aiorders-admin-hub`'s staff editor does a
**whole-row upsert** across `story`, `faqs` and more, so a stale staff page can
silently overwrite an owner's FAQ edit. There is no version column, ETag or
`updated_at` precondition on the table to detect it with. I accepted it rather
than building optimistic concurrency for a two-writer, low-frequency surface
nobody has reported a collision on. Two free mitigations: the existing
`saveMutation.onSuccess` already invalidates and refetches so the owner sees
stored truth immediately; and the owner-side patch sends only `{ faqs }`, so it
can never be the side that clobbers. The exposure is one-directional
(staff→owner), which is worth knowing when someone eventually reports "my FAQ
disappeared."

**ADR-009's clobber lesson, one level down.** That ADR found `CateringPageForm`
silently wiping unknown keys because it reconstructs its object from an explicit
field list instead of spreading `...content`. The same trap exists per-FAQ-item
here if the editor rebuilds `{ question, answer }`. Today the shape really is
just those two fields (`config-site-builder`'s `FAQ` interface confirms it), so
it costs nothing to be safe: patch items by spreading `{ ...faq, question }`.
In the Failure behaviour table.

**AC3's two readings.** The PRD's binding AC says "directly from the brand
portal"; the ticket's Outcome says "directly from **that view**." The stronger
reading is cheap to satisfy — a per-row button plus location state — so I
satisfied it rather than arguing the weaker one, without merging the two pages or
duplicating the editor.

**Blast radius the PRD didn't know about.** `restaurant_website.faqs` isn't only
read by the bot. It renders on the public site, and
`config-site-builder/src/utils/structuredData.ts` emits it as schema.org
`FAQPage` structured data for search engines. I also checked whether
`get-brand-website` applies the brand-metadata override that bit ADR-009 for
`catering` — it does **not**: `faqs` resolves straight from `restaurantData.faqs`
(with a `location.faqs ||` preference for per-location overrides). Good for
AC4/AC5, since there's no precedence trap. But it means an owner-authored FAQ is
published and indexed, not just chatbot fodder — so the editor has to say so in
its own copy. That's a UI requirement I would not have derived from the PRD.

**Naming left alone.** `EDITABLE_PAGES` now holds a non-page column and the name
is slightly wrong. Renaming it is cosmetic and would create a needless conflict
with ENG-022's unmerged edit to the same file. Comment widened, identifier
untouched, noted in Out of scope.

## 7. Routing (step 11)
