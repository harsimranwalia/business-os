### Why "manually verified" doesn't apply here

`definition-of-done.md`'s manual-verification allowance is for when
"automation genuinely can't reach" the thing. That's not this repo's
situation: `restaurant-portal` has a working test runner (`vitest`) and,
more specifically, **direct, repeated, on-point precedent for testing this
exact shape of component** —

- `src/components/autopilot/BroadcastReport.test.tsx` — a report component
  that fetches data (via a mocked hook) and asserts specific numbers and
  conditional sections (`"Coupon Performance"` block present/absent) render
  on screen, with test names tagged to the AC they cover (`"(AC4)"`,
  `"(AC5)"`).
  `src/components/catering/CateringDetailModal.test.tsx`,
  `src/components/catering/CateringKanban.test.tsx`,
  `src/components/website/CateringPageForm.test.tsx` — the same pattern,
  used repeatedly on this board (`ENG-032`'s round 2 fix hop added
  `CateringPageForm.test.tsx` for exactly this reason).

`AcquisitionReport` (`src/pages/acquisition/Index.tsx`) and
`ChannelBreakdown` (`src/components/acquisition/ChannelBreakdown.tsx`) are
architecturally the closest thing on this board to `BroadcastReport.tsx` —
a page/component that fetches a report over an API call and renders totals,
a breakdown, and conditional messaging. There is no technical barrier and no
convention gap; this is a coverage gap, not a manual-verification case.

### Gap 1 — AC1/AC3, blocking: nothing renders the breakdown and asserts it's on screen — CLOSED round 2

`ChannelBreakdown.tsx` (table + bar chart) and the totals/coverage block in
`Index.tsx` have zero test coverage. Specifically untested:

- The three `StatsCard`s render `data.totals.customers/orders/revenue`.
- The channel table renders one row per `channels[]` entry, each cell showing
  `label`/`customers`/`orders`/`revenue` (`currency.format(...)`), and a
  `direct_unknown` row appears even when its own counts are zero (AC3's
  actual visible claim — proven at the data layer by `acquisition.test.ts`,
  never proven on screen).
  The `low_volume` conditional column (`!lowVolume &&
  <TableHead>Share of revenue</TableHead>` / matching cell) — untested in
  either the shown or the suppressed state.
- The bar chart receives `chartData` derived 1:1 from `channels` — untested
  that the derivation is correct (label/revenue per bar).
- The empty state (`isEmpty`, zero customers and zero orders) and the
  coverage banner's `attributed_pct`/`unattributed_orders` text — untested.

**Specific fix:** add `src/components/acquisition/ChannelBreakdown.test.tsx`
and `src/pages/acquisition/Index.test.tsx` (or fold both into one file if
that matches how `CateringDetailModal.test.tsx` structures a
component-plus-container pair — either is fine), following
`BroadcastReport.test.tsx`'s own pattern: mock `brandPortalApi.getAcquisitionReport`
(or wrap the page in a `QueryClientProvider` with a pre-seeded query cache,
whichever this repo's own convention for a `useQuery`-driven page already
uses elsewhere — check `reports/Index.tsx`'s own test if one exists, since
the design cites it as this page's idiom twin). Minimum cases:

1. Renders totals (`customers`/`orders`/`revenue`) from a fixture response.
2. Renders one table row per channel, in the fixture's given order.
3. `direct_unknown` row renders even when its own counts are zero (the AC3
   claim, on screen).
4. A channel other than `direct_unknown` with zero customers/orders is not
   rendered as a row (mirrors the backend's own "omits a zero-value channel"
   test, one layer up).
5. `low_volume: true` suppresses the "Share of revenue" column; `false`
   shows it.
6. Empty state renders when `totals.customers === 0 && totals.orders === 0`.
7. Error state renders on a thrown query error.

### Gap 2 — AC2, blocking: no test that changing the range refetches/updates the figures — CLOSED round 2

`resolveRange` (pure function, `Index.tsx:20`) has zero direct test coverage
of its own date-window math (30d/90d/12m/this_year boundaries), and nothing
exercises the `Select` → `setPreset` → `useQuery` key change → new
`getAcquisitionReport` call path end to end.

**Specific fix:** `resolveRange` is already a small pure function — export it
and unit-test each preset's `from`/`to` boundary (fixed a reference "now" via
`vi.setSystemTime` so the assertions aren't flaky against the real clock, the
same reason `dispatch.test.ts` elsewhere on this board fixes its own clock
for due-date math). Separately, one rendering test: select a different range
option, confirm `brandPortalApi.getAcquisitionReport` is called with a new
`from`/`to` pair and the rendered totals update to match a second mocked
response.

### Gap 3 — AC4, blocking: the honesty framing itself is unverified — PARTIALLY CLOSED round 2 (disclaimer only — see Gap 4)

Nothing asserts that the organic-search disclaimer paragraph
(`Index.tsx:138-143`), the coverage sentence, or the low-volume caveat
actually render under the conditions the design specifies. This is the
criterion the PRD itself calls "not generic caution" (AC4 exists because a
last-touch number would otherwise overstate SEO's effect) — the exact case
where "traced it by hand and it reads correct" is weakest as a substitute for
a test, since the whole point is that a *user* sees the honest framing, not
that the code merely computes it.

**Specific fix:** covered by Gap 1's cases 1–3 plus two more: the organic
disclaimer paragraph renders when `channels` includes an `organic_search`
entry, and does not render when it doesn't.

### Gap 4 — AC4, blocking: the coverage sentence and low-volume caveat are set in every fixture but never asserted — CLOSED round 3

Round 2's fresh re-check, not just confirming the round-1 fix closed what it
said it would. The round-1 fix hop closed Gap 3's disclaimer-paragraph cases
exactly as specified, but Gap 3's own narrative named three unverified things
and the "Specific fix" bullet only asked for one of them — the other two
shipped with the rest of the round-2 diff, still untested. Confirmed by grep,
not assumed: `grep -rn "low_volume\|attributed_pct" src/pages/acquisition/
src/components/acquisition/` shows both fields set in every `Index.test.tsx`
fixture (`coverage: {..., attributed_pct: 61}`, `low_volume: false`) but never
read back with `getByText`/`findByText` anywhere in either new test file.
`low_volume: true` is never set in any `Index.test.tsx` fixture at all — the
caveat sentence's own render branch (`Index.tsx:108-112`) has zero test runs
that could reach it, not even incidentally.

This matters specifically because the architect's own design names this the
same AC4 the disclaimer serves, not a separate concern: `agents/architect/
designs/ENG-020-*.md` → "Risks" → "Attribution honesty — AC4" lists **four**
concrete mechanisms, and item 4 is exactly this — "`coverage.attributed_pct`
is always rendered. A report that can say '42% of your orders could not be
attributed' can also say SEO is not working, which is the PRD's own test for
honesty." The low-volume caveat is the same mechanism's small-restaurant case
(design → "Risks" → "Small-restaurant noise": "a plain-language line saying
there were too few orders in the period to show a reliable mix"). A
regression that silently deleted either sentence — or one that always showed
the low-volume caveat regardless of `low_volume`'s actual value — would pass
every test that exists today.

**Specific fix:** two additions to `Index.test.tsx`, no production-code
change implied by either:

1. Assert the coverage sentence renders with the fixture's actual numbers
   (e.g. `screen.getByText(/61% of orders in this period could be traced to a
   source/)`, or a substring match tolerant of the exact punctuation) against
   the existing `baseReport()` default.
2. A fixture with `low_volume: true` (none of the six existing `Index.test.tsx`
   cases use one) asserting the "too few orders" caveat renders, and confirm
   the existing `low_volume: false` default fixture asserts it does *not*
   render — the negative case, not just the positive one, per this repo's own
   `ChannelBreakdown.test.tsx` pattern for the same field one component over.

## Failure paths

| Scenario | Expected behaviour | Test |
|---|---|---|
| Caller does not manage the requested restaurant | Denied server-side, no data about that restaurant returned | `acquisition.test.ts` — "denies a restaurant the caller does not manage", mutation-verified |
| Missing/invalid `restaurant_id` | Rejected with a specific message | `acquisition.test.ts` — two tests (missing, non-uuid) |
| Unparseable date / `from > to` | Rejected with a specific message | `acquisition.test.ts` — two tests |
| Range > 3 years | Rejected, never silently clamped | `acquisition.test.ts` — "rejects a range spanning more than 3 years" |
| RPC not yet deployed (migration/edge-function deploy ordering) | Distinct "not available yet" message, no stack trace to the client | `acquisition.test.ts` — "reports the RPC-missing case distinctly", independently re-run |
| RPC errors otherwise | Generic message to the client, real error only to `console.error` | `acquisition.test.ts` — "reports a generic failure without leaking the underlying error" |
| Customer/guest order with no attribution data | Counted in `direct_unknown`, never dropped | `acquisition.test.ts` — the `(NULL,NULL,NULL)` tuple test |
| Fewer than 30 orders in range | `low_volume: true`, coverage still computed | `acquisition.test.ts` — "sets low_volume under 30 total orders" |
| Portal deployed ahead of the API | Page renders the "not available yet" error state, not a blank/crash | **Not automated — frontend has no test reaching this branch; the backend side (RPC-missing) is covered above** |
