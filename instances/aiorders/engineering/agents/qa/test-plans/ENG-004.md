## Failure paths

This ticket adds no application behaviour, endpoint, or user input — there is
no negative/authz case in the usual sense. What matters for a
*migration-history reconciliation* ticket is silent drift between what's
recorded here and what's actually true in git, or a future pass drawing a
conclusion from the wrong source:

| Scenario | Expected behaviour | Check |
|---|---|---|
| Either repo's `supabase/config.toml` silently repoints to a different Supabase project | AC1 fails | Direct `config.toml` read, this pass |
| `aiorders-admin-hub`'s `origin/main` regains a `supabase/migrations/` directory (e.g. a revert) | AC2 fails | Direct `git ls-tree` on `origin/main`, this pass |
| The six files' content silently diverges between the two repos | AC3 fails | Fresh SHA-256 hash comparison, this pass — all six identical |
| A new migration lands between `restaurant_activations` and `google_review_history` in sort order, or a rename breaks the ordering | AC4 fails | Direct `git ls-tree` + sort, this pass |
| `aiorders-admin-hub`'s local `main` drifts ahead of `origin/main` again (a new uncommitted change) | AC5 fails | `git rev-list --left-right --count`, this pass — `0	0` |
| A future pass trusts a worktree's own (possibly stale) branch instead of `origin/main` for this repo | Wrong conclusion, silently | Named as a residual risk in the design doc's Risks section; this review and this test plan both read `origin/main` directly (`git show`, `git ls-tree`), never the `_eng/` worktree's own checked-out files |

## Regression risk

None to any live application or schema — the six migrations' effects (RLS
policies, the `restaurants_public` view, the `restaurant_activations` table)
were already live before, during, and after both the original deletion and
its resolution; this ticket changes only which repo's *tracked file history*
matches that already-live reality. The one real risk this ticket's subject
matter touches is disaster-recovery replay integrity, which AC4 directly
covers.

## Not automated

All five ACs are direct git/disk-inspection checks by design (`ADR-001`,
extended by `ADR-004`) — there is no suite to wire into
`skills/test-suite-run/SKILL.md` for a ticket with no application code, and
`config/projects.md` confirms neither registered project (`aiorders-admin-hub`,
`aiorders-api`) has a test command that would apply here regardless.
