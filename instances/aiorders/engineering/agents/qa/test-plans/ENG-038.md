### Gap 1 — AC4, blocking: redemption/revenue has no test of its actual logic — CLOSED round 4

`brand-portal/broadcasts.ts:560-603` (`getBroadcastReport`, the
`if (campaign.offer_id)` branch) — fetches the attached offer's
`coupon_code`, fetches this restaurant's orders since
`campaign.scheduled_send_at`, filters to orders whose `promos` array
contains a matching `code`, counts them and sums `total_amount`. This is
AC4's entire implementation (the code's own comment at line 554 names AC4
directly), and it is real branching logic with a realistic bug surface:
array matching against nested JSON, a `.single()` lookup that fails
silently into `redemptions/revenue` staying `null` if the offer's own row
is missing, `Number(order.total_amount) || 0` silently zeroing a malformed
amount. Both existing `getBroadcastReport` tests set `offer_id: null`, so
neither one ever enters this branch — confirmed by reading both tests in
full (`broadcasts.test.ts:115-159`) and grepping the whole repo's test
files for `redemption`/`revenue`/`coupon_code`/`getBroadcastReport` (one
unrelated hit, `loyalty-config.test.ts`, a different feature).

A restaurant owner attaching a coupon to a campaign to measure its ROI —
the entire point of AC4 — would see whatever this untested branch computes,
right or wrong, with nothing having ever proven it right.

**Specific fix:** extract the matching+summing logic into a pure function,
e.g. `computeRedemptions(orders: {total_amount: number, promos:
{code: string}[]}[], couponCode: string): {redemptions: number, revenue:
number}` — no Supabase client inside it, data in, data out, same shape as
this ticket's own `buildBroadcastSmsBody`. Cover: a matching order counted
and summed; a non-matching `promos` entry excluded; an order with no
`promos` array excluded; multiple matches sum correctly; empty input →
`{0, 0}` (zero, not null — the null-vs-zero distinction is correctly the
*caller's* job for "no offer attached" one level up, so this function's own
empty-set behaviour should be zero).

### Gap 2 — AC5 (read half), blocking: delivery-by-channel aggregation untested beyond empty — CLOSED round 4

Same function, `broadcasts.ts:541-552` — buckets `communication_log` rows
by channel, counts `sent`/`delivered` as sent, counts `opened_at`/
`clicked_at` presence as opened/clicked. Both existing tests stub
`communication_log: () => ({ data: [], error: null })`, so this loop body
never executes on a non-empty input. Lower risk than Gap 1 (counting logic,
no arithmetic on money, no nested-array matching), but zero coverage of any
real branch is zero coverage.

**Specific fix:** extract into a pure function, e.g.
`buildDeliveryByChannel(logRows: {channel: string, status: string,
opened_at: string | null, clicked_at: string | null}[]): Record<string,
{sent: number, opened: number, clicked: number}>`. Cover: two channels
bucketed independently; `sent`/`delivered` both count as sent, `failed`
does not; `opened`/`clicked` counted only when their timestamp is present.

### Gap 3 — AC6, blocking: the unsubscribe mechanism itself has no test — CLOSED round 4

`_shared/broadcastUnsubscribe.ts`'s `signUnsubscribeToken`/
`verifyUnsubscribeToken` and `broadcast-unsubscribe/index.ts`'s handler
have zero test coverage anywhere — confirmed via `grep -rl
"verifyUnsubscribeToken\|signUnsubscribeToken\|broadcast-unsubscribe"
--include="*.test.ts"`, whose only hit is a test-fixture URL string that
happens to contain that path segment as flavor text, not an actual call
into either file. This is a **public, unauthenticated endpoint that mutates
a customer's consent state** off a cryptographic token, on a feature the
PRD's own Risks section explicitly flags for CASL exposure — the highest-
stakes of the three gaps in this report, since a bug here either fails a
real unsubscribe request (compliance exposure) or, if a token-handling bug
ever crossed wires between customers, flips the wrong one's consent.

Unlike Gaps 1–2, `signUnsubscribeToken`/`verifyUnsubscribeToken` need **no
extraction** — both are already exported, and both touch nothing but
`Deno`'s built-in `crypto.subtle` and one env var (`Deno.env.get(
'BROADCAST_UNSUBSCRIBE_SECRET')`, settable by a test itself via
`Deno.env.set(...)` without needing the real production secret). They can
be unit-tested directly, today, as written.

`broadcast-unsubscribe/index.ts`'s own handler (channel validation,
customer-not-found handling, the idempotent-already-unsubscribed check, the
consent-merge write, the distinct retry-vs-invalid-link response choice) is
real branching logic trapped inside a bare `serve()` callback — the same
shape `broadcast-dispatch/index.ts` solved by keeping `serve()` as a thin
adapter over `dispatch.ts`'s testable exports. `ENG-033`'s own precedent
for a `serve()`-level handler with no extracted equivalent (`catering-
request`, AC-10) accepted "verified by construction" only because no
extraction pattern existed anywhere in this repo at the time — it now does
(`dispatch.ts`, and after this ticket's own fix, `consumers.ts`), so the
same acceptance doesn't carry over here by default.

**Specific fix:** (a) add `broadcastUnsubscribe.test.ts` covering
`signUnsubscribeToken`/`verifyUnsubscribeToken` directly — a sign-then-verify
round trip returns the original `customerId`; a malformed token (wrong part
count, bad base64url) returns `null`; a tampered signature returns `null`;
a missing `BROADCAST_UNSUBSCRIBE_SECRET` throws from `hmacKey()` (F1's own
finding lives here too — cheap to close in the same pass, still
non-blocking on its own). (b) Extract `index.ts`'s decision logic (given a
verified `customerId` or `null`, a `channel`, an existing consent value, and
whether the update write errored → which of the four responses to return)
into a pure function the same way, and test each of the four response
branches: invalid channel, invalid/missing token, already-unsubscribed
(idempotent), and the write-failure retry case.

**All of (a) and (b) done, verified this round** — see
`agents/principal-engineer/reviews/ENG-038.md`'s test-quality section for
the independent regression run and the two mutation tests against
`decideUnsubscribePreCheck`.

### Gap 4 — AC5 (write half), blocking: the send-and-log write itself has no test — CLOSED round 5

`outgoing-communications/actors/consumers.ts:881-1020`
(`sendBroadcastMessage`) — resolves the customer and restaurant, gates each
channel on consent/content/contact-info (`wantsEmail`/`wantsSms`), sends via
`sendEmail`/`sendSMS`, and inserts one `communication_log` row per attempted
channel with `status` set from the send result. This is real branching logic
with a realistic bug surface (the per-channel gate, the `anySucceeded`
aggregation, the "no eligible channel" skip path, what gets written when one
channel succeeds and the other fails) — read line-by-line this round; no
confirmed defect found, but nothing has ever proven any of it right.
Confirmed via `grep -rn "sendBroadcastMessage"` across the repo: `dispatch.ts`
exports an unrelated function of the same name (an HTTP wrapper that POSTs to
`outgoing-communications`, injected as a fake in `dispatch.test.ts` per this
repo's "mock at the boundary" convention) — so `dispatch.test.ts`'s 10/10
never reaches this function at all, and `grep -rl "sendBroadcastMessage"
--include="*.test.ts"` returns nothing. `consumers.test.ts` covers only the
two pure body-builder functions this handler calls, not the handler itself.

This was already visible in round 3's own report, in the "Not automated"
section under AC5 (write): "not filed as its own numbered gap because the
read half (Gap 2) already fails the gate for this AC, and fixing both by the
same extraction pattern in one pass is the efficient path, not two" — a
reporting-efficiency deferral, not a substantive judgement that this path is
safe to leave untested (contrast AC3's restaurant-scoping note in the same
section, which stands on its own design reasoning and stays non-blocking).
The round-3 fix hop closed Gaps 1–3 as literally numbered and did not pick up
this parenthetical. Now that Gap 2 no longer masks it, AC5 as a whole is
still failing on this half, and the quality gate's own definition ("fails
when... an acceptance criterion has no passing test") applies plainly.

**Specific fix:** same remedy as Gaps 1–3 — extract the parts of
`sendBroadcastMessage` that don't need a live network call or a real
Supabase client into pure, testable pieces (at minimum, the per-channel
gate `wantsEmail`/`wantsSms` and the `communication_log` row shape each
branch builds), and test with a fake `supabase` client the same way
`broadcasts.test.ts` already fakes `supabase.from()`. Cover: email-only,
SMS-only, both, neither-eligible (the skip path), one channel succeeds and
the other fails (confirms `anySucceeded` and the per-row `status`
independently), and that each inserted row carries
`reference_type: 'broadcast_campaign'`/`reference_id: campaignId` — the
same shape `buildDeliveryByChannel` (Gap 2, now closed) reads on the other
end.

**Done and independently verified this round** — `decideBroadcastChannelEligibility`,
`buildBroadcastEmailLogRow`, and `buildBroadcastSmsLogRow` extracted exactly
as specified; `sendBroadcastMessage` exported with an injectable `deps`
parameter (`sendEmail`/`sendSMS`/`buildUnsubscribeUrl`) so the orchestration
itself is testable against a fake Supabase client with no network touched.
All five cover cases present in `consumers.test.ts` and mapped 1:1 to this
list, including the `reference_type`/`reference_id` stamp check. See
`agents/principal-engineer/reviews/ENG-038.md`'s test-quality section for
the independent regression run and two fresh mutation tests against this
round's new logic.
