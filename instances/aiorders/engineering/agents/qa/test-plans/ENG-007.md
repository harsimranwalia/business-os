## The gap that matters most: no live database this pass

**None of this ticket's database-dependent behavior (the trigger's actual
insert-time enforcement, RLS, the FK/check constraints, a real GET/POST
round trip) was exercised against a live or throwaway Postgres.** Docker
Desktop is installed on this host; it was launched and polled for its
daemon becoming ready for roughly 170 seconds across two bounded attempts
and did not come up in time. This is a materially different, and weaker,
situation than ENG-006's own test plan, which *did* reach a throwaway
container for its schema-level verification.

What stands in its place, stated plainly rather than papered over:

- **Every piece of decision logic that determines the *response*** — who's
  allowed to call this, whether a body is well-formed, which row is
  "current" as of a given instant, how a trigger's rejection maps to an
  HTTP status — is pulled out into pure, DB-free functions and has direct,
  real `deno test` coverage (37 of this ticket's 44 tests).
- **The trigger's own SQL logic** was hand-traced against concrete
  sequences (first insert, backdated insert, non-increasing insert, two
  concurrent inserts for the same vs. different restaurants) and
  cross-checked character-for-character against three pieces of code
  already applied to this exact live database (`restaurants.id`'s type,
  `api_keys.created_by`'s FK shape, `restaurant_activations`'s dedicated
  trigger-function convention). Full trace:
  `agents/database/migrations/ENG-007-per-restaurant-loyalty-configuration.md`.
- **What this does NOT prove:** that the migration file actually applies
  without a syntax error against a real Postgres, that the advisory-lock
  serialization behaves as reasoned under real concurrent load, or that RLS
  denies a client role in practice rather than only in the policy's stated
  intent. A live or throwaway-container run would prove all three and
  hasn't happened yet.

**Not filing this as a new finding distinct from the database migration
doc's own gate verdict** — it's the same gap, stated there first
(`agents/database/migrations/ENG-007-per-restaurant-loyalty-configuration.md`
→ Gate verdict: "pass, with a named verification gap"). Restated here so
this quality gate's own record doesn't imply stronger DB-level evidence
than actually exists, and so it surfaces again at the release-readiness
step where it's most actionable (a live-project migration dry run before
the PR merges, if the approver wants one).

## Why the DB-dependent branches stay unautomated, stated rather than waved past

Same repo-wide gap ENG-006's own test plan named: this repo has 47 edge
functions (46 plus this ticket's own) and zero precedent for mocking or
standing up a Supabase client inside a unit test. Building that
infrastructure is bigger than an `S`-sized ticket and would itself be an
unrelated-refactor automatic-failure if bundled in here. This ticket
narrows the practical size of the gap versus ENG-006's — by construction,
every *decision* is pure and tested, leaving only two thin `.from(...)`
calls untested — but does not close it.

## Regression risk

Purely additive: one new table (nothing existing altered except the README
catalog entry), one new handler module, a 2-line addition to
`admin-portal/index.ts` following the exact shape of every existing route
in that file. Nothing currently in production calls `/admin-portal/loyalty-config`
— no frontend exists anywhere in this sequence (explicit PRD non-goal) — so
this diff cannot regress any live behavior today.
