## The gap that matters most: no live app, either tier

**Neither side of this ticket was exercised against a running instance.**
`aiorders-api`: no Docker, no `psql`, no `supabase` CLI on this host (same
gap the migration doc and code review both name) — the handler's new
code path (`readBrandAnalytics` → KV → `deriveStage`/`deriveHealth`) has
never actually executed against a live `brands`/`orders` table.
`aiorders-admin-hub`: the worktree has no `.env` (no Supabase URL or
anon key), so `npm run dev` cannot reach a real backend — a live
`localhost:8080` session would show connection errors unrelated to this
diff, not real signal about whether the new columns/filter render
correctly. Checked before deciding to skip it rather than assumed: no
env file exists anywhere in this worktree (`find . -maxdepth 1
-iname ".env*"` — empty).

What stands in its place, stated plainly:

- **Every piece of decision logic** — which bucket a brand's stage/health
  falls into, given its raw columns — is pulled into two pure functions
  and has direct, real `deno test` coverage (12 of 12 tests target
  exactly these two functions).
- **The frontend's filter/render composition** was traced against the
  actual committed code, statement by statement, the same way a reviewer
  reads a diff — not run, but not guessed at either.
- **What this does NOT prove**: that a real Brands-page load actually
  shows the right pill for a real brand, that the KV read succeeds
  against the live Cloudflare account and its actual key format, that
  the stage filter dropdown's selected value survives a real render
  cycle, or that AC6's authz gate still rejects a non-staff caller now
  that the response body is larger. A live app session — either a
  throwaway Postgres for the backend or real `.env` credentials for the
  frontend — would prove these and hasn't happened yet.

This isn't a new gap this ticket invents: `aiorders-api` has zero
container-based verification precedent in this repo's history
(`ENG-006`'s migration doc, `ENG-007`'s test plan) and
`aiorders-admin-hub` has never had a QA gate run against it before (this
is the project's first ticket to reach this state) — so there's no
"regression from a prior baseline" here, only an honest statement of
what today's evidence does and doesn't cover.

## Failure paths

| Scenario | Expected behaviour | Check |
|---|---|---|
| Brand has no orders ever (new, or never processed through CloudWaitress) | `health: 'no_data'`, rendered distinctly from `inactive` | `deriveHealth(null)` test; `getHealthPill`'s `no_data` branch traced — distinct background/text color from `inactive` |
| Brand has real orders, but the last one was over a year ago | `health: 'inactive'`, never coerced into `no_data` | `deriveHealth` test with a 400-day-old timestamp — asserts `inactive` specifically, not merely "not active" |
| KV read fails or times out for one brand mid-list | That brand reads `no_data`; the rest of the list still renders | `readBrandAnalytics`'s own `catch` returns `null` on any fetch error or non-2xx/404 status, logged server-side via `console.error`, never thrown — traced in code, not exercised against a real network failure this pass |
| CF_ACCOUNT_ID/CF_ANALYTICS_KV_ID/CF_API_TOKEN unset in this environment | Every brand reads `no_data`, no 500 | `getKVConfig()` returns `null` (not a throw) when any of the three is missing; `readBrandAnalytics` treats a `null` config as `no_data` immediately, before attempting a fetch |
| `onboarding_step` is `null` on an inactive brand | Reads as `onboarding`, not `inactive` — a never-started brand shouldn't look churned | `deriveStage(false, null)` test, explicit about the reason (the `?? 0` fallback) |
| Deploy order: `aiorders-admin-hub` reaches production before `aiorders-api`'s new fields exist | Every row's Stage/Health cell shows `-`, not a crash | Traced in `getStagePill`/`getHealthPill`'s `default` branches — see code review's Design conformance section |

## Regression risk

Additive on both repos. `aiorders-api`: one function's output gains a
column (existing readers destructure by name, not position — `row.total_orders`
style access throughout, confirmed by reading `platform-analytics/index.ts`'s
own consumption of the RPC result), one handler's response gains two
JSON fields, one new file, one new util. `aiorders-admin-hub`: two new
table columns and one new filter control on one page; every existing
filter's behavior (`statusFilter`, `brandTypeFilter`, `searchTerm`) is
untouched — `matchesStage` is `&&`-composed alongside them, not replacing
any of them. Nothing currently live depends on the removed/changed lines
in either diff (the migration replaces a function whose only callers are
named and checked in the database migration doc).
