## Round 1 finding: AC-5/6/7's own derivation logic had no test — resolved round 2

**Resolved this round.** The fix hop extracted the block described below into
`deriveActionStatus()` in `validation.ts` and `index.test.ts` now covers all
five cases this finding named (absent, unrecognised, the
`MANUAL_CONTACT_REQUESTED`-with-selections discard case, `QUOTE_SUBMITTED`
valid, `QUOTE_SUBMITTED` invalid) — see Acceptance coverage above.
principal-engineer's round-4 review independently mutation-verified the
discard-on-purpose case and the absent/unrecognised fallback case rather than
trusting the fix hop's own account; both failed for the right reason under
mutation. Kept below as the original finding record.

`index.ts:247-264` is the code that actually implements AC-5, AC-6 and
AC-7 — the branch that reads `action_type`, decides `derivedStatus`, and
decides whether `selections` gets stored or force-nulled:

```ts
const normalizedActionType = VALID_ACTION_TYPES.includes(action_type) ? action_type : null;
let normalizedSelections: unknown = null;
let derivedStatus: string | undefined;

if (normalizedActionType === 'MANUAL_CONTACT_REQUESTED') {
  derivedStatus = 'Contact Requested';
} else if (normalizedActionType === 'QUOTE_SUBMITTED') {
  if (!isValidSelections(selections)) { /* 400 */ }
  normalizedSelections = selections;
  derivedStatus = 'Quote Generated';
}
```

`index.test.ts` imports only `isValidSelections` from `validation.ts` —
nothing calls into this branching logic itself, because it has no exported
entry point; it lives inline inside `serve(async (req) => {...})`, the same
reason `isValidSelections` had to be extracted in the first place (`index.ts`
calling `serve()` at module scope means importing it for a test starts a
real listener). Manually traced this round, line by line, against the
design's own validation table (`agents/architect/designs/ENG-016-catering-
quote-generator.md`, `### catering-request — additive request fields`) and
confirmed it matches exactly — every row of that table is correctly
implemented. But that is a read, not a test: it is exactly what
`agents/qa/agent.md` names first among what QA refuses — **"Signing off on
'manually verified' for something automation could reach."**

This is reachable. Unlike the branches `platform-customer-auth/
handler.test.ts` itself names as genuinely unreachable ("invalid session,
DB errors, the successful-link path... need a real or mocked Supabase
client, which this repo has no precedent or infrastructure for"), this
derivation logic touches no `req`, no `supabase`, no `fetch` — it is a pure
function of `action_type` and `selections` masquerading as inline handler
code. The design itself calls this logic out as load-bearing ("the one
place this ticket lets external input influence a field the owner acts
on"), which raises rather than lowers the bar for verifying it by
execution instead of by reading.

**Specific fix:** extract the derivation block above into a small, pure,
exported function alongside `isValidSelections` (same file or a new one —
shape is the implementing engineer's call, same latitude round 2 gave for
the `isValidSelections` export), and have `index.ts` call it. Cover at
least:

- `action_type` absent → no status, `selections` null
- `action_type` present but not one of the two literals (e.g. `"bogus"`)
  → same as absent
- `action_type = 'MANUAL_CONTACT_REQUESTED'` **with a non-empty `selections`
  also sent** → `status = 'Contact Requested'`, selections still forced
  `null` — this is the one case most likely to silently regress, since it's
  a discard-on-purpose behaviour the same shape as round 1's own note bug
  (a value present in the payload that must not survive into storage)
- `action_type = 'QUOTE_SUBMITTED'`, valid selections → `status = 'Quote
  Generated'`, selections stored as-is
- `action_type = 'QUOTE_SUBMITTED'`, invalid selections → the signal
  `index.ts` uses to return its 400 (whatever shape the extraction takes)

until round 2's finding closed it this round: covered by `index.test.ts`'s

see AC-10 below), but the "unaffected by construction" argument is the
design's own, checked against the actual migration and the actual
destructure list rather than taken on faith.

## Not automated

- **AC-10 (existing-caller compatibility).** No integration test exists for
  `catering-request` as a whole — the function has never had one, before or
  after this ticket, because it calls `serve()` at module scope with no
  extracted `handleRequest` equivalent (unlike `platform-customer-auth`)
  and this repo has no precedent anywhere in its 46 edge functions for
  mocking the Supabase client a full run would need. Verified by
  construction instead, same as the design's own argument: the new
  destructured fields (`action_type`, `selections`) are additive and every
  existing caller's payload has neither key, so the destructure simply
  binds them to `undefined` and every downstream branch treats that
  identically to an explicit absent value — read directly against the
  current diff this round, not assumed from the design doc's claim.
- **AC-13 (authorization on the new columns).** Out of scope for this
  ticket's own diff, not merely hard to reach: `catering-request` is an
  intentionally unauthenticated public lead-capture endpoint with no
  ownership check on writes today (any caller may submit a request naming
  any `restaurant_id` — that is the product, not a gap), and it only
  inserts, never updates, so there is no existing row it could leak or
  overwrite. The actual AC-13 mechanism — `brand-portal/catering.ts`'s
  `verifyRestaurantAccess` and the row-scoped RLS policies `CateringDetailModal`
  reads under — has zero lines touched anywhere in this diff. Same call
  `ENG-032`'s own test plan made for its half of this AC ("no code in this
  diff sits on that path"); `ENG-022`'s suite covers `brand-portal`'s
  access-check call sites generally.
