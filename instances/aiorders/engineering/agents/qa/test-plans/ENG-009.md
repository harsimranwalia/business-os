## Failure paths

| Scenario | Expected behaviour | Test |
|---|---|---|
| Invalid input at the boundary — non-integer/negative/over-ceiling `followers` | 400, specific message, nothing written | `rejects a non-integer followers` / `...a negative followers` / `...a followers count over the 1e9 ceiling` |
| Invalid input at the boundary — non-number/out-of-range `engagement` | 400, specific message | `rejects a non-number engagement` / `...an engagement above 100` / `...a negative engagement` |
| Invalid input at the boundary — non-string / over-length `social_stats_platform` | 400, specific message | `rejects a non-string social_stats_platform` / `...a social_stats_platform over 32 characters` |
| Explicit clear of `social_stats_platform` | Persists `null`, does **not** bump `social_stats_updated_at` (platform alone isn't a "social stats" write) | `PATCH clears social_stats_platform on explicit null` |
| Unauthorised caller on the new `GET /influencers/activity` route | 403, denied before any database call | `GET activity rejects a non-admin caller with 403` (proxy `adminSupabase` throws if invoked — same boundary-loyalty pattern as every other case in this file) |
| Zero-invitation influencer on the activity endpoint | Omitted from the response entirely, not a fabricated zero row | `GET activity omits an influencer with zero invitations rather than inventing a zero row` |
| Downstream Supabase error on the activity aggregate | 500 with a message, logged server-side, frontend degrades to "no activity data" without blanking the influencer list | **Not tested** (no fake simulates a mid-aggregation throw) — same standing gap `getInfluencer`/`updateInfluencer` already carry on this file; frontend side hand-traced: `fetchActivity`'s catch only sets no state, leaving `activityById` at its default `{}`, so every row's activity cell reads "No activity yet" rather than crashing |
| Concurrent write to the same influencer's social figure | Last write wins; `social_stats_updated_at` makes a stale value visible rather than silent (design's own accepted trade-off, no idempotency key needed — write is naturally idempotent) | Not tested (would require a real concurrent-client harness this repo has none of); accepted per design's Interfaces/Failure-behaviour section |
| Re-saving an unrelated field after followers/engagement were already set | `social_stats_updated_at` re-stamps even though the numeric value is unchanged (present-only semantics, not present-and-changed) | `PATCH stamps social_stats_updated_at when followers is written` exercises the stamp; the present-vs-changed trade-off itself is a named, accepted design deviation (see review receipt), not a bug to catch |

## Regression risk

Additive on both repos, extending `ENG-008`'s still-unmerged branch rather
than `main` directly. `aiorders-api`: two new nullable columns
(`social_stats_updated_at`, `social_stats_platform`) and three new entries
in `EDITABLE_FIELDS`; no existing `EDITABLE_FIELDS` entry's validation
branch was touched, confirmed by reading `updateInfluencer` in full — every
pre-existing field (`city_preference` through `collaboration_count`) has
the identical `if ('x' in body) { validate; update.x = ... }` shape it had
before this ticket. New `GET /influencers/activity` route is checked
**before** the generic `/influencers/{id}` match, which changes match
order but not match outcome for any real id (an id equal to the literal
string `"activity"` cannot exist — ids are the table's own generated keys).
`aiorders-admin-hub`: the only lines removed are the unconditional `0`/
`0.0%` renders, replaced by a conditional "Not set" — no existing prop,
fetch call, or unrelated component touched; `fetchData()`'s own
`Promise.all` is untouched, `fetchActivity()` is a fully independent
effect with its own try/catch, so a broken activity endpoint cannot
regress the influencer list itself (verified by reading the two functions
side by side, not just by the design's own claim that this is how it
works).
