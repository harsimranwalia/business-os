## The gaps that matter, named rather than papered over

**No live database this pass — same repo-wide gap `ENG-007`'s own test plan named.** The
"successful PATCH" test uses a hand-built fake Supabase client
(`.from().update().eq().select()` resolving a synthetic row), not a real
Postgres round trip. It proves `handleInfluencers` builds the right shape of
call and returns the right shape of response; it does not prove the six
columns this ticket added actually persist against the live schema, that the
`staff_rating` `CHECK (1–5)` constraint behaves as the handler's own
mirrored check assumes, or that the `barter_visit` backfill in the migration
produced the row states the building pass's row-count query described.
`aiorders-api` still has no live/throwaway Postgres access from this host
(same constraint ENG-007/ENG-011/ENG-013 each already carry) — named here so
this gate's record doesn't imply stronger evidence than exists, same
convention `ENG-007`'s plan set.

**The success test exercises 2 of 6 editable fields end-to-end
(`staff_rating`, `collaboration_count`); the other four
(`city_preference`, `accepts_paid`, `accepts_barter`, `min_visit_payment`)
are proven only at the validation boundary (each has its own rejection
test), not through a successful save.** The construction logic for all six
fields is uniform — each is an independent `if ('<field>' in body) { validate;
update.<field> = body.<field> }` block feeding the same `.update(update)`
call — so this is a real but narrow gap, not six independent unknowns.
Not blocking: the shared mechanism is what the one success test actually
exercises, and duplicating it five more times would test the same six lines
of glue code five more times, not new behaviour.

**`staff_rating: null` (the explicit "clear an existing rating" path) is
inspection-only.** The handler's own guard —
`body.staff_rating !== null && (!Number.isInteger(...) || ...)` — reads
correctly (null short-circuits past the range check and is assigned to
`update.staff_rating` as-is), but no test sends `staff_rating: null` and
asserts a 200 with `staff_rating` cleared. Named as a gap rather than
silently assumed from the code read.

**The new `GET /admin-portal/influencers/{id}` endpoint has zero coverage
beyond its 403 case.** `getInfluencer`'s success path (200 + row) and
not-found path (404) are both untested. Lower priority than it looks: the
frontend added by this same ticket does not call this endpoint at all — the
board still reads influencer rows directly via the existing Supabase-client
`fetchData()` — so this route currently has no live caller. Real gap,
correctly out of automatic-failure #10's scope (that rule is about the
*failure* case on an auth-gated path, which GET's 403 test does cover), so
this doesn't block the gate; it's carried forward rather than closed here.

## Regression risk

Additive only: two new nullable/defaulted columns plus a backward-compatible
backfill of two more (`barter_visit` itself untouched, still readable by any
out-of-repo caller); one new handler file; a 2-line routing addition to
`admin-portal/index.ts` following the exact shape of every existing route in
that file; the CORS `Access-Control-Allow-Methods` widening is additive
(adds `PATCH`, removes nothing). On the frontend, the only *removed* UI is
the read-only "Location Preferences" display block, directly superseded by
the new editable region field in the same dialog — not a regression, a
replacement of display-only by edit-capable in the same ticket. The Payment
Type table badge changed from reading one boolean to reading two; the
building pass confirmed via a live Supabase query that ~17% of rows
(51/306) have both new flags null post-backfill, and the new badge logic
renders "Not set" for that case rather than guessing — verified by reading
the rendering logic, not by fetching a null-flagged row through the UI this
pass.

## Not automated

- Live database round trip for any of the six new/changed columns (gap above).
- `staff_rating: null` clear path (gap above).
- `GET` success (200) and not-found (404) branches (gap above).
- Negative `min_visit_payment` — not rejected, and not asked for by the design (see Failure paths).
- A row with both `accepts_paid` and `accepts_barter` true, saved through the actual handler (only the frontend's ability to check both boxes was read, not exercised against the backend in the same test run).

This list is longer than `ENG-007`'s equivalent gate — that ticket's decision
logic was fully extracted into pure functions with 44 tests; this ticket's
validation is equally well covered, but its *success*-path coverage is
narrower (1 success test vs. exercising every field). Named for whoever
picks up the standing "promote colocated tests to a required step" question
this board has raised twice today (`ENG-013`, this ticket's own round-1 row)
— test *presence* is now enforced by automatic-failure #10; test *depth*
past the auth gate still isn't, and this plan is a concrete data point for
that gap.
