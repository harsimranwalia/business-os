**AC1's own regression note.** This test did not exist when the ticket first
reached this gate — added this hop (see `## Result`). RLS
(`"Restaurant managers can view their restaurant conversations"`, verified
live against `bmnmnejwdxbcqinqkwko` during the build hop) authorises a user
for *every* restaurant they manage, not only the one currently selected in
the portal — for an owner of 2+ restaurants (an explicitly supported case;
see this ticket's own review notes), RLS alone would not stop Restaurant
B's questions from appearing on Restaurant A's page if the client-side
`.eq('restaurant_id', ...)` filter were ever dropped. That filter is the
actual enforcement of AC1's narrower "never another's" claim, and this
ticket's own review round 1 found the identical shape of cross-restaurant
mix-up on the FAQ-*write* side (`agents/principal-engineer/notebook/2026-09-06-review-log.md`).
Verified mutation-style, not just reasoned about: removed the `.eq(...)`
call from `questions/Index.tsx`, confirmed this test — and only this
test — went red, then restored it via `git checkout --` (worktree
confirmed clean before and after).

## Failure paths

| Scenario | Expected behaviour | Test |
|---|---|---|
| `ai_conversations` query fails (RLS denial, network, timeout — all surface identically through PostgREST's `error`) | Distinct error card with retry, never the empty state | `pages/questions/Index.test.tsx :: "renders a distinct error state with retry, never the empty state, when the query fails (AC2)"` |
| Malformed session row (`messages` not an array) | Contributes zero rows; sibling well-formed sessions still render | `pages/questions/Index.test.tsx :: "a malformed session contributes nothing, but a well-formed sibling session still renders"` |
| FAQ draft hand-off arrives scoped to a restaurant other than the one currently open | Discarded, not applied — this ticket's own review round 1 finding | `WebsiteFaqForm.test.tsx :: "does not surface a draft scoped to a different restaurant"` — mutation-verified by both this hop's review (`agents/principal-engineer/reviews/ENG-041.md`) and independently by this gate: swapped in the pre-fix `WebsiteFaqForm.tsx` (`git show 81b00b1:...`), confirmed this test fails for the leak and no other test in the file regresses, restored clean |
| FAQ draft re-arrives after a save (content refetch) | Not re-appended a second time | `WebsiteFaqForm.test.tsx :: "does not re-append the draft when content re-arrives after a save"` |
| Repeated / blank FAQ rows on submit | Blank rows dropped before save; nothing unusable persisted | `WebsiteFaqForm.test.tsx :: "filters blank rows on save"` |

## Not automated

- **`WebsiteFaqForm`'s generic add-row / remove-row button clicks** — this
  component mirrors `CateringPageForm`'s own add/edit/remove idiom
  (confirmed identical pattern, `agents/principal-engineer/notebook/2026-09-06-review-log.md`,
  round 1), and `CateringPageForm.test.tsx` itself carries exactly one test,
  for an unrelated field (`orderFormEnabled`/`fulfillmentCopy`) — no test
  for its own add/remove clicks exists anywhere in this suite today. This
  ticket's four `WebsiteFaqForm` tests already exceed the test investment
  of the pattern being mirrored; adding click-interaction coverage for
  mechanics this ticket didn't introduce is a pre-existing gap on
  `CateringPageForm`, not a new one on this ticket's own surface.
- **"Load older" (`fetchNextPage`) as a click interaction** — the two
  independent conditions that hide it (`lastPage.length < PAGE_SIZE`, a
  null `updated_at` cursor) are covered at the `getNextPageParam`/comparator
  level by this ticket's own normaliser reasoning (build notebook); no test
  drives an actual second page fetch. Traced by reading
  `getNextPageParam` directly rather than given a dedicated test — it's a
  three-line, no-branching-beyond-what's-covered function.
- **Retention / `cleanup_old_ai_conversations`** — confirmed during the
  build hop to not run at all in production (informational finding, not a
  behavior this ticket changes); nothing to test.
