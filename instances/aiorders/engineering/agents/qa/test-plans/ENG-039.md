# Test plan — Broadcasts tab, composer, drip editor, report UI (ENG-039)

## Scope note

`ENG-019`'s PRD carries 7 acceptance criteria; per
`agents/eng-manager/notebook/2026-09-04-eng019-work-breakdown.md`'s own
AC-mapping, this ticket owns AC1-AC5 (composer send-now/schedule, drip
step editor, audience picker, ROI report display, send-history view) —
AC6 (unsubscribe) and AC7 (server-side tenant rejection) are fully
backend-enforced (`ENG-038`, shipped) with nothing for this ticket to add.

The build hop shipped zero tests, reasoning that no per-component
convention exists on this repo beyond one bug-fix regression test.
**That reasoning doesn't hold up against this repo's own history:**
`ENG-032`'s test plan shows two of its three new tests
(`CateringKanban.test.tsx`, `CateringDetailModal.test.tsx`) were
acceptance-criterion tests for new UI, not regressions — a convention for
exactly this shape of work already exists here, and `restaurant-portal`
has real, working test infrastructure (unlike `ENG-034`'s
`config-site-builder`, which genuinely has none). Written this hop rather
than carried forward as a gap.

## Failure paths

This ticket duplicates no server-side validation (ticket's own Notes) —
the rows below are the client-observable behaviors that exist, not a
re-test of `ENG-038`'s own already-tested rejections.

| Scenario | Expected behaviour | Test |
|---|---|---|
| Editing a campaign whose status is `active` or later | Form fully disabled, no save action offered, explanatory notice shown | `BroadcastComposer.test.tsx :: "locks the form to read-only..."` — mutation-verified (`isLocked` hardcoded `false` → failed for the right reason) |
| Editing a campaign still `draft`/`scheduled` | Form fully editable | `BroadcastComposer.test.tsx :: "leaves the form editable while the campaign is still in a pre-send state"` |
| Server rejects create/update/pause/resume/cancel (cap, interval, edit-after-active, network) | Surfaced via the existing toast path, not swallowed | Traced (`BroadcastComposer.tsx:230-236`, `Broadcasts.tsx:97-103`'s shared `showError`) — not automated; every catch block routes to the same, already-established toast helper used throughout this file's sibling pages, nothing new to this ticket's own logic to mutate-test |
| Report has no coupon attached (`redemptions: null`) vs. a coupon with zero redemptions so far (`redemptions: 0`) | Block absent vs. present-showing-zero — never confused | `BroadcastReport.test.tsx` — mutation-verified (`!== null` changed to `!== undefined` → failed for the right reason) |

## Regression risk

**None to the existing reactive `Automations` tabs.** `Automations.tsx`'s
diff is a 7-line addition (one `TabsTrigger`, one `TabsContent`); the
existing "Automation Flows"/"History" tab content is byte-for-byte
unchanged (confirmed via `git diff origin/main...HEAD -- src/pages/autopilot/Automations.tsx`,
principal-engineer's own review, same hop). `types/autopilot.ts`,
`pages/autopilot/Templates.tsx` untouched.

**No regression risk to `brandPortalApi.ts`'s existing methods** — the
diff only adds 8 new methods and one optional response field
(`pagination?`); every pre-existing method and the `BrandPortalApiResponse`
interface's existing required fields are unchanged.

**`EmailEditor`/`useOffers` reuse carries no regression risk of its own**
— both are pre-existing, unmodified by this diff; `useOffers()`'s own
suite (none exists) is unaffected either way.

## Not automated

- **Toast-surfaced server error paths** (cap/interval/edit-after-active
  rejections, network failure on any mutation) — traced directly against
  the code (see Failure paths), not exercised via a test. Every one of
  these routes through the same pre-existing toast helper this repo
  already uses on every other mutation across the autopilot pages; there
  is no new error-handling logic on this ticket's own surface to verify
  independently of that shared, unowned-by-this-ticket path.
- **The `scheduleLater` toggle's own click interaction** (as opposed to
  its restored state, which is covered) — this repo has no
  `@testing-library/user-event` dependency, and `fireEvent.click` does not
  reliably open/toggle a Radix `Switch`/`Select` in jsdom. Both code paths
  the toggle selects between are covered from other angles instead: the
  ISO-timestamp construction (create-path test, `scheduleLater` off) and
  the restore-from-server-data direction (schedule-prefill test,
  `scheduleLater` implicitly on via a future `scheduled_send_at`).
  Reasoning and citation: `agents/principal-engineer/reviews/ENG-039.md`,
  "Coverage note."
- **`Broadcasts.tsx`'s own row-action visibility rules** (pause/resume/
  cancel shown or hidden by status) — traced by direct code reading
  (`Broadcasts.tsx:208-226`) rather than given a dedicated test: this is
  orchestration/wiring around already-covered pieces (the composer, the
  report) and duplicates no acceptance criterion of its own; the
  conditions are simple status-equality checks with no computed logic to
  mutate.
