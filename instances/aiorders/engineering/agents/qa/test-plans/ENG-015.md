## Not automated

- **AC3/AC4/AC5's actual enforcement mechanism — the new RLS `INSERT`
  policy plus `AddRestaurantModal.tsx`'s conditional.** Two compounding
  gaps, both pre-existing and outside this ticket's scope to fix: no live
  Postgres/Supabase connection reachable this pass (named on every prior
  hop of this ticket — build, round-1-fix, migration doc), and
  `aiorders-admin-hub` has zero test infrastructure at all — no
  `vitest`/`jest`/`@testing-library`, no test script, no `*.test.*` file
  anywhere in the repo (confirmed fresh this pass; standing open proposal,
  `proposals.md` 2026-08-31, eng-manager — not re-filed).

  **De-risked by static trace instead of execution, done fresh this pass,
  not carried from any earlier hop's account:** read every migration that
  ever touched `public.restaurants`' policies (`20250729143357`,
  `20250814065341`, `20250814065439`, `20250814065606`, plus this ticket's
  own new one) in full. Confirmed: (a) no `RESTRICTIVE` policy exists
  anywhere in this table's history — every policy, including this ticket's
  new one, is the default `PERMISSIVE`, so policies OR together and cannot
  silently block each other; (b) the two pre-existing `INSERT`-capable
  policies ("Admins can manage all restaurants", "Restaurant owners can
  manage their own restaurant") grant a partner nothing, so they can't
  interfere with or duplicate this new grant; (c) the three SELECT-lockdown
  migrations use `USING (false)`, which governs SELECT only and has no
  bearing on INSERT; (d) the new policy's `WITH CHECK` is a plain
  three-term AND (`approved = false AND EXISTS(role check) AND
  EXISTS(brand ownership))` — no OR, so there's no obvious path to
  accidental over-permissiveness; (e) `restaurants.brand_id` inside the
  ownership `EXISTS` subquery correctly resolves to the row being
  inserted, matching how this codebase's other RLS policies already
  reference the current row from a subquery; (f) column names/types
  (`brands.partner_id`, `restaurants.brand_id`) match what
  `getPartnerBrandIds` already queries successfully elsewhere in this same
  diff. This is code-reading confidence, not execution evidence — it rules
  out the specific failure modes a policy-interaction bug would produce,
  it does not prove the policy runs.

  **Risk asymmetry, stated plainly:** the likelier failure mode if
  something is still wrong is the policy being *too strict* (rejects a
  legitimate partner insert) — a functional bug, surfaces on first real
  use, not a security regression. A too-*permissive* failure (the
  dangerous direction) would require the AND-only `WITH CHECK` to
  evaluate true when a term is false, which the static trace above finds
  no path to.

  **Recommendation, not a gate condition:** a manual smoke test against
  staging (partner account, add-restaurant flow, confirm the row lands
  `approved: false` and is scoped to the right brand; second partner
  account, confirm a cross-brand attempt is rejected) before or
  immediately after this ships. Whoever picks up the open
  `aiorders-admin-hub` test-harness proposal closes this gap for good on
  the next ticket, not just this one.

- **A live end-to-end call against a real Supabase project generally** —
  out of scope per this repo's own boundary (`engineering-standards.md`:
  no test touches production; `definition-of-done.md`: synthetic data
  only) even where infrastructure exists elsewhere on this board.
