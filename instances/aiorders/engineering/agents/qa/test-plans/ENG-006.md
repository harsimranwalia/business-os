## The one gap that matters most: Auth configuration, not code

**Four of this ticket's seven acceptance criteria (1, 2, 5, 6) are gated on
Supabase's phone-auth provider and an SMS vendor being configured**, and
neither is done. This was already on the record before this review — the
design doc's Risks section and this ticket's own G2 log entry both name the
SMS vendor as unresolved — restated here because a test plan that stayed
silent on it would let "code is done" quietly read as "feature works,"
which is not true yet. Until that configuration exists:

- No diner can actually request or receive an OTP through this system —
  `platform-customer-auth` is unreachable in practice, because reaching it
  requires a client-side `verifyOtp()` to have already succeeded.
- AC1/AC2/AC5/AC6 cannot be exercised end to end by any test this pass could
  write, automated or manual — there is no live phone provider to call.
- This is a configuration/vendor dependency, not a defect in the 678 lines
  this ticket adds. The code that runs *after* a successful OTP verify
  (upsert, linking, validation) is tested to the extent this repo's
  infrastructure allows (see per-AC table above).

**Not filing this as a new finding** — it's already visible in
`agents/architect/designs/ENG-006-unified-customer-identity.md` (Risks) and
carried into this ticket's own log. Restating it here so the quality gate's
own record doesn't imply a stronger claim than the code supports, and so it
surfaces again at the release-readiness step where it actually needs a
decision (can this be released to real diners before that configuration
lands, or does the PR wait).

## Why the DB-dependent branches stay unautomated, stated rather than waved past

This repo has 46 existing edge functions and, per this review's own check
(`agents/principal-engineer/reviews/ENG-006.md`), zero precedent for
mocking or standing up a Supabase client inside a unit test. Building that
infrastructure is bigger than this ticket and would be exactly the kind of
"unrelated refactor bundled into a feature change" `engineering-standards.md`
flags as an automatic failure if done here. Named as a real, repo-wide gap
rather than solved or hidden.

## Regression risk

Purely additive: two new tables (nothing existing altered), one new edge
function (nothing existing modified except the README catalog entry).
`customers` is read-only from this code's perspective, confirmed above.
Nothing currently in production calls `platform-customer-auth` — it has no
existing caller anywhere in any of the four frontends (frontend work is an
explicit PRD non-goal for this ticket) — so this diff cannot regress any
live behavior today.
