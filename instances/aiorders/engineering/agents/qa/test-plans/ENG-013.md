## The gaps that matter, named rather than papered over

**No live database this pass — same repo-wide gap `ENG-007`/`ENG-008`/`ENG-011`'s own test plans already named.** Both write tests use a hand-built fake Supabase client (`.from().update().eq().eq().select()` recording each `.eq()` call and resolving a synthetic row), not a real Postgres round trip. It proves `setStageOverride`/`resetStageOverride` build the right shape of call with the right scoping and return the right shape of response; it does not prove the new `foodswipe_stage_override` column and its six-value `CHECK` constraint behave as the handler's own mirrored `VALID_STAGES` check assumes against the live schema. `aiorders-api` still has no live/throwaway Postgres access from this host (same constraint every prior ticket on this board carries) — the building pass's own migration doc
(`agents/database/migrations/ENG-013-foodswipe-funnel-stage-control.md`) is
where that verification actually happened, via the read-only Supabase MCP
connection against the real schema; named here so this gate's record
doesn't imply stronger evidence than exists, same convention every prior
plan on this board has set.

**Only 1 of the 6 stage values (`menu_uploaded`) is exercised through a successful write; the other five are proven only at the validation boundary.** The construction logic is uniform — `VALID_STAGES.includes(stage)` then one `.update({ foodswipe_stage_override: stage })` — so this is a narrow-but-uniform gap, not six independent unknowns, same shape `ENG-008`'s own plan accepted for its six editable fields. Not blocking: duplicating the success test five more times would test the same three lines of glue code five more times, not new behavior.

**"Set, then reload shows the override" (AC2) is never exercised as one test — only as two separately-tested facts.** The write test proves the column gets set; the `GET` path's `?? classifyStage(...)` precedence is read, not driven by a test that first sets an override and then calls the listing fetch and asserts the returned stage. Both halves are individually well-covered and the logic connecting them is a single nullish-coalescing operator, not a place bugs hide — but named honestly rather than implied as integration-tested when it isn't.

**The new `FOODSWIPE_STAGE_SET`/`FOODSWIPE_STAGE_RESET` frontend calls (`handleSaveStage`, `handleResetStage`) have zero automated coverage** — no test harness is registered for `aiorders-admin-hub` at all (`config/projects.md`), so this is consistent with every other frontend change on this board, not a gap specific to this ticket. `handleResetStage` does not set a loading/disabled flag while its request is in flight (unlike `handleSaveStage`'s `isSaving`), so a rapid double-click could fire two reset requests — low risk since the operation is idempotent (both calls set the same column to the same `null`), named for completeness rather than as a defect.

## Regression risk

Additive only: one new nullable column (no default, no backfill — every
existing row's override starts `null`, meaning "keep computing
automatically," so no existing listing's displayed stage changes until a
staff member acts on it); the unchanged `GET` path gains one extra selected
column and a fallback expression, not a rewrite; two new routes reached
only through path substrings (`/foodswipe/stage/set`,
`/foodswipe/stage/reset`) that did not exist before this ticket, so nothing
that previously matched a different branch can now match one of these
instead. On the frontend, the only structural change to existing markup is
the kanban card gaining a dropdown trigger and an optional badge — the
card's existing read-only fields (name, email, phone, dates) are untouched
by this diff.

## Not automated

- "Set, then a separate GET reflects it" as one test (gap above).
- Both new frontend handlers (`handleSaveStage`, `handleResetStage`) — no test harness registered for this project.
- The unexpected-exception (500) branch in either new handler — code-inspection only, matching this repo's existing convention for every other handler.
