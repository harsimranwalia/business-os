## Round-1 gap this ticket exists to close

Automatic-failure #10 (code review round 1, 2026-08-29): zero test
coverage on the new authz-gated write path, specifically no proof that
`.eq('source', 'foodswipe')` actually stops a write from landing on a
non-Foodswipe profile. Closed by `setStageOverride scopes its write to id
AND source='foodswipe'...` / the `resetStageOverride` equivalent: both
use a fake Supabase client (`adminAuthRecordingEq`) that records every
`.eq()` call rather than just returning canned data, so the assertion on
`calls` fails if that scoping line is ever removed — a mutation on the
threat, not on the assertion. Full reasoning: code review, Test quality
section.

## Failure paths

| Scenario | Expected behaviour | Test |
|---|---|---|
| Invalid input at the boundary — missing/non-string `profileId` | 400, `profileId is required`, nothing written | `setStageOverride rejects a missing profileId` / `...a non-string profileId`; same two for `resetStageOverride` |
| Invalid input at the boundary — missing/out-of-range `stage` | 400, `stage must be one of: ...`, nothing written | `setStageOverride rejects a missing stage` / `...rejects a stage outside the six-value enum` |
| Unauthorised caller (all three routes) | 403, denied before any database call | The three tests under AC5 above |
| Wrong tenant — a valid id that isn't a Foodswipe profile | 404, not a silent write, not a 200 | `setStageOverride returns 404 rather than writing when the id/source scoping matches no row` / the `resetStageOverride` equivalent |
| Duplicate/replayed reset | Idempotent — resetting an already-`null` override still matches the row on `id`+`source` and returns 200, never a spurious 404 | Not directly tested; traced by hand — the update's `WHERE` clause matches on `id`/`source`, never on the override's current value, so a repeat call takes the same path as the first |
| Method not allowed | 405, checked before role, so a rejected-role caller can't distinguish "wrong method" from "wrong role" via timing/response shape | `handleFoodswipe rejects DELETE with 405 even for a role that would also fail the access gate (method checked first)` |
| Downstream Supabase error | 500 with a message, logged server-side, never a silent swallow | Not tested (no test simulates the fake throwing mid-write); traced by hand — both new actions' `catch` blocks mirror the file's own pre-existing GET-path catch, same repo convention, not a new gap this ticket introduces |
| Concurrent write to the same profile from two staff | Last write wins; no merge is attempted or expected for a single discrete enum value | Not tested — this is the intended semantic, not a defect, and there is no correct "merge" of two different manually-chosen stages. Named here rather than silently assumed |

## Regression risk

Additive on both repos. `aiorders-api`: the GET/kanban path gains one
selected column and one `??` fallback in its stage-assignment loop —
every existing row's override is `null` (no backfill), so
`classifyStage()`'s output is byte-for-byte unchanged for every listing
until a staff member acts; confirmed by reading the fallback expression,
not assumed. No existing route, table, or authz check is modified —
`hasFoodswipeAccess` is an extraction of already-live logic, not a
behavior change (see code review's Design conformance for the
`Boolean(...)` wrap's own inertness). `aiorders-admin-hub`: purely
additive UI (a dropdown, a badge, a dialog) on an existing page; no
existing prop, state, or fetch call is removed or reshaped.
