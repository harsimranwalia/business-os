## Regression risk

**The `CateringPageForm` save-path fix** (round 1's automatic-failure finding,
closed round 2): an owner editing unrelated catering copy no longer silently
wipes `orderFormEnabled`/`fulfillmentCopy` on save. Covered by
`CateringPageForm.test.tsx`, verified red against the pre-fix code by
principal-engineer this same round (`agents/principal-engineer/reviews/ENG-032.md`)
— not re-verified a third time here, same evidence, same round.

**No regression risk to pre-existing catering-page fields** (title, subtitle,
venues, FAQs, etc.): the new Online Order Form card is additive UI at the end
of the form; `set()`/`setFulfillmentCopy()` are new, isolated setters that
don't touch any existing field, and the `...content`-spread fix is what
makes any field — old or new — survive a save, so the fix itself is the
regression guard for the whole form, not just the two new keys.

**No regression risk to the five pre-existing stages' board behaviour**: the
two new entries are additive appends to every `columns`/`statusConfig`/
`statusOptions` array; nothing about an existing stage's key, position, or
config value changes. Directly exercised by the AC-8 test above (a
`'Finalized'`-status request renders correctly alongside the two new-stage
requests in the same board).

## Not automated

- **Brand-level catering content overriding the restaurant-level switch**
  (`get-brand-website` resolves `catering: brand.metadata?.catering ||
  restaurantData.catering`) — a pre-existing precedence, newly consequential
  now that the object carries a functional switch. Named in ADR-009's
  Consequences and the design's own Risks as "worth a line in QA's test plan
  and worth an observation; not fixed here." This is that line. Not
  automated: no brand-level-content fixture exists in this repo's test
  suite, and reaching this ticket's own diff (a plain owner-side editor, no
  precedence logic of its own) is orthogonal to it — the precedence lives in
  `get-brand-website` (`aiorders-api`), untouched by this diff. Observation
  filed (`observations.md`) per the design's own instruction.
- **The switch/copy-editor's own click-and-type interactivity** (toggling
  `orderFormEnabled`, typing into a `fulfillmentCopy` field) — not a PRD
  acceptance criterion at this ticket's level (AC-1/AC-2, which the switch
  and copy exist to serve, are `ENG-034`'s public-form criteria); the data
  round-trips correctly per the regression test above, and the controls
  themselves are typed, pre-existing shadcn primitives (`Switch`, `Input`,
  `Textarea`) with no custom interaction logic to test independently.
