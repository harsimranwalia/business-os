## Review of the lines (this round's own diff)

- `hasFoodswipeAccess` extraction: byte-identical logic to what round 1 read
  inline, now wrapped in `Boolean(...)` — confirmed this is *not* a
  behavior change by diffing against the round-1 commit (`ac4efba`)
  directly: the inline version already read `allowedRoles.includes(...) ||
  (...)`, which for every call site observed (single boolean-context use)
  was already effectively boolean; wrapping it is type hygiene, not a
  logic fix (unlike `ENG-008`'s sibling bug, which this ticket does not
  share — confirmed by reading, not assumed from the similarity).
- `uncalledAuth()`'s throwing `Proxy` — real, not a placebo: checked that
  every one of the 6 rejection branches in `setStageOverride`/
  `resetStageOverride` returns before `auth.adminSupabase.from(...)` is
  reached — true, confirmed by reading both functions against the test's
  own claims.
- `adminAuthRecordingEq()`'s fake chain records both `.eq()` calls
  positionally (`column`, `value`) rather than just returning canned data —
  so a mutation that deletes the `source` scoping fails this test for the
  actual threat, not a coincidence. **Verified by mutation, independently
  this round, not trusted from the build pass's own log**: removed
  `.eq('source', 'foodswipe')` from `setStageOverride` by hand (isolated
  edit in the shared worktree, reverted immediately after), re-ran —
  exactly the two tests round 1 most needed (`setStageOverride scopes its
  write...` and `setStageOverride returns 404...`) went red (17/19),
  `resetStageOverride`'s own pair correctly stayed green since only
  `setStageOverride` was mutated. Reverted; `git diff --stat` against
  `HEAD` confirmed empty before moving on; re-ran clean, 19/19.
- `setStageOverride`/`resetStageOverride` both validate `profileId` and (for
  `set`) `stage` before touching `adminSupabase` — external input validated
  at the boundary per `engineering-standards.md`, consistent with every
  sibling handler.
- The two new POST routes are matched by `fullPath.includes(...)` guarded
  with `&& req.method === 'POST'` — a GET or a bodyless POST to
  `/foodswipe/stage/set` falls through to the general listing fetch rather
  than a dedicated 404/405. Checked against `origin/main`: this fallthrough
  already existed before this ticket (the method gate has always allowed
  GET *and* POST through to the same listing logic) — not new behavior,
  not introduced by this diff, so not a finding.
