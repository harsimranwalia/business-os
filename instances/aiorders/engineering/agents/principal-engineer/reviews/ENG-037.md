## Review of what isn't there

Two specific, non-blocking findings — the step this house style treats as the
one most reviews skip:

**F1 — `broadcast_campaign_recipients.step_id` (migration line 99) has an
`on delete cascade` foreign key with no dedicated index.** Postgres does not
automatically index a referencing column on the child side of a foreign key
— only the referenced column gets one, via the parent's primary key. A
`delete` against `broadcast_campaign_steps` (cascading through `step_id`)
would need a sequential scan of `broadcast_campaign_recipients` to find
matching rows — the one table this ticket's own migration doc names as the
schema's actual load case (fan-out, one row per customer per step, sized to
a restaurant's full customer list). **Judged non-blocking**: no interface in
the design's own Interfaces section deletes a step directly (only
`cancel_broadcast`, which updates `status`, never deletes rows), and the one
plausible indirect path — `update_broadcast` replacing a draft campaign's
steps — can only run before the campaign reaches `active`, at which point no
recipient rows exist yet to scan (the dispatcher only inserts them on
enrollment). So today's reachability is effectively nil, not the same shape
as a currently-exploitable gap. **Specific fix**, if picked up: `create
index if not exists broadcast_campaign_recipients_step_id_idx on
public.broadcast_campaign_recipients using btree (step_id);` — cheap, and
consistent with this same migration's own established pattern of indexing
every other FK it expects to be queried or cascaded through.

**F2 — `broadcast_campaigns.scheduled_send_at` (migration line 45) is
nullable with no constraint tying it to `status`.** The design's own
unified-dispatch model (`ADR-018`) and the dispatcher's stated enrollment
query (`WHERE status = 'scheduled' AND scheduled_send_at <= now()`) both
presume every non-`draft` campaign has a real `scheduled_send_at`. If
`create_broadcast` (`ENG-038`) ever inserted a row with `status: 'scheduled'`
and a null `scheduled_send_at` — a bug in code that doesn't exist yet, not
in this diff — that row would sit at `scheduled` forever: `NULL <= now()` is
never true, so the dispatcher's own claim query would silently skip it, with
no error, no log line, and no visibility to the restaurant owner watching an
apparently-scheduled campaign never send. **Judged non-blocking**: not
reachable from any code that exists today, and the design doesn't ask for
this constraint explicitly. Flagged rather than silently passed over because
this migration already sets its own bar higher elsewhere in the same file —
`broadcast_campaigns_audience_param_check` and
`broadcast_campaign_steps_order_unique` are both DB-level integrity rules
added beyond the design's literal text, for exactly this class of "don't
trust the application alone" reasoning. This one gap is the same shape and
was, on the evidence here, simply not extended this far. **Specific fix**,
if picked up: `constraint broadcast_campaigns_scheduled_requires_time check
(status = 'draft' or scheduled_send_at is not null)` — `draft` is the one
status where an unset send time is legitimate (a campaign still being
composed); every other status in the enum is only reachable after a real
send time was set.

Neither finding blocks this round. Both are additive (a new index, a new
constraint) and can land in `ENG-038` or a follow-up without touching
anything this ticket ships.
