## Read against the finding it fixes — verified by reading the code, not by the tests passing

- **Placement matches the finding's own requirement exactly.** The finding
  said "before any branching on `webhookData.event`," specifically because
  gating only the terminal branch would leave `order_new` open — the actual
  fabrication path. Read `handleCloudWaitress` directly: the
  `verifyCloudWaitressSecret` check sits immediately after `request.json()`
  and strictly before the structural-validation check, the terminal-event
  branch, and the `order_new` branch. All three paths are covered, not just
  the three this ticket added.
- **Fails closed, and the failure direction is uniform with the rest of this
  standard's own rule.** `if (!expected || !provided) return false;` —
  an unset `CLOUDWAITRESS_WEBHOOK_SECRET` never matches even an
  equally-missing `webhookData.secret`, so a misconfigured deployment
  rejects everything rather than accepting everything. Confirmed by running
  the dedicated test for exactly this case, not just reading the line.
- **Sourced from an env var, not a second hardcoded literal** — the finding
  named `cloudwaitress-middleware/handlers/restaurant.ts`'s existing
  hardcoded `AIORDERS_WEBHOOK.secret` as the value to compare against, and
  explicitly scoped migrating *that* literal as separate, already-tracked
  cleanup. This diff doesn't touch that file, matching the finding's own
  scoping.
- **Matches this project's own established shape for a service-side secret
  check** — `loyalty-auto-complete/index.ts`'s `authorizeServiceRole` (this
  same ticket's own earlier work) rejects with the same `401`
  `{success:false, error:'Unauthorized'}` shape via the same
  `createErrorResponse` helper. Two service-boundary auth checks in one
  ticket, one idiom — not a second way to do the same thing.
- **Extracted as a pure, exported, directly-testable function rather than
  left inline in the handler** — `verifyCloudWaitressSecret` takes the
  webhook data in and returns a boolean, no network or datastore client
  inside it, matching `engineering-standards.md`'s "decision logic does not
  live trapped inside a bare request handler" rule (promoted 2026-09-04)
  exactly, unprompted.
- **Logs the denial without logging the secret.** `console.warn` includes
  only the event name (`event: ${webhookData?.event ?? 'unknown'}`), never
  `webhookData.secret` or the expected value — satisfies the observability
  standard's "no PII, no secrets, no tokens in that log line" without being
  asked.

The 8 new tests are the right shape for a security regression guard, not
just "it returns 401":

- **Two unit tests on `verifyCloudWaitressSecret` directly** (match,
  mismatch) and **two more on its edge cases** (missing `webhookData.secret`

  proves "fail closed" rather than "matches when both sides happen to be
  set."
- **The exploit-chain test replays the finding's own traced attack, not a
  generic 401 check**: an `order_new` with no configured secret asserts
  `res.status === 401` **and** `tableCalls.length === 0` **and**
  `rpcCalls.length === 0` — proving the request never reaches Supabase at
  all, which is the property the finding actually needed (an attacker who
  can't authenticate can't get partway through order creation either).
- **A second rejection test covers a terminal event with a wrong secret**,
  not only `order_new` — the one place a narrower fix (gating only the three
  new terminal events) would have looked complete while leaving the
  original path open. Both this test and the `order_new` one assert the
  same zero-Supabase-calls property.
- **Two positive tests prove the gate doesn't block legitimate traffic** — a
  correctly-signed ignored event still returns `200 {success:true}` and
  touches no table; a correctly-signed terminal event still reaches
  `credit_order_if_eligible` with the exact same RPC arguments round 1's own
  tests already asserted. Without these, a passing suite would be equally
  consistent with an over-broad fix that also rejected valid traffic.

No test asserts an implementation detail; every assertion is on the response
shape, the response status, or the fake's own call log (`tableCalls`/
`rpcCalls`), the same fakes round 1 already established as real and
