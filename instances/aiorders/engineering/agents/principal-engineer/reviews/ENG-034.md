## Findings — all non-blocking

**F1 — `CateringForm.tsx:131` (`handleSubmit`).** `(e.nativeEvent as
SubmitEvent).submitter` is how the two same-shaped submit buttons are told
apart, and the choice over tracking the clicked button via `onClick` state
is well-reasoned (state set in a click handler isn't guaranteed to have
flushed before `handleSubmit` runs — true). But there's no fallback: if
`submitter` doesn't populate (an unsupported/non-compliant browser —
`SubmitEvent.submitter` shipped in Safari 15.4, March 2022, so this is a
shrinking population by now, not a live-currently-common one), `actionType`
silently becomes `undefined` even on the "Submit Quote Request" path. The
request still succeeds — no crash, no error shown — but `action_type` and
the customer's `selections` are both dropped from the payload
(`selections: actionType ? … : undefined`), so the request lands in
today's default column with none of the itemized detail this feature
exists to capture, and the customer sees the same "submitted successfully"
message either way. This is the shape `engineering-standards.md`'s
"failure direction is uniform" rule and "every failure path… has a
message" standard both speak to directly — every other invalid/malformed
input on this ticket fails closed with a message; this one fails open and
silent. **Not blocking**: meaningfully lower reachability than a
same-shaped bug this board has failed a round over before (ENG-033 round
1's non-string `note` — reachable by any HTTP client, no special
conditions), and the fallback degrades to "no worse than the gate-closed
experience" rather than crashing or corrupting data. **Specific fix**, if
picked up: when `orderFormEnabled && !submitter`, treat it as a blocked
submission with a message, the same way the zero-selections case is
handled, rather than silently proceeding.

**F2 — `CateringForm.tsx:237`.** `(orderFormEnabled &&
fulfillmentCopy?.[option.value]?.label) || option.label` uses `||`, so an
owner who intentionally clears a label to an empty string falls back to
the hardcoded default rather than rendering blank. `label` is typed
`string | undefined`, so `??` is the more precise operator here. Very
low real-world likelihood (depends on how `restaurant-portal`'s own editor,
`ENG-032`, represents a cleared field — not this ticket's file). Style
preference, not a correctness bug in this diff.

**F3 — `CateringForm.tsx:475-520`.** The `Loader2`/"Submitting…" JSX block
is duplicated verbatim between the gate-open "Submit Quote Request" button
and the gate-closed single button. A small shared fragment (or a
`SubmitButtonLabel` helper) would remove the duplication. Preference, let
go — the file doesn't get meaningfully harder to read as-is.

**F4 — File size.** `CateringForm.tsx` is 540 lines post-diff, further past
`engineering-standards.md`'s ~400-line smell threshold — it was already at
~420 pre-diff (this ticket's own net addition is ~120 lines), so this
ticket didn't create the condition, but it did grow it. No single piece of
this diff reads as a second concern wearing the same file (it's still
cohesively "the public catering form, plus what displaying it now takes"),
so not asking for a split this round — worth watching if the next ticket
here adds materially more.
