## Line-level correctness

Traced the fix end to end against round 1's own reproduction:

1. `questions/Index.tsx`'s `handleAddToFaqs` now carries
   `restaurantId: currentRestaurant.id` alongside the question. The
   `if (!currentRestaurant) return` guard immediately above it is dead code
   by construction (the only caller is a button that can't render before
   the component's own early return) — correctly justified in a comment
   rather than removed, since the closure captures `currentRestaurant` from
   the outer scope and TS can't narrow across that. Fine as defensive code,
   not a finding.
2. `WebsiteFaqForm`'s effect now computes
   `faqDraft?.restaurantId === currentRestaurantId ? faqDraft : null` before
   the existing `.question` / `draftConsumedRef` check. Re-derived the
   original bug's repro against this new code by hand (A → add-to-FAQs →
   land on `/website` with `faqDraft` scoped to A → switch to B →
   `WebsiteFaqForm` remounts against B's content and a fresh
   `draftConsumedRef` → `draftForThisRestaurant` evaluates to `null`
   because `'A' !== 'B'` → `else` branch → `setForm(base)`, B's own content
   only). Leak closed.
3. Checked the adjacent case the fix doesn't need to (and doesn't) treat
   specially: switching **back** to A without saving. `form` is fully
   recomputed from `content` (the last **persisted** value) on every
   remount regardless of path taken to get there, so A → B → A reproduces
   the same single, non-duplicated draft-appended state as a direct visit
   to A — not a growing/duplicating list. Not a finding.
