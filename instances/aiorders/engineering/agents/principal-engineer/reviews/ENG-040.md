**Non-blocking finding — inconsistent-looking operator, factually-shaky
rationale.** `getWebsiteContent`'s three fields:

```ts
catering: data?.catering || null,
careers: data?.careers || null,
faqs: data?.faqs ?? null
```

The ticket and design both justify `??` here as necessary so `content.faqs =
[]` survives instead of being nulled by `||`. That's not actually true in
JS — `[] || null` evaluates to `[]`, because an empty array is truthy; `||`
would have preserved it exactly as well as `??` does. Neither operator can
distinguish `[]`/`{}` from a "real" value for any of these three fields,
since none of them ever legitimately holds a falsy-but-meaningful value —
only `null`/`undefined` need distinguishing, and both operators treat those
identically. So the code is correct and safe either way; what's wrong is the
stated reason, not the line. Flagging per `engineering-standards.md`'s own
promoted rule ("a comment or doc that asserts a property the code does not
have is a defect... applies to docs prose, not just code comments") — the
design doc and ticket Notes both carry this claim. **Not blocking**: no
behavior is wrong, and I'd rather this land noted than hold an XS ticket on a
docs-accuracy point. Worth a one-line inline comment on the `faqs` line if
anyone touches this function again, so a future reader isn't left guessing
why the third field looks different from its two siblings.
