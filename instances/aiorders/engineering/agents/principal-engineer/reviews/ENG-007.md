## Design conformance

Checked the committed code against
`agents/architect/designs/ENG-007-per-restaurant-loyalty-configuration.md`
line by line:

- **Table** — column set matches the design's Data section exactly
  (`id`/`restaurant_id`/`online_earn_pct`/`dine_in_earn_pct`/
  `redemption_value_per_point`/`effective_from`/`created_at`/`created_by`/
  `updated_at`), same types and check constraints.
- **Index** — `(restaurant_id, effective_from desc)`, matching the design's
  stated single access pattern exactly.
- **Trigger** — `enforce_loyalty_config_effective_order` matches the
  design's SQL verbatim (advisory-lock, strictly-increasing, future-only).
- **One deliberate deviation from the design doc's text, not from its
  intent — named in the migration doc, not hidden here.** The design's Data
  section claims a shared `update_updated_at_column()` function is "the
  established way to maintain `updated_at` — reused here." Checked against
  the actual migration history (`grep -rn "EXECUTE FUNCTION"
  supabase/migrations/`): that function is defined but wired to zero tables
  anywhere in this repo, while `restaurant_activations` — the design's own
  cited closest structural precedent — writes a dedicated trigger function.
  This diff follows the real precedent (`update_restaurant_loyalty_configs_updated_at()`,
  dedicated, matching `restaurant_activations`' shape exactly) rather than
  the design doc's inaccurate claim about which function is "established."
  Full reasoning: `agents/database/migrations/ENG-007-per-restaurant-loyalty-configuration.md`.
  Not a scope or one-way-door question — a same-outcome, more-consistent
  implementation choice, and the kind of "where the design is silent or
  wrong, the standards apply and you say so" call `agents/backend/agent.md`
  asks the implementing engineer to make.
- **Interface** — `GET`/`POST admin-portal/loyalty-config`, admin/sub-admin
  only, matching the design's stated auth scope exactly (see automatic-failure
  #4 disposition above for why this is narrower than `admin-portal`'s shared
  four-role gate, and matches the design's explicit words rather than the
  gate's broader default). `POST` validates the three numeric fields before
  ever reaching the database, matching the design's stated reason (friendlier
  400 instead of a raw constraint-violation 500) — and the trigger's own
  400-mapped rejection is exactly the "let the trigger own the harder
  invariant" split the design called for.
- **RLS** — enabled, no policies, matching the design's explicit choice and
  ENG-006's precedent it cites.

No divergence from the design's *intent* found; one factual correction to
the design doc's stated *convention*, made and recorded rather than quietly
followed into a table this repo doesn't actually build that way.

- **DB-dependent branches are not exercised by an automated test** — a real
  `GET`/`POST` round trip against a live table, and the trigger-rejection-to-400
  path's actual wiring (as opposed to the pure mapping function that produces
  it, which *is* tested). Same repo-wide gap ENG-006's review named: no
  precedent anywhere in this repo's 47 edge functions for mocking or standing
  up a Supabase client in a unit test. This ticket narrows the gap
  materially more than ENG-006 could — every piece of *decision logic*
  (auth gate, validation, "current as of T" derivation, error-code mapping)
  was pulled out pure and DB-free specifically so it has real test coverage,
  leaving only the DB plumbing itself (the two `.from(...)` calls) untested.
- **The migration was not run against a live or throwaway Postgres this
  pass** — Docker Desktop is installed on this host but its daemon did not
  come up within budget; substituted with a hand-traced verification of the
  trigger's transaction semantics plus direct comparison against three
  already-applied precedents in this exact repo. Full detail and exactly
  what was and wasn't checked: `agents/database/migrations/ENG-007-per-restaurant-loyalty-configuration.md`.
  Materially weaker than ENG-006's own container-verified migration —
  named as such, not written up to sound equivalent.
- **Unbounded history query** (automatic-failure #5 above) — accepted given
  the domain's real cardinality (rate changes are rare, deliberate admin
  actions), worth a `limit()` if a later ticket reuses this pattern against
  a less-bounded table.
