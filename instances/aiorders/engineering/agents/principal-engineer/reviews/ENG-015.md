## Non-blocking notes (not automatic failures, not asked for a re-round)

1. **Empty-update-payload edge case, unverified against real PostgREST.** A
   partner `PUT` containing *only* `{approved: true}` (or only `brand_id`)
   strips to `updates = {}`. The fake client no-ops on this in the test
   suite; real `supabase-js`/PostgREST behavior for an empty PATCH body
   (200 no-op vs. an error) was not exercised — no live Postgres reachable
   this pass, same standing gap named on every other hop of this ticket.
   Low severity: either outcome preserves the security property (the
   restricted fields never land), the only realistic trigger is an
   exploit-shaped request, and a legitimate UI edit will always carry other
   fields alongside. Not blocking.
2. **`updateRestaurant`'s ownership check is read-then-write, not atomic**
   (fetch `existing.brand_id`, then update by `id` alone, no `WHERE
   brand_id = ...` re-check). Pre-existing shape since the original build
   hop, unchanged by round 1's fix — not a regression this round. Narrow
   theoretical race (an admin reassigning the same restaurant's brand mid
   partner-request); no code path in this codebase does that today. Noting
   for completeness, not blocking.
3. **No log line on the two new 403 denials** (`getRestaurantById`,
   `updateRestaurant`). Checked against this ticket's own cited precedent
   for the 403 wording, `_shared/restaurantAccess.ts` — that file's
   equivalent denial also logs nothing, so this is consistent with the
   convention this ticket explicitly modeled itself on, not a deviation
   from it. `offers.ts` (`ENG-022`, same day) does log every denial, but
   that's a different file's own return-style convention, not the one this
   design cited. Letting this go rather than making it a standard off one
   data point on each side.
