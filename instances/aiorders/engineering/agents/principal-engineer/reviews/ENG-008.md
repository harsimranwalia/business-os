## Design conformance

Checked against
`agents/architect/designs/ENG-008-influencer-profile-admin-management.md`
and the PRD's 8 acceptance criteria — re-confirmed this round, not assumed
still true from round 1:

- **AC1/AC2** (region preference visible, editable, persists) — `Region
  Preference` input round-trips through `city_preference`
  (join on open, split-and-filter on save); backend validates
  array-of-strings and writes it through the same generic `update()` call
  every other field uses.
- **AC3/AC4** (campaign-type: paid, barter, or both; editable) — the two
  independent `accepts_paid`/`accepts_barter` checkboxes are the fix for
  the single-boolean XOR the design's own "Alternatives considered" section
  named; the table's badge row now renders both simultaneously when both
  are true, satisfying "both" for the first time.
- **AC5/AC6** (rating set/changed) — `staff_rating` Select, 1–5 plus
  "Not rated" (→ `null`), backend `CHECK 1–5` plus an explicit
  `!== null` carve-out so clearing is possible.
- **AC7** (collaboration count set or incremented) — plain editable integer
  input; design's own Interface section defines this as a settable value
  (`integer >= 0`), not a dedicated increment control, so a number field
  satisfies it — incrementing is "type current value + 1."
- **AC8** (non-admin/non-staff rejected) — one shared gate
  (`hasInfluencerAdminAccess`), checked once before the GET/PATCH branch,
  so there is no per-method copy of the check that could drift.

No divergence from the design's intent in either repo.

## Test quality (shape, not coverage)

- **The allowlist test is mutation-sensitive, not just shape-sensitive.**
  It captures the exact object passed to `adminSupabase....update()` and
  asserts equality against `{ staff_rating: 4 }` — if a future edit added a
  new field to `EDITABLE_FIELDS` without a corresponding `if ('x' in body)`
  branch (or vice versa), this test's assertion is unaffected either way,
  which is correct: it tests actual write behavior, not the documentation
  constant. Worth naming plainly: `EDITABLE_FIELDS` itself is referenced
  only in the `badRequest` message, not iterated to build `update` — the
  real allowlisting is the six independent `if` blocks. Not a defect (the
  six blocks are exactly the six array entries today, each with its own
  type check, arguably safer than a generic loop), but a future edit to one
  without the other would drift silently. Not blocking; noted for whoever
  next touches this file.
- **No test asserts on private/internal structure.** Every assertion is on
  `Response.status`, response body fields, or the recorded `update()`
  argument — the last is testing an external, observable fact (what a real
  Supabase client would be told to write), not an implementation detail.
- **Naming and shape match this repo's convention**
  (`loyalty-config.test.ts`, `foodswipe.test.ts`).

## New finding this round (non-blocking)

- **`src/pages/Influencers.tsx`, `handleSaveInfluencer`
  (`min_visit_payment` inclusion): stale value can be written after
  toggling `accepts_paid` off.** The field is sent whenever
  `editForm.min_visit_payment.trim() !== ''`, independent of the current
  `accepts_paid` value. Sequence: open an influencer with `accepts_paid:
  true, min_visit_payment: 50`; uncheck "Paid" (now `accepts_barter`-only,
  `accepts_paid: false` in form state); the min-payment input disappears
  from the UI but `editForm.min_visit_payment` is never cleared; save.
  The PATCH body includes both `accepts_paid: false` and
  `min_visit_payment: 50` — the backend writes both, since its own
  validation has no cross-field awareness either. Result: a barter-only
  influencer with a persisted (if now-hidden, since the read path gates
  the "Min: $" display on `accepts_paid`) min-payment value that
  resurfaces without the user re-entering it if `accepts_paid` is
  re-checked later without touching the payment field. Not a crash, not a
  security issue, not named in any of the 8 acceptance criteria
  (`min_visit_payment` isn't itself an AC) — a P3 per
  `definition-of-done.md`'s severity table ("cosmetic, minor, or a
  nice-to-have", has a workaround: re-enter the value). Not filed as a bug
  or a proposal given this board's own practice of naming small,
  single-occurrence, non-blocking findings in the review rather than
  spawning a ledger entry for them (`agents/qa/bugs/` has never held one).
  Fix, for whoever next touches this file: clear `min_visit_payment` in
  the same `setEditForm` call that unchecks `accepts_paid`, or gate the
  send on `body.accepts_paid !== false`.
