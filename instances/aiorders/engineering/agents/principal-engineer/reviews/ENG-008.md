## Diff shape

fixed in the file the test needed to import from — no scope creep. The fix
itself (`Boolean(...)` wrapping the existing OR-chain) is the minimal
change, not a rewrite of the function. Test file structure mirrors

## Review of the lines (this round's own diff)

- `Boolean(allowedRoles.includes(...) || (additional_roles && ...))` —
  correct fix: preserves the exact short-circuiting, only coerces the final
  result to a real boolean. Confirmed by mutation (above) that reverting it
  reproduces the exact pre-fix behaviour the bug report described.
- `uncalledAuth()`'s throwing `Proxy` — a real assertion, not a placebo: if
  any of the 8 rejection branches accidentally reached `adminSupabase`
  before returning 400, the test would fail with the Proxy's own thrown
  error rather than silently passing. Checked the source to confirm every
  rejection branch in `updateInfluencer` does in fact `return badRequest(...)`
  before the `auth.adminSupabase.from(...)` call — true.
- `adminAuthReturning()`'s fake chain (`.from().update().eq().select()`)
  ignores its own `_table`/`_column`/`_value` arguments (prefixed
  underscore, deliberately unused) — so this test proves the handler
  reaches the right *shape* of call and returns the right *shape* of
  response, not that it targets the right table/column/row. Same
  limitation `loyalty-config.test.ts` already carries and named openly
  ("this repo still has no precedent or infrastructure for mocking a
  Supabase client") — not a new gap this ticket introduced, and not
  silently inherited either: restated in the QA test plan.
- One success test covers `staff_rating`/`collaboration_count`; the other
  four editable fields are proven only at the validation boundary. Detail
  and why this isn't blocking: QA test plan, "The gaps that matter."

## Review of what isn't there

- **No test for `staff_rating: null`** (the explicit clear-a-rating path).
  The guard (`body.staff_rating !== null && (...)`) reads correctly by
  inspection — null short-circuits past the range check — but nothing
  exercises it. Named in the QA test plan, not blocking: it's a coverage
  thinness past the auth/validation gate, not a missing failure-case test
  on an auth path (automatic-failure #10's actual scope).
- **No test for `getInfluencer`'s success or 404 branch.** Lower priority
  than it looks — this ticket's own frontend diff never calls the `GET`
  endpoint (the board still reads via the existing direct-Supabase
  `fetchData()`), so this route has no live caller yet. Real gap, correctly
  outside #10's scope (the *auth failure* case on `GET` is tested), carried
  forward rather than closed here.
- **No negative-number guard on `min_visit_payment`.** Checked against the
  approved design doc's own Interfaces section before treating this as a
  miss: it names only "rating out of range" and "negative count" as this
  handler's validation failure cases, not a `min_visit_payment` lower
  bound. Not a deviation from what was approved — noted, not required.
- **The `hasInfluencerAdminAccess`/`AuthenticatedRequest` shape is now
  duplicated a third time** (`foodswipe.ts`, `loyalty-config.ts`,
  `influencers.ts`), with two different conventions live in the same repo:
  `foodswipe.ts`/`influencers.ts` dereference `userProfile.role` directly
  (throws on a null/undefined profile); `loyalty-config.ts` (`ENG-007`)
  uses `profile?.role` throughout and takes a typed, nullable parameter.
  This ticket matches its most direct same-day sibling (`foodswipe.ts`)
  exactly, which is the right call for "read like the code around it" given
  two precedents already disagree — but the disagreement itself is real and
  pre-dates this ticket. Filed as a proposal (see below) rather than fixed
  here: unifying three files' access-check shape is a cross-cutting change
  this ticket didn't create and shouldn't absorb.
