## Design conformance (re-checked, not re-derived from round 1)

Re-read `agents/architect/designs/ENG-027-....md`'s Approach section on the
cancellation-vs-credit race: "cancellation updates `orders.status`
unconditionally; it does not touch `loyalty_processed_at`... if a cancellation
commits before any credit attempt, the credit function's own guard blocks it
— credited zero times (AC5). If a credit already committed, a later
cancellation still updates status... but does not delete or rewrite the
existing ledger entry (AC16)." The migration's guard clause
(`loyalty_processed_at IS NULL AND status IS DISTINCT FROM 'cancelled'`)
matches this exactly, and neither AC5 nor AC16 is touched by round 2's two
fixes. No divergence.

## Review of what isn't there

**One pre-existing, repo-wide pattern, not a defect this ticket introduces:**
`loyalty_ledger_entries`'s own comment claims "append-only, never updated or
deleted," but nothing in this migration (or any other on this project —
checked: `create_influencer_notes.sql` makes the identical claim, same
comment-only enforcement) actually revokes `UPDATE`/`DELETE` from
`service_role` on the table. `service_role` bypasses RLS by default on this
project (confirmed on the replica above: `Bypass RLS` on `service_role`,
absent on `anon`/`authenticated`), so any future service-role code — a
mis-written ticket-5 correction, or an unrelated handler — could technically
mutate a supposedly-immutable ledger row with no database-level guardrail,
same as it always could have on this project's other "append-only" table.
**Not blocking** — introducing that lockdown on this ticket alone would be a
new, unprecedented pattern on this project ("reads like the code around it"
cuts the other way here), and the actual write path this ticket ships
(`credit_order_if_eligible`) only ever inserts. Filed as a proposal rather than
fixed here: `proposals.md`, this date.
