## Design conformance

Re-read `agents/architect/designs/ENG-051-....md`'s Interfaces section
line-by-line against the function body. Signature order, the 7-step body
order (guard raise → advisory lock, seed `1` → idempotency check before the
balance read → rate resolve → `not_enrolled` → customer-exists →
`invalid_code` → balance sum → `insufficient_balance` → insert →
`redeemed`), the idempotency-match condition
(`platform_customer_id`/`restaurant_id`/`points = -p_points`), and the
grant/revoke shape all match the design exactly. No divergence found.

One thing the design itself left unaddressed and this migration's own build
hop caught: `rate_applied` was `numeric(5,2)` (sized for the earn side's
percentage rates); `redemption_value_per_point` is `numeric(10,4)`. The
design's Interfaces section states `rate_applied = v_rate` without naming the
width mismatch. The fix (widen to `numeric(10,4)`) is correct and the right
size — not a truncation, every existing percentage value casts up losslessly,
confirmed below, not merely asserted.

## Line-level review

- **Ordering is correct and load-bearing, confirmed by reading, not by the
  comment claiming it.** The idempotency lookup runs before the balance read,
  inside the advisory lock, after the input guard. This is the one property
  the design calls out as correctness-critical (a genuine retry must replay,
  not bounce as `insufficient_balance`) — verified directly this round with an
  actual replay against a real prior debit, not inferred from the code's own
  shape (below).
- **Balance boundary is `<`, not `<=`** (`if v_balance < p_points then return
  'insufficient_balance'`) — an exact-balance redemption must succeed.
  Verified directly (below), not read off the operator.
- **The advisory lock key is namespaced correctly.** Seed `1`, distinct from
  `ENG-007`'s own seed `0` on the same `hashtextextended` mechanism — the two
  locks cannot collide on the same 64-bit key. Correct and matches the
  design's own stated reason.
- **`security definer` hardening**, checked the same way `ENG-048`'s gates
  checked it: `set search_path = 'public'` is pinned, and every table
  reference in the body is schema-qualified (`public.loyalty_ledger_entries`,
  `public.restaurant_loyalty_configs`, `public.platform_customers`) regardless
  — belt-and-suspenders against a search-path hijack even though the pin alone
  would suffice.
- **`order_id`/`fulfillment_reason` are omitted from the insert's column list**
  rather than passed as explicit `null`. Not a defect — both are nullable with
  no default, so the omission is exactly equivalent to an explicit `null` —
  but it's a minor style question, not an established violation: no prior
  function on this table has ever inserted a null-shaped `order_id`/
  `fulfillment_reason` pair via SQL (`credit_order_if_eligible` only ever
  inserts non-null values for both, on the `online_order` path; `dine_in`
  rows are inserted from TypeScript, not this file). Nothing to match or
  diverge from. Non-blocking, not a standard — first occurrence.
- **`amount` stores a positive dollar figure (`p_points * v_rate`) while
  `points` stores the negative delta.** Matches the design's own Interfaces
  section exactly (`amount = p_points * v_rate`, not `-p_points * v_rate`), so
  this is a design decision faithfully implemented, not an implementation
  choice to relitigate here. Read as "amount is the magnitude of the
  transaction this row is about" (consistent with how the earn side already
  uses the column — the cart total that produced the points, not a signed
  mirror of `points`), not as a bug. Noting it so a future reader isn't
  surprised the two columns carry opposite conventions; not blocking, and not
  this ticket's decision to reopen.
