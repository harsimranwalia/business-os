## Design conformance

Checked the committed code against
`agents/architect/designs/ENG-006-unified-customer-identity.md` directly,
line by line rather than trusting the ticket log's summary:

- **Tables** — both column sets match the design's Data section exactly:
  `platform_customers` (`id`/`phone`/`display_name`/`consent_recorded_at`/
  `created_at`/`updated_at`) and `platform_customer_legacy_links`
  (`id`/`platform_customer_id`/`legacy_customer_id` unique/`restaurant_id`/
  `brand_id`/`matched_via` checked/`needs_review`/`review_reason`/
  `linked_at`). `display_name` and `consent_recorded_at` are present but
  unpopulated by this ticket's code, matching the design's own "not
  collected by this ticket" note for both.
- **RLS** — matches exactly: `platform_customers` gets owner
  select+update (no client insert/delete), `platform_customer_legacy_links`
  gets owner select only (no client insert/update/delete). Verified this is
  the *complete* policy set for both tables (no extra policy either design
  or migration doesn't account for).
- **Interface** — `POST .../verify` runs with the caller's own JWT via
  `admin.auth.getUser(token)`, matching the design's stated pattern (same
  shape as the existing `proxy-login` function). Upsert on `platform_customers`
  keyed on `id` with `onConflict: 'id'` is a no-op-shaped update on a
  returning login, matching AC2 as designed. No separate "read my links"
  endpoint was added, matching the design's explicit call not to build one.
- **Linking semantics** — `linking.ts`'s `planLinks` matches the design's
  "What 'ambiguous' means here, precisely" section verbatim: different
  restaurants on one phone auto-link with no review; same
  restaurant/brand-scope collision or a diverging name links but sets
  `needs_review`/`review_reason` rather than dropping the match. Verified
  in the unit tests, not just the design doc's prose.
- **Validator** — `validation.ts` matches the design's Risks section call
  for a stricter boundary validator instead of reusing `crm/utils.ts`'s
  lenient `normalizePhone()`, with the reasoning restated in its own header
  comment.

No divergence found between the design and the code.
