## Findings — non-blocking

**F1 — `BroadcastComposer.tsx:167-169` (`addStep`), low-to-medium
severity, high confidence.** The default delay for a newly added drip step
is `24 * (current.length + 1)` hours. This only happens to land on a
`BROADCAST_DELAY_OPTIONS` preset (0, 1, 24, 72, 168, 336, 720) for the
first click past the initial two-step minimum (`2 -> 24*3 = 72`, "3 days
later"); every click after that produces a value absent from the list
(`96`, `120`, ...). Radix `Select` then has no matching `SelectItem` for
that `value`, so the trigger renders with no visible label until the owner
manually reopens it and picks a real option. Not data-corrupting — the
value is still valid, still submits, and is trivially fixable by the owner
reselecting — but it's a real, deterministically-reachable display defect
for any drip with 4+ steps, which the feature explicitly supports with no
upper bound. **Fix, if picked up:** pick the smallest listed option
strictly greater than the previous step's delay, falling back to the
largest option once past it, rather than a fixed arithmetic guess.

**F2 — `BroadcastComposer.tsx`, shape, low severity.** 526 lines at
creation — already past `engineering-standards.md`'s ~400-line smell
threshold, not grown into it the way `ENG-034`'s `CateringForm.tsx` was.
Two pieces read as their own module: the per-step email/SMS editor block
(`:360-447`, ~90 lines) and the schedule date/time picker (`:450-508`,
~60 lines). Splitting either would bring the file back under the
threshold. Not blocking — the file is still one cohesive concern (the
compose form), matching this same ticket's own design rationale for why
`BroadcastComposer` is split out from `Broadcasts.tsx` in the first place;
worth doing if this file grows again.
