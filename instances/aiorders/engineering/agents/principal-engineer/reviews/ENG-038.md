## Read against the design and the security findings it fixes

**Finding 1 (recipientId contract).** Traced the new
`sendBroadcastMessage` control flow end to end: looks up
`broadcast_campaign_recipients` by `recipientId`, requires
`status === 'claimed'`, then derives `customer_id`/`restaurant_id`/
`step_id` from that row — never from the request body. Confirmed
`broadcast_campaign_recipients.restaurant_id` is a real, populated column
(`supabase/migrations/20260904140000_broadcast_campaigns.sql:101`,
denormalized on purpose so the dispatcher's claim query never joins out),
and that `'claimed'` is a legal status value
(`20260904150000_broadcast_recipients_claimed_status.sql`, added in the
*original* build commit `c1d55df`, already live in the constraint —
pre-existing, not new this round).

Checked one thing closely enough to be worth recording even though it
turned out clean: the new consent re-check reads
`customer.consent_email?.consent !== false`, which only does what the
backend's own notebook claims ("re-derived from the freshly-fetched
customer row") if `consent_email` is an object with a nested `.consent`
field, not a plain boolean. Grepped every read/write site
(`crm/customers.ts`, `broadcast-dispatch/dispatch.ts`'s own pre-existing
`resolveRecipient` check, `website-submissions/*.ts`) — the object shape is
real and this is the established idiom already used twice elsewhere in
this exact file. Not a defect; recording the check since a shape mismatch
here would have silently made the "defense in depth" consent gate inert.

**Finding 2 (audience cap / send-interval).** `audienceExceedsCap` and
`tooSoonSinceLastCampaign` both run after `requireRestaurantAccess` (no
unauthenticated query), both fail closed on a lookup error, and
`updateBroadcast` correctly gets the cap but not the interval check (an
edit doesn't create a new campaign row, so it doesn't touch the "how
often" half of the finding — reasoned explicitly in the backend's own
notebook and confirmed by reading the call sites). The one `.or()` filter
in `audienceExceedsCap` interpolates a server-computed ISO cutoff, never
attacker text — same pattern security's own round-1 walk already cleared
for `enrollAudience`.

## Good work, worth naming

The "derives customer, restaurant, and content strictly from the claimed
recipient row, ignoring anything else the caller sends" test is exactly
the right shape for a security regression guard — it doesn't just test the
new code path, it replays the *old* attack shape against the new code and
asserts the attacker-supplied fields were never read. That's a
meaningfully stronger guarantee than "the new contract works" and is the
test I'd want here if I were choosing one myself.
