## Design conformance

Checked the committed code against
`agents/architect/designs/ENG-011-client-stage-health-visibility.md` line
by line, and independently re-verified the one factual claim the
implementing pass's own comment made rather than trusting the comment:

- **Stage derivation** matches the design's three-bucket mapping exactly
  (`is_active` true → `live`; false + below final step → `onboarding`;
  false + at/above final step → `inactive`). The code comment claims the
  wizard's final step is `3`, "confirmed against restaurant-portal's
  OnboardingWizard.tsx and LogoMenuStep.tsx." **Re-verified independently
  this review, not taken on the comment's word**: grepped
  `restaurant-portal`'s onboarding source directly —
  `LogoMenuStep.tsx:111` writes `onboarding_step: 3` and is confirmed the
  last step (`AddLocationsStep.tsx` writes `2`, `OnboardingWizard.tsx`'s
  own initial value is `1`; no step 4 exists anywhere in that directory).
  One value worth flagging that the design didn't anticipate:
  `OnboardingWizard.tsx:123` sets `onboarding_step: -1` as a "special flag
  for no brand" — traced this to a **local React state object only**,
  never written to the `brands` table (it fires when no brand row exists
  for the logged-in user at all, so there's no row to write it to). Not a
  live edge case this ticket's `deriveStage` needs to handle; confirmed
  rather than assumed.
- **Health derivation** matches the design's four-bucket signal
  (`active`/`at_risk`/`inactive`/`no_data`) reusing
  `calculate_platform_analytics()`'s aggregate. The specific day
  boundaries (14/30 days) aren't in the design doc — the design left the
  exact recency thresholds open, and the implementing pass's own comment
  says so plainly rather than presenting them as spec. Judgement call,
  easy to retune (one function, `deriveHealth`, both constants named).
- **No new stored field beyond the one additive column** — confirmed:
  `git diff --stat` on `aiorders-api` shows one migration file and no
  change to `brands`/`restaurants`. Matches the design's stated
  drift-avoidance rationale (closing the G1 readback's named one-way-door
  risk) exactly.
- **No new endpoint** — confirmed: both new response fields extend the
  existing `admin-portal` brands-list route; `Brands.tsx` makes no new
  fetch call.
- **`no_data` renders distinctly from `inactive`**, per the design's own
  named risk — confirmed in `getHealthPill`: four distinct cases, no
  fallthrough between them.
- **One thing the design didn't discuss, checked anyway because it's a
  first for this instance: cross-repo deploy ordering.** This ticket
  ships to two separately-deployed repos. If `aiorders-admin-hub`'s new
  `Brands.tsx` reaches production before `aiorders-api`'s new response
  fields do, `brand.stage`/`brand.health` are `undefined` on every row.
  Traced both pill functions' `default` branches (`getStagePill`,
  `getHealthPill`) — both render a plain `-` rather than throwing or
  mis-rendering. So either deploy order degrades gracefully; still
  recommending `aiorders-api` first in the release plan below so the
  *intended* order is documented rather than left to chance.

No divergence from the design's intent found in either repo.
