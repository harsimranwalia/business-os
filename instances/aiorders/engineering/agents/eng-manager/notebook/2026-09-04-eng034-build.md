## Interpretation calls, flagged rather than silently resolved

- **No price anywhere in the picker.** The design's `## Data` section and
  `## Out of scope` both say Piece 1 "shows no price anywhere" — stronger than
  "doesn't store a price." `CateringMenuSelector` never renders `item.price`,
  unlike `MenuList.tsx`'s own card, which does.
- **Selection identity vs. wire shape.** The design's Data section gives the
  *stored* element shape (`category`/`item_id`/`name`/`quantity`/`note`, "AC-5's
  five fields, no more") and separately calls for a composite
  `${menuIndex}-${categoryIndex}-${itemIndex}` "selection identity" so two
  same-named dishes across categories never collide. Read these as two
  different concerns: `CateringSelection` (the picker's own controlled value)
  carries an `id` field for that identity, and `CateringForm` strips it
  (`selections.map(({ id, ...selection }) => selection)`) before POSTing, so
  the wire payload still carries exactly the five named fields.
- **`category`/`name` are snapshots taken at add-time**, read directly off the
  live menu the moment a guest sets a quantity > 0 — satisfies AC-5's
  snapshot requirement without needing a second re-resolution step at submit,
  since nothing on the page can change the menu between adding an item and
  submitting the same form load.
- **No separate `no-stock` handling.** Reused `isDishHidden` from
  `@/utils/menuItems` unmodified — it filters only `hidden`/`status:'hidden'`,
  so a `no-stock` dish stays selectable by construction, matching the design's
  explicit rule, with no new code needed for it.
- **`note` capped at 500 chars client-side** (`maxLength` on the `Input`) —
  not itself named by an AC, but matches `catering-request`'s own already-
  shipped server boundary (`ENG-033`) so a guest never types past a limit the
  request will just reject.
- **Which submit button fired is read from `SubmitEvent.submitter`, not
  component state.** A button's own `onClick` setting state (e.g.
  `setPendingAction(...)`) is not guaranteed to have flushed into the closure
  `handleSubmit` reads by the time the browser's very next `submit` event
  fires — `(e.nativeEvent as SubmitEvent).submitter` sidesteps that timing
  question entirely.
- **AC-9 byte-parity, mechanically enforced rather than asserted.** Every
  gate-open-only change is expressed as `orderFormEnabled ? new : original`
  (labels, `required`, placeholder, the submit-button block) rather than a
  parallel gate-closed branch written separately — so there is exactly one
  place per field where the "closed" behaviour could drift, and it's the
  literal original code. Verified `required={false}` on a native input
  renders no `required` attribute at all in React (same DOM as omitting the
  prop), and `orderFormEnabled && (<Picker/>)` renders nothing (no wrapper)
  when closed.
- **Guest-count note / fulfillment description placement.** Rendered as an
  extra `<p>` under `number_of_guests` / `delivery_method` respectively, gated
  on `orderFormEnabled && formData.delivery_method` and the specific
  `fulfillmentCopy[value]` key being present; each container's `h-16` height
  class is relaxed only when its own note/description is actually rendering,
  so the gate-closed layout is unchanged pixel-for-pixel.
- **`CateringFulfillmentCopy` and the two new `CateringPageContent` keys**
  mirrored field-for-field off `restaurant-portal`'s already-shipped copy of
  this same interface (`types/website.ts`, read from that repo's own `_eng`
  worktree at `origin/main`) rather than reinvented independently — same
  precedent `ENG-033`'s own hop set for the `aiorders-api` copy of this type.
