## ENG-022 (aiorders-api) — raw `error.message` reachable via `verifyRestaurantAccess`'s own catch-all (6th+ occurrence — not re-proposed)

**Category:** A05 Security Misconfiguration (verbose error). Occurrence: not
independently counted against the `ENG-009`/`ENG-010` tally — different call
shape (a shared helper's own catch, not a handler's top-level catch) but the

client, via `offers.ts`'s `access.error` in a 200 body or via a thrown

correct"). Not blocking `ENG-022`'s gate: pre-existing, and only reachable
when `verifyRestaurantAccess`'s own DB lookup errors, not the ordinary-denial
path (which returns the clean fallback string).

**Not re-proposed.** The 2026-09-02 `ENG-009` proposal
(`agents/principal-engineer/notebook/2026-09-02-security-proposal-verbose-error-response.md`)
already covers this class and remains unactioned; a second proposal would be
a duplicate for `principal-engineer` to reconcile, same disposition `ENG-010`
already set for its own 4th/5th occurrences.

## ENG-022 (aiorders-api) — `brand-portal` runs on a service-role client; `verifyRestaurantAccess` is the only access control, no RLS backstop

**Category:** A01, architectural note rather than a per-ticket finding.
Confirmed by reading `brand-portal/index.ts:38-44` directly (unchanged by
this diff, not in scope to fix here): the Supabase client every handler in
this directory uses is constructed with `SUPABASE_SERVICE_ROLE_KEY`, so RLS
is bypassed at the database layer for all nine files, not only the five
`ENG-022` touched. `verifyRestaurantAccess`/`requireRestaurantAccess` is not
one layer among several — it is the *entire* access control for this
function. Worth keeping in mind for any future `brand-portal` change: a new
call site that forgets the check (the exact bug this ticket fixed) has
nothing else standing behind it.

Not filed as a proposal — no action follows from this by itself (it explains
*why* `ENG-022` was correctly rated P0 and confirms this diff is sufficient
to close the hole, not a gap needing a fix of its own). Recorded here so a
future review of this directory starts from the fact instead of re-deriving
it.

## ENG-015 (aiorders-api) — RLS activation on `public.restaurants` unverified from the repo (recommendation, not a confirmed defect)

**Category:** A01-adjacent, verification gap rather than a finding of a
live bypass. `public.restaurants` predates all tracked migration history —
no migration creates the table or runs `ALTER TABLE ... ENABLE ROW LEVEL
SECURITY` on it (`grep -rnE "ALTER TABLE (public\.)?restaurants\b"` and the
equivalent `CREATE TABLE` search, both zero matches across every migration
file). QA's and the round-2 code review's own static traces verified the
new `INSERT` policy's *logic* — correctly — but both assume RLS is already
active on the table; this is one layer beneath either check. No live
Postgres/Supabase session reachable this pass to confirm
`pg_class.relrowsecurity` directly (same standing gap every other hop on
this ticket already named).

**Not asserted as a live defect** — this table's own three-migration
public-SELECT lockdown history (2025-08-14) would be pointless unless RLS
has been enforced throughout, and no incident in this business's history
suggests otherwise. **Not blocking `ENG-015`'s gate:** pre-existing
regardless of this diff, and not safely fixable blind (a defensive
`ENABLE ROW LEVEL SECURITY` would be a platform-wide, unbounded-blast-radius
change touching every direct-client caller across four frontends, not just
this ticket's surface — considered and rejected, same reasoning that kept
`updateBrandOwner()` out of this ticket). Full reasoning:
`agents/security/reviews/ENG-015.md`, Finding #1. Recommendation folded
into QA's own already-planned staging smoke test rather than filed as a
separate proposal: that test should include a direct insert/update attempt
as a test partner account, confirming the row is actually rejected or held,
never unrestricted — proving RLS-enabled-and-correct in one empirical check.

## ENG-031 (aiorders-api) — RLS activation on `public.catering` unverified from the repo (2nd occurrence today, routed forward to ENG-033)

**Category:** A01-adjacent, verification gap rather than a confirmed
defect — same class as this file's own ENG-015 entry above
(`public.restaurants`), same day, same root cause (no live Postgres or
Supabase MCP session reachable this host/session to check
`pg_class.relrowsecurity` directly).

`20250729143357_initial_restaurant_rls.sql` defines seven policies against
`public.catering` (owner/manager SELECT, public INSERT, owner/manager
UPDATE/DELETE, admin ALL), and `ENG-031`'s design leans on those policies

authorization code. No tracked migration runs `ALTER TABLE ... ENABLE ROW

`supabase/migrations/` — confirmed by grep, not assumed. **Not asserted as

named policies on `catering` ("Enable insert for authenticated users

their prior existence is real evidence RLS predates tracked history on
this table too, the same inference `ENG-015`'s finding drew for
`restaurants`.

**Not blocking `ENG-031`'s gate:** pre-existing by five-plus weeks
minimum, not worsened by two nullable columns riding on the same
protection as every other column already on this table, and not fixable
blind within a schema-only ticket's scope.

**Not filed as a proposal, not folded into a smoke test — routed forward
instead.** Unlike `ENG-015`, `ENG-031` has nothing live to smoke-test
(both new columns are null and unread until `ENG-033` ships), so there is
no already-planned staging step to attach the empirical check to yet. The
right point is `ENG-033`'s own QA/security gate — the first ticket where
`selections`/`action_type` are actually reachable through a real path.
That gate's own Inputs already include this notebook

not a note that depends on anyone remembering to look for it.
**Recommendation for whoever runs `ENG-033`'s gate:** attempt a `catering`
SELECT/UPDATE as a non-owning authenticated account against a real
request and confirm it is actually rejected — one empirical check proves

Two occurrences of this exact class in one day, two different tables —

## ENG-032 (restaurant-portal) — `brand-portal/catering.ts` has correct access checks but zero negative-case test coverage, found verifying QA's own coverage claim

**Category:** A01-adjacent, test-coverage gap rather than a code defect —
the access-check code itself is correct. QA's test plan for this ticket
(`agents/qa/test-plans/ENG-032.md`) justified skipping a new negative-authz
test by citing "`ENG-022`'s own suite already covers `brand-portal`'s
access-check call sites generally." Checked directly against
`origin/main`'s tree rather than taken on trust: `ENG-022`'s 19 negative
tests span exactly 5 of `brand-portal`'s 10 handler files (`feedback`,
`customers`, `hiring`, `website`, `offers`); `catering.ts` isn't one of
them, and no `catering.test.ts` exists anywhere in the directory.

Read `catering.ts` itself on `origin/main` to check whether the missing
tests are hiding an actual defect (same instinct as `ENG-022`'s own root
cause — an *assumed*-correct access check turning out not to be): they
aren't. All three actions (`get_catering_requests`,
`create_catering_request`, `update_catering_request`) call
`verifyRestaurantAccess` before touching the row, correctly ordered, same
shape `ENG-022` fixed the other five files into. This is a coverage gap,
not a live vulnerability.

**Why it's newly relevant, not just newly noticed:** `selections`/
`action_type` have existed on the `catering` row since `ENG-031`, but
nothing in `restaurant-portal`'s UI rendered them until `ENG-032`. A
`get_catering_requests` access-check regression was always possible; as of
this ticket it's also immediately consequential, since its return value
now reaches the owner's screen directly. `menus.ts`, `onlineOrders.ts`, and
`profiles.ts` show the identical no-test-file gap (confirmed via the same
directory listing) but weren't independently re-verified for a correct
access check this pass — outside what `ENG-032`'s own gate needed checked.

**Not blocking `ENG-032`:** that ticket adds no code to this repo and
changes nothing about what `get_catering_requests` returns or to whom —
see `agents/security/reviews/ENG-032.md`, Negative-case test coverage and
Findings #1. Filed as a proposal
(`agents/eng-manager/proposals.md`, 2026-09-03, security, `aiorders-api`)
rather than fixed inline — out of `ENG-032`'s own repo and scope, and the
department doesn't turn its own findings straight into tickets
(`eng_build_loop.md` step 3).

Full detail: `agents/security/reviews/ENG-032.md`.
