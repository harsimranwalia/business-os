# Security notebook — 2026-09-05

## ENG-020 (aiorders-api / restaurant-portal) — `verifyRestaurantAccess` leaks restaurant existence via a distinct error string, found verifying AC5 against the design's own claim (gate: PASS, non-blocking)

**Category:** A01-adjacent, minor information disclosure — verification
finding, not a live exploit of anything sensitive.

`agents/architect/designs/ENG-020-marketing-roi-attribution-reporting.md`
states, in its Interfaces table, that a denied request reveals "nothing about
that restaurant, including its existence." Checked against the actual code
rather than taken on trust: `brand-portal/utils.ts`'s `verifyRestaurantAccess`
(unchanged by this diff) returns `'Restaurant not found'` when the
`restaurants` row itself doesn't exist, and a separate `'Access denied to
this restaurant'` (or whatever `RLS`/ownership check produces) when it exists
but isn't the caller's — two distinguishable strings, and `acquisition.ts`
forwards `access.error` verbatim. An authenticated brand-portal caller
(any restaurant owner/manager account) can therefore learn whether an
arbitrary UUID is a real restaurant row, one bit at a time, before ever
reaching this ticket's own report data.

**Not blocking `ENG-020`'s gate.** The helper and this exact behaviour are
pre-existing and shared verbatim by every other consumer in the directory
(`menus.ts`, `catering.ts`, `restaurants.ts`, `onlineOrders.ts`) — not
introduced or worsened by this ticket. Exploit value is marginal: a
restaurant UUID isn't a credential, and the existence bit exposes nothing
about the restaurant's data, which stays denied either way.

**Not filed as a proposal.** Narrower than the observation/proposal bar —
nobody would be disappointed if this specific string-granularity question
goes unfixed indefinitely, and fixing it for one new caller while every
sibling caller keeps the coarser behaviour would recreate the
half-guarded-function shape `ADR-011` already declined on this same ticket
for a different reason. Logged here so a future pass touching `utils.ts` or
re-reviewing this directory's error surface starts from the fact rather than
re-deriving it. First occurrence of this specific mechanism — distinct from
the standing `error.message`-verbosity proposal (`ENG-009`,
2026-09-02-security-proposal-verbose-error-response.md), which is about
exception internals leaking, not a deliberate two-valued denial string.

Full detail: `agents/security/reviews/ENG-020.md`, Findings — non-blocking, #1.
