## ENG-010 (aiorders-api) — repo-wide CORS wildcard on every admin-portal handler, named for the first time

**Category:** A05 Security Misconfiguration (permissive CORS).
**Severity:** Low. First occurrence this gate has named explicitly, though the
pattern itself is not new — `grep -rn "Access-Control-Allow-Origin"
supabase/functions/admin-portal/handlers/*.ts` shows all eleven handler files
in this directory, including this ticket's new one, use the identical
`'Access-Control-Allow-Origin': '*'`, predating every ticket this gate has
reviewed.

`security-baseline.md` states plainly: "CORS not `*` on anything
authenticated." Every route under `admin-portal` is authenticated, so this is
a real, literal deviation, not a false positive — worth stating rather than
passing over silently just because it's old. Read as lower-severity than the
baseline's flat framing suggests for this specific app: authorization here is
a `Bearer` token the browser does not attach automatically the way it would a
cookie, so a third-party origin can't ride an authenticated user's browser
session merely because the origin check is wide open — an attacker would
already need the token itself, at which point the CORS header isn't the
control standing between them and the data.

**Not filed as a three-strike proposal** — this is one repo-wide fact
restated by every ticket that touches this directory, not a new occurrence
appearing across independent tickets the way the verbose-error pattern did.
Worth a second look, by a future review or a dedicated pass, only if a
concrete exploit path surfaces that this reasoning didn't account for.
