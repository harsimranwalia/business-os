## ENG-033 (aiorders-api) — pre-existing HTML-injection into the owner-notification email, found reading `catering-request/index.ts` in full (proposal filed)

**Category:** A03 Injection, missing output encoding for an HTML sink.
`index.ts:348-378` (unchanged by `ENG-033`'s diff) builds `message_html`/
`message` via raw template-literal interpolation of `full_name`, `phone`,
`email`, `event_type`, `event_location`, `event_timings`, `number_of_guests`,
`normalizedDeliveryMethod`, and `requirements` — every one attacker-controlled
on this intentionally unauthenticated public endpoint — with zero
HTML-escaping. `send-notification/index.ts:142-162` forwards both fields
verbatim to a third-party workflow webhook (Pabbly Connect) that actually
emails/SMS/WhatsApps the restaurant owner. Confirmed by reading both files
directly.

**Severity: Medium.** Bounded impact — most email clients strip `<script>`/
inline event handlers, so this is an HTML-formatting/link-injection
(phishing/spoofing) vector inside an otherwise-legitimate transactional
email, not script execution or data exposure — but real, reachable by
anyone, zero cost, zero authentication, today, independent of this ticket.

**Not blocking `ENG-033`'s gate:** the vulnerable lines are untouched by this
diff, and `action_type`/`selections` — the only two fields this ticket adds —
are not included in either template. Filed as a proposal
(`agents/eng-manager/proposals.md`, 2026-09-04, security, `aiorders-api`),
same routing `ENG-032`'s own review used for an analogous pre-existing/
out-of-diff finding.

Full detail: `agents/security/reviews/ENG-033.md`, Finding 1.

## ENG-038 (aiorders-api) — `broadcast_message` is reachable fully unauthenticated through the pre-existing `outgoing-communications` systemTriggered bypass (gate: FAIL)

**Category:** A01 Broken Access Control, compounded by A04 (spam-relay
capability) and a Restricted-data (PII contact channel) misuse angle.

`outgoing-communications/index.ts` (pre-existing, unchanged by this diff)
skips its entire authentication block whenever the caller's own JSON body
sets `systemTriggered: true` — a client-supplied boolean, not a credential.
This is `ENG-036`'s own bug (P0, filed 2026-09-03, still `state: designed`,
owner `architect`, not yet built — confirmed on the board, not assumed).
`ENG-036`'s PRD enumerated the actions reachable this way at filing time
(`order_feedback_request`, `welcome_offer`/`every_order`/`first_order`,
`brands.ts`'s campaign notifications) — it could not have named
`broadcast_message`, since `ENG-038` had not added it yet.

This ticket's new `sendBroadcastMessage` (`actors/consumers.ts`) trusts
`data.customerId`/`data.restaurantId`/`data.emailSubject`/`data.emailBody`/
`data.smsBody` verbatim, with no lookup against a real campaign/step and no
re-check of `consent_email`/`consent_sms` (that check lives only in
`broadcast-dispatch/dispatch.ts#resolveRecipient`, bypassed entirely by
calling `outgoing-communications` directly). Net effect: an unauthenticated
internet caller can send arbitrary-content email/SMS to any customer id in
the database, spoofed as any restaurant (`from: noreply@aiorders.io`,
`fromName: restaurant.name`), bypassing consent, with no rate limit —
verified by reading `index.ts`, `consumers.ts`'s new case, and
`dispatch.ts` directly, not inferred.

**Severity: Critical.** Zero authentication, zero rate limit, arbitrary
content, arbitrary target, on an L1 project explicitly documented as
"highest blast radius of the set" (`agents/eng-manager/config/projects.md`).
Worse than the actions `ENG-036` already enumerated: those are bounded to a
real order/template event; this one is free-text.

**Blocking `ENG-038`'s gate.** Fix specified in the ticket log (round-1
security-gate entry): switch the call contract to a `recipientId` — the
already-claimed `broadcast_campaign_recipients.id` — and derive
customer/restaurant/content from that row server-side, never from the
request body. Closes this specific action regardless of `ENG-036`'s own
timeline; does not fix `ENG-036` itself (every other actor/action behind
the same shared gate stays exposed until that ticket ships).

Full detail: `agents/eng-manager/board/ENG-038-broadcast-composer-api-dispatcher-and-unsubscribe.md`
(round-1 security-gate log entry — no `agents/security/reviews/ENG-038.md`
exists, per this gate's own "no receipt on fail" rule).

## ENG-038 (aiorders-api) — no rate limit, quota, or audience-size cap on broadcast sends (2nd occurrence — routed from ENG-037, now decided: blocking)

**Category:** A04 Insecure Design, business-logic abuse / missing
rate-limit.

`ENG-037`'s own security review (this file, above) explicitly routed this
gap forward and asked `ENG-038`'s gate to either confirm a bound exists or
record its absence as a deliberate decision. Checked directly this pass:
`validateBroadcastInput`/`createBroadcast`
(`brand-portal/broadcasts.ts`) and `enrollAudience`
(`broadcast-dispatch/dispatch.ts`) impose no cap on recipients per
campaign, campaigns per restaurant per day, or minimum send interval.
`BATCH_SIZE = 200` throttles per-tick throughput only. No ADR or design
text accepts this specific abuse angle (the design's Risks section frames
the unbounded case as throughput/latency, not abuse-prevention).

**Severity: Medium.** Requires a legitimate or compromised restaurant-owner
credential (not anonymous, unlike the finding above) — but the send
infrastructure (`noreply@aiorders.io`, the shared SMS provider) is common
across every tenant, so one restaurant's unbounded send is a
deliverability/reputation risk for every other tenant on the platform, not
just its own.

**Blocking `ENG-038`'s gate** — not re-routed a third time. Accepting the
gap is the approver's call (risk-acceptance ADR), not this gate's to grant
silently; a cheap fix (recipient cap and/or minimum send interval, checked
in `createBroadcast`) is specified in the ticket log rather than deferred
further.

Full detail: `agents/eng-manager/board/ENG-038-broadcast-composer-api-dispatcher-and-unsubscribe.md`
(round-1 security-gate log entry).

## ENG-038 (aiorders-api) — both round-1 findings confirmed closed (gate: PASS), one new non-blocking finding

Re-verified both findings above against the actual fix commits
(`92d1bd4`/`63f5635`) and the live code/schema, not against the backend's or
principal-engineer's own accounts of them. Finding 1: `sendBroadcastMessage`
now takes only `{recipientId}`, requires `status = 'claimed'` on that row
(a random `uuid`, atomically single-claimable, consumed within one HTTP
round trip), and derives customer/restaurant/content/consent from the
database only — the removed fields aren't read anywhere in the function
body. Finding 2: `audienceExceedsCap`/`tooSoonSinceLastCampaign` run after
`requireRestaurantAccess`, fail closed, and are backed by tests asserting on
the real returned error strings. Fresh regression: 85/85 across five suites.

**New, non-blocking: A04-adjacent TOCTOU race in `tooSoonSinceLastCampaign`**
(`brand-portal/broadcasts.ts`, `createBroadcast`). The interval check is a
plain `SELECT`, not a lock — two `create_broadcast` calls close together for
the same restaurant can both read "no recent campaign" and both proceed,
defeating the 24h cooldown once per race won. Bounded blast radius: each
resulting campaign is still independently capped at `MAX_RECIPIENTS_PER_CAMPAIGN`
(10,000), which has no equivalent race (a point-in-time count, not a
state-transition decision). Requires an already-authenticated owner
credential — same prerequisite Finding 2 itself assumed — firing precisely
concurrent requests, not a single crafted payload. Not filed as a proposal:
specific to this ticket's own new code, not a systemic pattern.

Full detail: `agents/security/reviews/ENG-038.md` (the receipt — round 1 had
none, per this gate's "no receipt on fail" rule).
