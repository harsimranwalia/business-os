## ENG-049 (aiorders-api) — CloudWaitress webhook has no signature check at all; this ticket wires it directly to real financial crediting (gate: FAIL)

**Category:** A08 Software & Data Integrity (webhook signatures verified —
always, no "we'll add it later" — `security-baseline.md`) compounded by A04
Insecure Design (unbounded business-logic abuse).

`external-integrations`'s CloudWaitress route has never checked that an
inbound webhook is actually from CloudWaitress —
`CloudWaitressWebhook.secret` is declared on the interface
(`cloudwaitress.ts:7`) and never read anywhere in the file; the router
(`index.ts`) does no auth of its own either, matching this project's own
`supabase/functions/README.md` per-function note ("No JWT/auth check at
the top-level router — relies on webhook secrets/service-role trust",
`README.md:294`) — a reliance that isn't actually wired up. The missing
half is a live value, not a hypothetical: `cloudwaitress-middleware/
handlers/restaurant.ts:6-7` hardcodes the real webhook registration
(`AIORDERS_WEBHOOK.secret`) CloudWaitress is configured with for every
restaurant — the same field this route's own interface anticipates and
never compares against. Pre-existing, and — on its own, before this
ticket — bounded to fabricating inert `orders` rows. `ENG-049` is what
gives an unauthenticated caller a reason to do that: `cw_order_id` (new
this ticket) lets a forged order be found later, and `loyalty-auto-
complete`'s new 24h sweep (`sweep.ts`) credits *any* row matching its
eligibility predicate with no check that CloudWaitress ever reported it
complete — crediting `bill.cart - bill.discount`, read verbatim from the
same forged, attacker-authored payload. Traced end to end against this
ticket's own new code (`createOrder`'s insert, `selectEligibleOrders`'s
predicate, `credit_order_if_eligible`'s SQL), not asserted: one
unauthenticated POST, repeatable without bound, mints real loyalty-point
value with a 24h delay and no further attacker action. Secondary, lower-
confidence consequence of the identical gap: a guessed/leaked real
`cw_order_id` lets the same unauthenticated caller force early completion
or wrongful cancellation of that real order. Full exploit chain, the fix
specified, and the full OWASP walk: this ticket's own board-file log,
security-gate round 1.

**Severity: Critical.** Zero authentication, unbounded, directly
monetizable (real ledger value, not a spam/reputation risk), reachable
with a single crafted HTTP POST and zero timing race or privileged
credential.

**Not accepted on the ticket's own account.** The build hop's own log
states the webhook signature gap is "confirmed pre-existing... and
explicitly out of this ticket's scope per the design's own 'no auth-model
change'" — true that it predates this ticket, but the design's Risks
section never actually examines the webhook's own trust boundary, and
`ENG-048`'s own security gate had already forward-noted this exact
question for this gate to answer ("only true if `ENG-049`'s handler
actually authenticates the inbound webhook"). Principal-engineer's round-1
review did not treat it as blocking either — this is squarely this gate's
own catch, not a re-derivation of what either already found.

**Same shape as `ENG-038` security-gate round 1, Finding 1** (2026-09-04,
this notebook): a pre-existing, already-known unauthenticated bypass
(`outgoing-communications`'s `systemTriggered` flag there) that a *new*
ticket's own added capability turns from a standing nuisance into a live,
unbounded abuse path. Blocked the same way there, fixed in the very next
hop — no reason for a different outcome here.

**Blocking `ENG-049`'s gate.** Fix specified in the ticket log: gate
`handleCloudWaitress` on the shared secret before any branching on
`webhookData.event` — covering `order_new` too, not only the three
terminal events this ticket adds, since gating only the terminal branch
leaves the sweep-mediated fabrication path fully open. Compare against the

registers (one shared constant, confirmed no per-restaurant variation);
401 + logged denial on mismatch, matching this same ticket's own

existing hardcoded literal to an env var is the separate, already-tracked
cleanup item (`README.md`'s "Known issues"), not blocking here.

Full detail: `agents/eng-manager/board/

**One new non-blocking finding: A02/A07-adjacent, low severity.**
`verifyCloudWaitressSecret`'s `provided === expected` is not a
constant-time comparison — in principle a timing side channel on the
secret. Not blocking: the real secret is a full UUID (~122 bits) compared
over a public HTTP round trip, where network jitter dwarfs a single-
character V8 string-compare delta, and CloudWaitress's own webhook contract
already sends the secret in-band in the body rather than as an HMAC-signed
header, so this fix authenticates against the mechanism the integration
actually has. Fix, if picked up next time this function is touched: a
constant-time compare (fixed-length HMAC or byte-by-byte with no early
return). Specific to this one function, not a systemic pattern — not filed
as a proposal.
