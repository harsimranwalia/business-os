# Security review — ENG-015

## Threat model

1. **What new input can an attacker control?** Nothing new. A partner-role
   (`partner-admin`/`partner-user`) caller already reached
   `GET`/`PUT /admin-portal/restaurants[/:id]` and the direct-client INSERT
   from `AddRestaurantModal.tsx` before this diff. What changes is that the
   caller's implicit claim to a given `restaurant_id`/`brand_id`, and the
   `approved` field on a write, are no longer trusted at face value on the
   two functions this diff adds a server-side check to
   (`getRestaurantById`, `updateRestaurant`) and the one path whose
   enforcement point moves from nothing to RLS (the INSERT).
2. **What new capability does this grant, and to whom?** None granted — this
   diff *revokes* a capability. A partner previously saw and could fetch/
   update every restaurant on the platform (`getRestaurants`/
   `getRestaurantById`/`updateRestaurant` all ran on the unconditional
   service-role client with no role branch); now scoped to their own
   brand(s). The one thing partners gain that didn't work at all before is a
   functioning add-restaurant path — explicitly held for staff review
   (`approved: false`), matching AC5, not an auto-approved create.
3. **What new data does this expose, and to whom?** None — this diff
   narrows exposure (it is the fix for the P1 cross-tenant leak the ticket's
   own Problem section names). No new field, join, or response shape is
   added anywhere in the diff.
4. **What breaks if this component is fully compromised?** A compromised
   partner-role session is now bounded to that partner's own brand(s) for
   read/update, and can insert only a held-for-review row under a brand it
   owns — a bounded blast radius, against the pre-diff state of platform-
   wide read/write reach via the unconditional service-role client on two of
   three functions, plus a totally broken (silently-rejected) insert path.

## Findings — both non-blocking

1. **A01-adjacent: RLS activation on `public.restaurants` is unverified
   from this repo — a layer beneath what QA's/review's own traces already
   covered.** No migration in tracked history creates `public.restaurants`
   or runs `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` on it — checked both
   directly (`grep -rnE "ALTER TABLE (public\.)?restaurants\b"` and the
   equivalent `CREATE TABLE` search across every migration file in the
   repo: zero matches for either). The table predates tracked migration
   history entirely — the same untracked-schema-history gap `ADR-006`/the
   PRD already name for `brands`/`profiles`/`influencers`, now specifically
   at the RLS-toggle level for `restaurants`, one level beneath the
   policy-content trace QA already ran. If RLS were somehow not enabled on
   this table, none of its policies — old or new, including this ticket's
   own `INSERT` guard — would be enforced at all.

   **Not asserted as a live defect.** This table's own migration history
   (three separate 2025-08-14 migrations progressively locking down public
   `SELECT`, ending in a `USING (false)` policy and a dedicated
   `restaurants_public` view for safe public reads) is very difficult to
   explain unless RLS has been active and enforced throughout — that
   hardening effort would be theatre with no effect otherwise — and nothing
   in this business's history (`observations.md`, prior security notebook
   entries) suggests a "whole table publicly readable" incident ever
   surfaced. No live Postgres/Supabase session was reachable this pass to
   check `pg_class.relrowsecurity` directly — the same standing gap named
   on every other hop of this ticket; the one linked `supabase` CLI session
   on this host points at an unrelated project, not `aiorders-api`'s own
   (`bmnmnejwdxbcqinqkwko`), and was left untouched rather than probed
   further.

   **Not blocking:** low likelihood per the reasoning above, pre-existing
   regardless of this diff (not introduced or worsened by it), and not
   something a code change in this ticket could safely fix blind — adding
   `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` defensively to the new
   migration was considered and rejected here, since it would be a
   platform-wide, unbounded-blast-radius change (every direct-client caller
   across all four frontends touching `restaurants`, not only this
   ticket's own surface) made with no visibility into whether anything
   currently depends on RLS being off. That is exactly the kind of silent
   scope expansion this instance's own practice avoids (the same reasoning
   that kept `updateBrandOwner()` out of this ticket entirely).

   **Recommendation — sharpens QA's own already-planned manual smoke test
   rather than adding a new one:** the staging verification QA already
   recommended should include a direct attempt to insert or update a
   restaurant as a test partner account and confirm the row is actually
   rejected or lands held, never unrestricted. That one check empirically
   proves the whole chain — RLS enabled *and* policy-correct — at once,
   without touching schema RLS toggles blind.
