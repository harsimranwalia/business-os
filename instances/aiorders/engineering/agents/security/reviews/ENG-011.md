# Security review — ENG-011

## Threat model

1. **What new input can an attacker control?** None, server-side. `stage`
   and `health` are new *output* fields on the existing, already-gated
   `GET admin-portal/brands` route — no new query parameter, no new body
   field, no new route. The stage filter (`stageFilter`) is entirely
   client-side state in `Brands.tsx`, filtering data already fetched and
   already authorized; it never becomes a server-bound parameter.
2. **What new capability does this grant, and to whom?** None. Whoever
   could already call `GET admin-portal/brands` (gated by
   `getAllBrands`'s existing `auth.user.profile.role === 'admin' ?
   adminSupabase : supabase` split, unmodified by this diff) sees two
   more fields per row they could already see the row for. No caller
   gains access to a brand they couldn't already see.
3. **What new data does this expose, and to whom?** `stage` is derived
   from `is_active`/`onboarding_step` — columns already present on the
   same row the caller already receives (`select('*')`, unmodified).
   `health` is derived from `calculate_platform_analytics()`'s aggregate
   (order count/value/recency) — business-internal, revenue-adjacent,
   not customer PII and not payment-instrument data, exposed only to the
   same admin/sub-admin/partner tier that already sees this list and
   (per `ENG-007`'s own precedent finding) already sees restaurant
   financials via `billing.ts`/`analytics`.
4. **What breaks if this component is fully compromised?** A compromised
   admin/sub-admin token could already read the full brand list and its
   existing fields; this ticket adds two derived, read-only fields to
   that same response. No new write path, no new deletion path, no new
   privilege. Blast radius is unchanged from today.

## Negative / degraded-auth cases, traced rather than assumed

Read `brands.ts` end to end for this diff's own surface (not the whole
file — the other routes are untouched):

| Case | Behaviour | Where |
|---|---|---|
| Caller not authenticated | Unchanged — `index.ts`'s existing gate handles this before `handleBrands` is ever reached; this diff adds no code upstream of it | pre-existing, out of this diff |
| Caller authenticated but lower-privilege (e.g. partner/reseller) | Unchanged — `getAllBrands`'s existing `role === 'admin' ? adminSupabase : supabase` client selection is untouched; whatever row set that already returned for a given role, it still returns, now with `stage`/`health` attached to the same rows | `admin-portal/handlers/brands.ts`, pre-existing branch, not modified by this diff |
| KV read fails, times out, or returns a non-2xx/404 | `readBrandAnalytics` catches every case and returns `null`, logged server-side via `console.error` (no stack trace or credential in the log line) — the row still returns with `health: 'no_data'`, the request never fails or 500s because of this new dependency | `analytics-kv.ts` |
| `CF_ACCOUNT_ID`/`CF_ANALYTICS_KV_ID`/`CF_API_TOKEN` unset in this environment | `getKVConfig()` returns `null` rather than throwing; every brand reads `no_data` — a missing optional integration degrades the response, it doesn't fail it | `analytics-kv.ts` |
| A brand row with `onboarding_step: null` or a stage/health value outside the known set | Both pill renderers (`getStagePill`/`getHealthPill`) have a `default` branch rendering a plain `-` — no unhandled-case crash on the frontend | `Brands.tsx` |

## Secrets

Scanned both diffs (`git diff origin/main HEAD`, both repos) for
key/secret/token/password/bearer/PEM patterns: the only hit is the
pre-existing `apikey` literal inside the standard CORS
`Access-Control-Allow-Headers` string — not a credential. `analytics-kv.ts`
reads `CF_ACCOUNT_ID`/`CF_ANALYTICS_KV_ID`/`CF_API_TOKEN` from `Deno.env`
only, the same three names `cloudflare-kv.ts` already uses — no new
secret introduced, no value hardcoded anywhere in either diff.

## PII handling

No new PII surface. `stage` reflects onboarding/activation state (business
process data, not customer data); `health` reflects order-volume/recency
aggregates (business-internal, revenue-adjacent). Data classification:
**Internal** per `security-baseline.md`'s table — same tier `ENG-007`'s
review assigned to loyalty rate data. No restriction beyond the existing
admin/sub-admin/partner gate is warranted, and none is loosened by this
diff.

## Verdict: PASS

No exploitable vulnerability, no access-control gap, no secret, no
injection surface, no new SSRF risk (outbound target is
caller-uncontrolled). Every new failure path degrades to a safe,
already-designed-for state (`no_data`, a rendered `-`) rather than an
error or a crash. The two items carried forward (A04's fan-out, the
no-live-verification gap) are both non-blocking and neither is a defect
this diff introduces beyond what's already true of the systems it
extends.
