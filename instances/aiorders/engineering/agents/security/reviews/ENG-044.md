# Security review — ENG-044

## Threat model

1. **What new input can an attacker control?** `p_channel text default null`
   on `get_restaurants_optimized`, a function already granted to `anon` (this
   grant is pre-existing and unchanged — confirmed against the original,
   below). Free text, same as the function's other pre-existing filter
   parameters (`p_city`, `p_search`, `p_cuisines`, `p_price_levels`,
   `p_services`); no new class of unvalidated input, an addition to a
   function that has never enum-validated any of its text/array filters.
2. **What new capability does this grant, and to whom?** None. The parameter
   only narrows the existing result set further via an `AND`-ed predicate —
   it cannot be used to see more than the pre-existing
   `approved = true and show_in_marketplace = true` gate already allows.
   Read the actual `WHERE` clause to confirm this rather than trusting the
   ticket's account of it (see A01 below).
3. **What new data does this expose, and to whom?** `opening_hours` (`jsonb[]`)
   is added to `RETURNS TABLE`, to the same `anon`/`authenticated` audience
   already reading name/address/rating/etc. from this public discovery
   endpoint. Restaurant operating hours are not PII and are already
   client-visible on the detail page — no new audience, no new data class.
   The three new boolean columns themselves (`has_order_food`/`has_dine_in`/
   `has_catering`) are used only inside the `WHERE` clause and are **not**
   added to `RETURNS TABLE` — nothing new is returned from them directly.
4. **What breaks if this component is fully compromised?** Unchanged from
   today: the function runs `SECURITY INVOKER` (no `SECURITY DEFINER` in
   either the original or this version), so a compromised `anon`/
   `authenticated` role gets exactly what that role could already reach
   through this function and RLS — this diff adds a filter, not a new
   privilege boundary.

## Verified directly, not taken on the ticket's word

- **The channel gate can only narrow, never widen, visibility.** Read
  `20260907120001_...sql`'s `WHERE` clause directly: `p_channel`'s
  three-branch `OR` is one more `AND`-ed condition alongside
  `r.approved = true`, `r.show_in_marketplace = true`, and every other
  existing filter — it cannot short-circuit or replace them. This is the
  A01-relevant property of this diff, and it's true by the query's own
  structure, not by convention.
- **Port fidelity, independently re-diffed.** Pulled
  `restaurant-marketplace`'s real `20240302_optimize_restaurant_discovery.sql`
  from that repo's own worktree and compared it directly against this
  migration's ported function body: identical column list, identical
  Haversine block, identical CTE structure, identical `ORDER BY`/`LIMIT`/
  `OFFSET` — the only differences are the two stated additive ones
  (`p_channel` appended last, `opening_hours` appended last to
  `RETURNS TABLE`) plus the channel predicate itself. Confirms the
  principal-engineer review's own "byte-for-byte" claim rather than
  accepting it.
- **`DROP FUNCTION IF EXISTS` signature matches the true original exactly** —
  13 positional types, same order, confirmed against the same source file
  just re-read. This is what prevents the overload-coexistence defect
  `database`'s own testing found (a bare `CREATE OR REPLACE` with a changed
  arg count creates a second overload instead of erroring, leaving old
  callers on a stale, ungated function forever) — re-confirmed here as its
  own independent check, not inherited from the review's account of it.
- **`grant execute on function public.get_restaurants_optimized to anon,
  authenticated, service_role`** matches the original grant list verbatim
  (`GRANT EXECUTE ... TO anon, authenticated, service_role` in the 2024
  source). `DROP FUNCTION` drops grants with it, so re-issuing the identical
  grant after `CREATE OR REPLACE` is what keeps this a public discovery
  endpoint rather than silently narrowing or widening who can call it. No
  privilege escalation, no accidental lockout.
- **No dynamic SQL anywhere in the function.** `p_channel` is compared with
  native `=` inside a `plpgsql`/CTE query, the same parameter-binding pattern
  every other filter on this function already uses — no `EXECUTE`, no
  `format()`, no string concatenation into a query. An out-of-enum
  `p_channel` value makes all three `OR` branches false and returns zero
  rows; it cannot error, leak a distinguishable message, or reach a
  different code path.
