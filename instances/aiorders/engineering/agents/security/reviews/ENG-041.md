# Security review — ENG-041

## Threat model

1. **What new input can an attacker control?** No new *unauthenticated* input.
   The questions page adds a read (`ai_conversations`, scoped to
   `currentRestaurant.id`); the FAQ tab adds a UI source for text already
   reachable by the owner (their own customers' chat questions) that gets
   carried, pre-filled, into the same `content.faqs` write `ENG-040` already
   reviewed. The one new *shape* of input is free text that originated from an
   anonymous customer rather than the owner's own typing — but the owner reads
   and can edit it before anything saves, so the trust boundary crossed is
   still "authenticated owner submits this text," unchanged from `ENG-040`.
2. **What new capability does this grant, and to whom?** A restaurant
   owner/manager can now *see* their own restaurant's chat-bar questions in
   the portal (previously true only via direct DB/RLS access, not surfaced in
   any UI) and can turn one into an FAQ with one click instead of retyping it.
   No new class of principal, no new write capability beyond what `ENG-040`
   already granted.
3. **What new data does this expose, and to whom?** Customer-submitted chat
   questions, to the exact principal RLS already authorizes for that
   restaurant (`user_has_restaurant_access` → `restaurant_managers`) — not a
   new audience, a new UI surfacing existing authorized access.
4. **What breaks if this component is fully compromised?** A compromised
   `restaurant-portal` session for owner O could read O's own restaurant's
   chat questions (already-authorized data for that principal) and write
   arbitrary FAQ text to O's own restaurant's public site — both already true
   before this ticket via other tabs/routes. No cross-tenant escalation: both
   enforcement points (RLS on the read, `requireRestaurantAccess` on the
   write) are unchanged by this diff and independently re-confirmed below.

  logged.
- **Only the customer's own turns rendered, never the assistant's.**
  `flattenSession` skips any element where `role !== 'user'` — read directly.
- **No export path.** Confirmed by reading the full diff — no download/copy/
  export control exists anywhere in `questions/Index.tsx`.
- **Nothing persisted until the owner explicitly saves.** The hand-off is
  pure in-memory `react-router` state, cleared on consume
  (`navigate(location.pathname, { replace: true, state: null })`); the text
  only reaches `restaurant_website.faqs` (and from there the public site,
  schema.org markup, and the bot's context) if the owner reviews the
  pre-filled draft and presses "Save FAQs." This human-in-the-loop step is
  the actual control standing in for redaction, which is an explicit PRD
  non-goal per `ADR-014` — a considered, already-recorded position, not
  re-litigated here.
