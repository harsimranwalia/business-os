## Threat model (re-run against this round's diff only)

1. **What new input can an attacker control?** Less than before this fix, not
   more. Pre-fix, every field of the CloudWaitress payload was attacker-
   controlled on a route with no caller check at all. Post-fix, the same
   fields are only ever reached if `webhookData.secret` matches
   `CLOUDWAITRESS_WEBHOOK_SECRET` — a value the attacker does not have and
   cannot derive from the response (a mismatch returns a fixed `401
   Unauthorized`, no timing or content signal about which part was wrong).
2. **What new capability does this grant, and to whom?** None — this is a
   capability *removal*. Before: any caller, unauthenticated, could reach
   `createOrder`/`handleTerminalOrderEvent`. After: only a caller who holds
   the shared secret can.
3. **What new data does this expose, and to whom?** None. No new read path.
4. **What breaks if this component is fully compromised?** Unchanged in kind
   from round 1's own analysis: if `CLOUDWAITRESS_WEBHOOK_SECRET` itself
   leaks, a holder can still run the exact exploit chain round 1 traced. That
   residual is inherent to CloudWaitress's own webhook design (a shared
   secret carried in the payload, not an HMAC-signed header) — confirmed by
   reading `cloudwaitress-middleware/handlers/restaurant.ts`'s own
   registration shape, unchanged by this diff and out of this ticket's
   scope to redesign. What this fix removes is the *unconditional* path;
   secret-leak is a different, pre-existing risk category (credential
   handling), not a gap in this fix.

## Read against the finding it fixes — verified by reading the code, not by the tests passing

- **Placement matches the finding's own requirement exactly.** The finding
  required the check "before any branching on `webhookData.event`," because
  gating only the terminal branch would leave `order_new` — the actual
  fabrication path — open. Read `handleCloudWaitress` directly:
  `verifyCloudWaitressSecret(webhookData)` sits immediately after

  rather than silently accepting everything. Verified via its own dedicated
  test, re-run by me (below), not just read.

  named `cloudwaitress-middleware/handlers/restaurant.ts`'s existing

  `git show 0bec87c` for it, zero hits outside the JSDoc's own prose
  reference.
- **No secret leakage in the fix itself.** `console.warn` on a mismatch logs
  `event: ${webhookData?.event ?? 'unknown'}` only — read the exact call

## Findings — non-blocking

1. **A02/A07-adjacent, low severity: the secret comparison is not
   constant-time.** `cloudwaitress.ts`, `verifyCloudWaitressSecret`:
   `return provided === expected;` is a standard JS string equality check,
   which short-circuits on the first mismatched byte — in principle a timing
   side channel an attacker could use to recover the secret one byte at a
   time. **Why this doesn't block:** the real secret is a full UUID
   (`cloudwaitress-middleware`'s `AIORDERS_WEBHOOK.secret`,
   ~122 bits of entropy), the channel is a public HTTP round trip (network
   jitter is orders of magnitude larger than a single-character V8 string-
   compare timing delta), and CloudWaitress's own webhook contract already
   sends the secret in-band in the request body rather than as an
   HMAC-signed header — this fix authenticates against the mechanism the
   integration actually has, and a constant-time compare narrows an
   already-impractical channel rather than closing an open one. **Fix, if
   picked up:** swap to a constant-time comparison (e.g. compare
   fixed-length HMACs of both values, or a `timingSafeEqual`-style
   byte-by-byte compare with no early return) the next time this function is
   touched. Not filed as a proposal — it's specific to this one function, not
   a systemic pattern across the project, and `eng_build_loop.md` step 3
   reserves `proposals.md` for the latter. Logged here and in
   `agents/security/notebook/2026-09-07-findings.md` only.
