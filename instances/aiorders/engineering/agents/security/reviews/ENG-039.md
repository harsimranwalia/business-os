## Threat model

1. **What new input can an attacker control?** Nothing beyond what `ENG-038`'s
   gate already accepted. This diff adds no new endpoint — every one of its 8
   API calls (`list/get/create/update/pause/resume/cancel_broadcast`,
   `get_broadcast_report`) reaches an action that already exists, unchanged,
   on the already-reviewed backend. The frontend adds client-side state (form
   fields, drip-step content) an owner controls, but all of it is submitted to
   a backend that validates and authorizes independently, ignoring the
   client's own opinion of whether the form was "valid."
2. **What new capability does this grant, and to whom?** A UI surface for a
   capability that already existed at the API layer since `ENG-038` shipped.
   No new actor gains access to anything — an owner who could already call
   `create_broadcast` via a raw HTTP request can now do the same thing through
   a form. The set of people who can reach this at all is exactly the set
   `requireRestaurantAccess` already admits: a real, authenticated user with
   access to that specific restaurant.
3. **What new data does this expose, and to whom?** None beyond what
   `get_broadcast`/`get_broadcast_report`/`list_broadcasts` already return to
   an authorized caller (`ENG-038`'s own reviewed surface). `BroadcastReport.tsx`
   renders recipient counts, delivery-by-channel, and coupon
   redemptions/revenue — all already scoped server-side to the requesting
   restaurant; nothing here widens that.
4. **What breaks if this component is fully compromised?** A compromised
   browser session (XSS, stolen token) already has whatever access the
   underlying user session grants. This diff introduces no new sink (see A03)
   that would let a compromised *client* reach further than a compromised
   session already could, and introduces no new secret or credential of its
   own to steal (see Secrets, below).
