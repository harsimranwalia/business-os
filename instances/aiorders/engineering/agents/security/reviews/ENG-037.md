# Security review — ENG-037

## Threat model

1. **What new input can an attacker control?** None. This diff is one
   migration file: three `create table if not exists`, five indexes, one
   trigger, three `enable row level security` (zero policies each), one
   `cron.schedule`. No endpoint, handler, or parser anywhere in this repo
   reads or writes any of the three new tables yet — confirmed fresh this
   pass, not taken on trust from QA's/review's own accounts:
   `grep -rln "broadcast_campaign" supabase/functions/` returns zero hits.
   The cron job's own SQL body has no attacker-reachable input either: the
   URL is a literal, the body is a literal `{}`, and the only value the
   `Authorization` header depends on is a Vault secret read by fixed name.
2. **What new capability does this grant, and to whom?** Practically none
   yet. All three tables ship with RLS enabled and zero policies — Postgres
   denies `anon`/`authenticated` entirely in that state, confirmed live
   this ticket's own build hop (`relrowsecurity = t` on all three, direct
   query against a disposable replica), matching `api_keys`' own
   service-role-only convention. Only a service-role credential — which
   already bypasses RLS everywhere on this project — can reach them; not a
   new capability. The cron job registers a recurring outbound call, but it
   is a no-op today two ways over: the tables it would act on are empty,
   and the Vault secret its header depends on (`service_role_key`) does not
   exist yet (`SELECT name FROM vault.secrets`, names only, build hop) — so
   every tick's header evaluates to a null bearer and 401s even once
   `ENG-038`'s target function exists.
3. **What new data does this expose, and to whom?** None. No rows exist
   pre-`ENG-038`, and RLS-with-zero-policies denies direct client access
   even once rows do. `offer_id`/`customer_id`/`restaurant_id` are foreign
   keys to existing identity, not new PII columns.
4. **What breaks if this component is fully compromised?** No change from
   today — same reasoning `ENG-031`'s own review used: a compromised
   service-role credential already has full read/write on this database;
   two more service-role-only tables and one more scheduled outbound call
   add nothing to that blast radius.
