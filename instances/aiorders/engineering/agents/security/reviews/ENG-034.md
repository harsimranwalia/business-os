# Security review — ENG-034

## Threat model

1. **What new input can an attacker control?** `selections` (category, item_id,
   name, quantity, note) via the picker UI, and which of the two buttons fires
   (`action_type`). Neither is a new field at the trust boundary: both are
   exactly the shape `ENG-033`'s already-reviewed, already-shipped
   `catering-request` validates and accepts from any HTTP client, gate closed
   or not. This diff is the client that constructs that payload by clicking
   rather than by hand-crafted request — it adds no field, endpoint, or
   validation-relevant surface of its own. `email` becoming required is a
   behaviour change, not a new attacker capability.
2. **What new capability does this grant, and to whom?** None beyond what
   `ENG-033` already granted. A raw POST to `catering-request` carrying
   `action_type`/`selections` was already possible the moment that ticket
   shipped; nothing here raises the authority of an anonymous site visitor.
3. **What new data does this expose, and to whom?** None to a new audience.
   The menu is already public via the menu page (`MenuList.tsx`), and
   `config.catering.*` is already part of this site's own public page config.
   Confirmed no new fetch/network call exists anywhere in this diff (`git
   diff origin/main...HEAD` — zero `fetch`/`supabase`/`axios` additions):
   `CateringMenuSelector` is purely presentational over props already
   delivered to the page.
4. **What breaks if this component is fully compromised?** No change from
   today. This is an anonymous marketing site with no session of its own; a
   compromised build already has exactly the authority any visitor's browser
   has, which is none beyond what an unauthenticated POST already carries —
   same answer `ENG-032`'s review gave for the same repo family.
