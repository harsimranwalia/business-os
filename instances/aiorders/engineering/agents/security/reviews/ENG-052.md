# Security review — ENG-052

## Threat model

1. **What new input can an attacker control?** `redeem_points_if_eligible(p_platform_customer_id
   uuid, p_restaurant_id uuid, p_points numeric, p_idempotency_key text,
   p_created_by uuid)` takes five parameters, but post-migration `EXECUTE` is
   restricted to `service_role` (verified below) — no `anon`/`authenticated`
   caller can invoke it directly. The real attacker-facing input is whatever
   `ENG-053`'s not-yet-built `brand-portal` handler accepts from a client and
   forwards as `p_platform_customer_id` (the redemption code) — explicitly
   out of this ticket's own scope (Notes, AC ownership) and flagged forward
   below.
2. **What new capability does this grant, and to whom?** `service_role`
   gains the ability to debit a diner's per-restaurant loyalty balance via
   one guarded function. No capability is granted to `anon`/`authenticated`.
3. **What new data does this expose, and to whom?** None. `loyalty_ledger_entries`
   already exists (`ENG-027`/`ENG-048`), RLS-enabled, zero policies — this
   migration doesn't touch RLS, confirmed still deny-by-default below. The
   new `idempotency_key` column is caller-supplied, not secret or PII.
4. **What breaks if this component is fully compromised?** Bounded by the
   function's own guards even under a compromised `service_role`: the
   per-`(diner, restaurant)` advisory lock, the idempotency check, and the
   balance read all live inside the one function, so the worst a malicious
   `service_role` caller could do is what any legitimate caller already
   can — debit a real diner's real balance at a real restaurant, an
   existing, project-wide risk this ticket neither introduces nor worsens
   (same position `ENG-048`'s own review took for `credit_order_if_eligible`).
   The design's own Risks section separately names the redemption *code*
   itself (`platform_customer_id`) as a bearer credential — unchanged by
   this ticket, carried from the PRD, and not this ticket's own surface to
   fix (see "Flagged forward" below).

## Verified directly, not taken on the ticket's, code review's, or QA's word

Independently reproduced from scratch — own fixture (not the one on file at
`agents/database/migrations/ENG-052-....md`), own disposable container
(`public.ecr.aws/supabase/postgres:15.8.1.073`, same image every prior
verification on this ticket sequence used), the real migration files applied
unmodified via `psql -f` (`20260829130000`, `20260907130000`, then this
ticket's own `20260908160000` — no edits, no shortcuts):

- **Confirmed the `pg_default_acl` mechanism itself before applying anything**,
  same discipline `ENG-048`'s own gate set: this image's `public` schema
  carries a function-object (`defaclobjtype = 'f'`) default-ACL entry naming
  `anon`, `authenticated`, and `service_role` directly with `EXECUTE` at
  function-creation time — independent of the `PUBLIC` pseudo-role, which is
  why a bare `revoke ... from public` doesn't close it project-wide.
- **`has_function_privilege` for all four roles, post-migration:**
  `anon → false`, `authenticated → false`, `service_role → true`,
  `postgres → true`.
- **Went past the catalog read: attempted the actual RPC as both roles.**
  `set role anon; select redeem_points_if_eligible(...)` and the same as
  `authenticated` both fail with a real `ERROR: permission denied for
  function redeem_points_if_eligible` — not inferred from the grant table.
  `set role service_role` executes normally throughout.
- **`security definer` hardening:** `set search_path = 'public'` confirmed
  pinned at the catalog level (`pg_proc.proconfig = {search_path=public}`,
  not just textually present in the source), and every table reference
  inside the body is schema-qualified regardless — belt-and-suspenders
  against a search-path hijack, same standard `ENG-048`'s function was held to.
- **RLS unaffected:** `loyalty_ledger_entries` still `relrowsecurity = t`,
  zero rows in `pg_policies` — this migration doesn't touch RLS, confirmed
  rather than assumed.
- **Idempotency-before-balance-read ordering, the design's own load-bearing
  claim:** replaying the same `idempotency_key` after a successful redemption
  returns `redeemed` again with **zero** new rows for that key (count query,
  not the return value alone) — a genuine retry doesn't get charged twice
  regardless of the balance at replay time.
- **Idempotency-conflict guard:** the same key reused for a different points
  amount raises a real error (`idempotency_key ... already used for a
  different request`), not a silent success at the wrong amount.
- **Both input guards:** `p_points = 0` and `p_idempotency_key null` each
  raise a real error, not a silent no-op.
- **Sub-cent precision fix, the regression this ticket's own build hop
  introduced a fix for:** a restaurant configured at
  `redemption_value_per_point 0.0025` produces a stored `rate_applied` of
  `0.0025`, not `0.00` — reproduced against the actual widened column
  (`numeric(10,4)`), not asserted.
- **Exact-balance boundary:** a redemption request equal to the diner's full
  balance succeeds (`redeemed`), balance reads back as exactly `0.0000`
  afterward — confirms "exceeds" is `<`, not `<=`.
- **`not_enrolled` / `invalid_code`:** a restaurant with no
  `restaurant_loyalty_configs` row, and a nonexistent
  `platform_customer_id`, each return their own distinct sentinel rather
  than a raw constraint error.
- **All four per-source `CHECK`s, both directions, real inserts:** a
  positive-points `redemption` row rejected; a negative-points `online_order`
  row also rejected (the new sign check binds the pre-existing sources too,
  not just the new one); a `redemption` row with null `created_by` rejected
  (the audit-trail arm); two `redemption` rows with null `idempotency_key`
  coexist (nullable-safe unique, confirmed `count = 2`).
- **`rate_applied` backward compatibility:** a pre-existing-style
  `online_order` row (`5.00`) reads back as `5.0000` — the widening changes
  representable range, not stored value.
- **Secrets — diff and full branch history.** One commit, 267 insertions / 0
  deletions (diffstat confirmed), so the final file is the whole history for
  this path. Grepped
  `key|secret|password|token|bearer|AKIA|BEGIN (RSA|EC|PGP|OPENSSH)|api[_-]?key`
  over `git log origin/main..HEAD -p`: zero matches — no constraint-name false
  positives even, unlike `ENG-048`'s own scan.

  left running (`docker ps -a --filter name=eng052-sec` empty).

## Findings

None blocking.

**Flagged forward for `ENG-053`'s own security gate** (same mechanism
`ENG-048`'s gate used to flag `ENG-049`, not a gap in this ticket):

1. **A01 — the wrong-tenant case lives at the handler, not here.** Confirm
   `requireRestaurantAccess` (or equivalent) actually gates which
   `restaurant_id` a staff member's request may name before it ever reaches
   `redeem_points_if_eligible` — this function trusts `p_restaurant_id`
   completely, by design, because authorizing the caller is explicitly this
   ticket's sibling's job (this ticket's own Notes, AC ownership).
2. **A04 — the redemption code is a bearer credential, unchanged by design
   (design's own Risks, carried from the PRD).** Whoever presents
   `platform_customer_id` can have it redeemed against; nothing in
   `ENG-053`'s scope is expected to change that (the PRD's own accepted
   tradeoff, `ADR-022`), but the handler should not *widen* the exposure —
   e.g. logging the raw code somewhere it doesn't already appear, or
   returning it in a response body beyond what QR issuance already does.
3. **Pre-existing, not from this diff:** `loyalty_ledger_entries` still has
   no database-level protection against `UPDATE`/`DELETE` by a future
   `service_role` code path (open proposal, principal-engineer, 2026-09-07).
   This ticket adds a second write path to the same table rather than the
   first — strengthens the case for that proposal, doesn't newly create the
   gap, and isn't this ticket's own scope to fix.
