# Security review — ENG-004

## What this reviews

Per `ADR-004`, this ticket produces no diff — the remediation it investigated
was already executed by the approver directly, on `origin/main` in both
repos, on 2026-08-24. Review and QA (`agents/principal-engineer/reviews/ENG-004.md`,
`agents/qa/test-plans/ENG-004.md`) already independently re-confirmed all
five acceptance criteria against disk/git, including byte-identity of the six
named files via a fresh SHA-256 hash. **What neither of those gates checked,
and what `ADR-004` reserves for this one, is the content itself** — whether
the RLS/`search_path` hardening the six files carry is actually coherent
security hardening, not just an unchanged blob. Ceremony here would be
re-running the same hash check a third time; the substantive version is
reading what the SQL does.

## Threat model

1. **What new input can an attacker control?** None. The six files are
   pre-existing, already-applied migrations; this ticket introduces no new
   code, route, or endpoint in either registered project.
2. **What new capability does this grant, and to whom?** None beyond what
   was already live before this ticket existed.
3. **What new data does this expose, and to whom?** None from this ticket.
   The six files' own effects (RLS on `profiles`/`restaurants`, the
   `restaurants_public` view, `restaurant_activations`) were already live
   before, during, and after the deletion and its resolution (design,
   Regression risk).
4. **What breaks if this component is fully compromised?** Not applicable in
   the usual sense — there is no runtime component belonging to this ticket.
   The equivalent question for a history-reconciliation ticket is what breaks
   if the *tracked* history is wrong: a from-scratch replay that silently
   omits hardening, or restores it out of order. AC3/AC4 are exactly that
   question, re-checked below.

## Content review — the hardening itself

What each of the six files actually does, read directly off `aiorders-api`'s
`origin/main`:

1. **`20250729143432_updated_at_functions.sql`** — pins `SET search_path =
   'public'` on two `SECURITY DEFINER` trigger functions
   (`update_updated_at_column`, `update_ai_updated_at`). Standard, correct fix
   for a mutable-search-path `SECURITY DEFINER` function. Intact.
2. **`20250814063528_...`** — removes two unconditional public-read policies
   on `profiles` (any role could read every row), replaces with owner-only
   (`auth.uid() = id`) plus an admin-role check. The admin check queries
   `profiles` from inside a policy defined *on* `profiles` — a
   self-referential pattern that is itself the defect the next migration
   fixes. Intact as originally written; not a regression introduced by this
   ticket's reconciliation.
3. **`20250814064923_...`** — fixes the infinite-recursion defect via a
   `SECURITY DEFINER STABLE` helper, `get_current_user_role()`, and rewrites
   the admin policy to call it instead of querying `profiles` directly.
   Intact. This function does not yet pin `search_path` — closed two
   migrations later (item 5).
4. **`20250814065439_...`** — removes unconditional public read access to
   `restaurants` (`USING (false)` blocks all direct access), replaces it with
   a `restaurants_public` view exposing an explicit safe-column allowlist
   filtered to `approved = true`; the migration's own comment names what it
   excludes (API keys, credentials, Stripe info). Intact.
5. **`20250814065606_...`** — recreates `restaurants_public` and adds the
   `search_path = public` pin to `get_current_user_role()` that item 3 was
   still missing. Intact.
6. **`20260312000001_restaurant_activations.sql`** — new table, RLS enabled
   on creation, single policy scoped `TO service_role` only (`USING (true)
   WITH CHECK (true)`) — correctly *not* granted to `anon`/`authenticated`,
   appropriate for a table only edge functions touch. Intact.

All six read as coherent, complete hardening, consistent with the original
request's own characterization, and — per the blob-hash match above —
unchanged from what was live in `admin-hub` before deletion.

## Out of scope, named rather than silently skipped

The PRD's own non-goals are explicit: *"Does not re-verify or change RLS
policy logic itself beyond restoring what the six files specify — auditing
whether that policy is still the right policy today is a separate question
this ticket doesn't take on."* This review stays on the correct side of that
line — confirming the six files' hardening is present, unmodified, and
correctly ordered, not re-auditing whether every design choice inside them
is still ideal.

One thing noticed while reading item 5's content sits on the far side of
that line, so it is not filed as a finding against this ticket: its own
comment says the view is recreated "without SECURITY DEFINER (default is
SECURITY INVOKER)". Postgres's actual default for a plain `CREATE VIEW` (no
explicit `WITH (security_invoker = true)`, the PG15+ opt-in) is the reverse —
the view runs with the *owner's* rights against the underlying table's RLS,
not the querying role's — so this migration's comment may describe the fix
backwards, and the drop-and-recreate may not have changed the view's
actual RLS-bypass posture at all. This is a statement about whether a
~1-year-old, already-live migration's own comment is accurate, not about
anything this ticket's reconciliation could have broken, and evaluating it
further would mean auditing current policy correctness — the exact question
the PRD excludes. No DB credential is available to check Supabase's advisor
output directly either (design, Risks). Logged as an observation in
`agents/eng-manager/observations.md`, not a finding, and not blocking.
