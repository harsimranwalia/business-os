# Security review — ENG-008

## Threat model

1. **What new input can an attacker control?** `influencerId` (a URL path
   segment) and a JSON PATCH body carrying up to six named fields
   (`city_preference: string[]`, `accepts_paid`/`accepts_barter: boolean`,
   `min_visit_payment: number`, `staff_rating: 1–5 | null`,
   `collaboration_count: integer >= 0`) on two new routes,
   `GET`/`PATCH /admin-portal/influencers/{id}`. Both sit behind the
   router's existing bearer-token `authenticate()` (unmodified by this
   diff) and the handler's own admin/sub-admin role gate
   (`hasInfluencerAdminAccess`), checked once before either method branches.
2. **What new capability does this grant, and to whom?** Write access to
   four fields (two genuinely new columns — `staff_rating`,
   `collaboration_count` — plus two flags replacing a former single
   boolean) for callers already holding `admin`/`sub-admin` — the same
   population that could already read every influencer row via this same
   page (`select('*')`). Before this diff the entire Influencer Management
   page was 100% read-only, no save path anywhere; it is now read+write on
   six fields for the same audience that already read all of them.
3. **What new data does this expose, and to whom?** None of the four
   new/changed columns raises the classification tier of what admin/
   sub-admin already receives on this same `GET` (name, contact, social
   handles, engagement stats — all pre-existing). `staff_rating`/
   `collaboration_count`/`accepts_paid`/`accepts_barter` are internal
   business-process fields, the same class as `ENG-013`'s
   `foodswipe_stage_override`.
4. **What breaks if this component is fully compromised?** `adminSupabase`
   is a service-role client — RLS is bypassed entirely, the same
   architecture every other admin-portal handler already uses. The *only*
   access control on every read/write here is the two in-code role checks
   (`authenticate()`'s `hasAdminAccess`, then `hasInfluencerAdminAccess`). A
   compromised admin/sub-admin token, or a defect in either check, has full
   read/write over every influencer row — an integrity/business-data risk
   (a rating, preference, or tally could be forged), not a new
   confidentiality tier (that same token already reads full influencer PII
   today regardless of this diff) and not a new architecture: identical
   blast radius to `loyalty-config.ts`/`foodswipe.ts`, both already accepted
   at this gate.

## Verdict: PASS

Every new write is gated by a single, shared, already-correctly-scoped
role check with no per-method copy to drift, and the negative cases the
baseline requires (no-token, wrong-role, missing-profile) are either
directly tested with mutation-sensitive assertions or confirmed against an
existing, unmodified upstream control read fresh this pass. No IDOR — body
`id` is never used for row selection. No secret, no injection surface, no
new dependency, no elevation of privilege, no new data-classification tier.
The one new observation (raw error message on a 500) is low-severity,
copies rather than introduces an established repo pattern, and is tracked
for the three-strike rule rather than blocking a ticket that only extended
an already-accepted instance of it.
