# Security review — ENG-008 (round 3)

## Why this round exists

The approver rejected the redundant `accepts_barter` column on the merge
request ("no need for a new column when we already have a column to signify
the same intent"). The fix hop renamed every reference to the pre-existing
`barter_visit` column instead. Round 2's security verdict (2026-08-31,
`57f8c4b`/`63be255`) was for a diff this ticket no longer ships — this round
re-verifies against the revised diff rather than assuming the rename is
security-neutral.

## What changed since round 2 — read from the diff, not the fix hop's own account

Rename-only delta: `git diff 57f8c4b..HEAD` (`aiorders-api`, 3 files/20
lines) and `git diff 63be255..HEAD` (`aiorders-admin-hub`, 1 file/33 lines),
both read in full this pass.

- **`aiorders-api`**: `EDITABLE_FIELDS` swaps the literal `'accepts_barter'`
  for `'barter_visit'`; the PATCH validation block is renamed identically
  (`typeof body.barter_visit !== 'boolean'` → same shape, same rejection
  message pattern); the one dedicated test renamed in lockstep. Migration:
  the `accepts_barter` column and its half of the backfill are dropped
  entirely; `accepts_paid`'s backfill (`accepts_paid = NOT barter_visit`) is
  untouched; `barter_visit` itself is still never written by the migration.
- **`aiorders-admin-hub`**: the two interface fields collapse to one
  (`barter_visit: boolean | null` replacing both `barter_visit: boolean`
  and `accepts_barter: boolean | null`); every read/write site
  (`openInfluencer`, `handleSaveInfluencer`'s conditional-send, the Payment
  Type badge, the edit-dialog checkbox + its `id`/`htmlFor`) now targets
  `barter_visit` directly.
- **Not touched by this delta, confirmed by the diff's own file list**:
  `hasInfluencerAdminAccess`, the router's `authenticate()`, `index.ts`
  (CORS/routing — still just the round-2 `PATCH` addition), and every other
  `EDITABLE_FIELDS` entry. No auth logic, no new route, no new field, no new
  capability. **The surface actually shrinks**: round 2 reviewed "two new
  flags replacing one boolean"; this round is one new flag
  (`accepts_paid`) plus reuse of an existing, previously-read-only column —
  narrower than what round 2 already cleared, not broader.

**Consumers of `barter_visit` enumerated**, not assumed contained to this
diff: `git grep -n barter_visit` across both repos' full tracked trees.
`aiorders-api`: only `influencers.ts` (this handler) and the migration.
`aiorders-admin-hub`: only `Influencers.tsx` and the generated
`supabase/types.ts` (type declarations, no logic). No other handler,
campaign-matching logic, billing path, or automation reads or writes this
column — reusing it here creates no seam with code outside this ticket's own
diff.
