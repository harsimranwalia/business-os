# Security review — ENG-008

## Threat model

1. **What new input can an attacker control?** The `PATCH` body (six
   optional fields: `city_preference`, `accepts_paid`, `accepts_barter`,
   `min_visit_payment`, `staff_rating`, `collaboration_count`) and the
   `{id}` path segment on both `GET`/`PATCH
   /admin-portal/influencers/{id}`. Both require a valid Supabase session
   already verified by `admin-portal/index.ts`'s existing `authenticate()`
   middleware (unmodified by this diff — confirmed by diffing `index.ts`
   directly: the only changes are an import, one CORS methods string, and
   two routing lines) — no anonymous or unauthenticated path exists to
   either handler.
2. **What new capability does this grant, and to whom?** To a caller whose
   *server-derived* profile (`auth.user.profile`, built in `index.ts` from
   `profiles.role`/`additional_roles`, read from the database by the
   already-verified `user.id` — never a client-asserted claim, traced
   directly in `authenticate()`) resolves to `role === 'admin' ||
   'sub-admin'`, checked again by `hasInfluencerAdminAccess` inside this
   handler, narrower than the router's own broader
   admin/sub-admin/partner-admin/partner-user gate: read any influencer's
   full row, and edit six fields on any influencer. Not scoped to
   "influencers this admin manages" — but admin/sub-admin are platform-wide
   staff roles everywhere else in this router (`restaurants.ts`,
   `brands.ts`, and `ENG-007`'s own already-reviewed
   `loyalty-config.ts` all grant the same unscoped platform-wide reach to
   the same two roles), so this is consistent with existing, already-accepted
   precedent, not a new IDOR-shaped gap.
3. **What new data does this expose, and to whom?** `GET` returns the full
   influencer row via `select('*')`, which includes `email` and `phone`
   (real PII, not just marketing metadata — `Influencer` interface in
   `src/pages/Influencers.tsx`, confirmed directly) alongside the new
   staff-only fields. Not new exposure in practice: the admin board's
   existing `fetchData()` already does the identical `select('*')`
   client-side and has since before this ticket (design doc: "the page
   already fetches with `select('*')`"), to the same or a *broader*
   audience (the page itself, not re-audited by this ticket) than this
   narrower admin/sub-admin-only endpoint. This new `GET` route also has no
   caller anywhere in this diff — the frontend still reads influencer rows
   through the existing Supabase-client path, confirmed by grep — so it adds
   no live exposure today, only a dormant route gated at least as tightly as
   the existing one. Classified **Confidential** (email/phone are PII, not
   merely "Internal" business data) rather than the design doc's own
   "business-internal" framing — worth naming precisely even though the
   verdict doesn't change.
4. **What breaks if this component is fully compromised?** A compromised
   admin/sub-admin token could rate/tag/edit-preferences-for or read contact
   info on any influencer. No payment, no auth, no ledger data — same
   ceiling as `ENG-007`'s already-accepted "bounded by what admin/sub-admin
   can already do platform-wide" reasoning, and lower stakes than that
   ticket (marketing metadata + contact info, not a financial rate table).

## PII handling

`email`/`phone` are present on the `influencers` row and reachable via the
new `GET` endpoint's `select('*')` — real PII, not merely "Internal" per
`security-baseline.md`'s classification table (**Confidential**, not
Internal — noted under Threat model above). Not new exposure: the same PII
is already exposed by the pre-existing frontend `fetchData()` call to
whatever role can already load this admin page, and the new endpoint's own
gate (admin/sub-admin only) is at least as narrow. No new PII field is
added by this ticket — `staff_rating`, `collaboration_count`,
`accepts_paid`, `accepts_barter` are all staff-authored operational data
about the relationship, not data about a natural person's identity beyond
what already existed.

   actually receives), a consistency/maintainability item — not re-filed
   here.

## Verdict: PASS

No exploitable vulnerability, no access-control gap beyond this router's
own already-accepted platform-wide admin/sub-admin model, no secret, no
injection surface. Every access path is server-side gated and the negative
case (non-admin caller, unsupported method) is tested. The PII exposed via
the new `GET` route is pre-existing exposure via a route with no live
caller today, gated at least as tightly as the existing display path. The
three items carried forward are all either pre-existing host constraints
already accepted elsewhere on this board or non-blocking coverage/style
gaps, none a defect introduced by this diff.
