# Security review — ENG-009

## Threat model

1. **What new input can an attacker control?** Three new fields on the
   existing `PATCH /admin-portal/influencers/{id}` body (`followers:
   integer 0–1e9`, `engagement: number 0–100`, `social_stats_platform:
   string ≤32 chars or null`), and a new route with no parameters, `GET
   /admin-portal/influencers/activity`. All four sit behind the same
   single, unmodified gate every other field on this handler already
   sits behind: the router's bearer-token `authenticate()` (untouched by
   this diff), then `hasInfluencerAdminAccess`, checked once before the
   method/route branches — confirmed by reading `handleInfluencers`
   directly: the new activity-route check at line 60 and the `influencerId`
   match at line 65 both execute *after* the access check at line 48, not
   before it.
2. **What new capability does this grant, and to whom?** Write access to
   two previously-unwritten columns (`followers`, `engagement` — both
   exist today, `DEFAULT 0`, written by nothing in either repo) plus one
   genuinely new column (`social_stats_platform`), for callers already
   holding `admin`/`sub-admin` — the same population that already reads
   these same columns (and every other influencer field) via this same
   page's `select('*')`. Read access to a new aggregate
   (invitations/visits/completed_visits/responded/response_rate/
   last_activity_at) over `influencer_invitations`, computed on read,
   for the same admin/sub-admin population. This table has no staff/admin
   `SELECT` policy at all, so this aggregate is unreachable through any
   client-side path today — the new route is the *first* staff-facing
   window onto this data, but the window opens to callers who already
   have unrestricted read on every influencer's PII on the same page.
3. **What new data does this expose, and to whom?** The activity
   aggregate exposes counts and dates derived from `influencer_invitations`
   — no name, contact, or handle, nothing beyond what an aggregate over a
   join table can carry. Lower sensitivity than the influencer row itself,
   which admin/sub-admin already reads in full. `social_stats_platform`
   is a free-text label staff type themselves (e.g. "Instagram") — not
   user-controlled in any sense an attacker could exploit; the value
   round-trips into a DB column and a `<p>` text node, never a sink where
   32 characters of plain text could do anything (no HTML injection point
   in this rendering path — React JSX text content is escaped by default,
   confirmed by reading the render call: `{social_stats_platform}` is a
   plain JSX expression child, not `dangerouslySetInnerHTML`). No new
   data-classification tier over what this `GET` already returns.
4. **What breaks if this component is fully compromised?** Identical to
   `ENG-008`'s own answer, re-confirmed rather than assumed: `adminSupabase`
   is a service-role client, RLS bypassed entirely, and the only gate is
   the same in-code role check every other write on this handler already
   depends on. A compromised admin/sub-admin token could forge a social
   figure or read the activity aggregate for any influencer — an
   integrity/internal-business-data risk, not a new confidentiality tier
   (that token already reads full influencer PII today) and not a new
   architecture (identical blast radius to `loyalty-config.ts`/
   `foodswipe.ts`, both already accepted at this gate).
