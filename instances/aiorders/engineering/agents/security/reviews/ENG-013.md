# Security review — ENG-013

## Threat model

1. **What new input can an attacker control?** `profileId` (string) and
   `stage` (string, six-value enum) in the JSON body of two new routes,
   `POST /foodswipe/stage/set` and `POST /foodswipe/stage/reset`. Both sit
   behind the router's existing bearer-token authentication
   (`admin-portal/index.ts`'s `authenticate()`, unmodified by this diff)
   and the handler's own admin/sub-admin role gate
   (`hasFoodswipeAccess`, checked once before either new branch runs).
2. **What new capability does this grant, and to whom?** Write access to
   one field (`profiles.foodswipe_stage_override`) for callers already
   holding `admin`/`sub-admin` — the same population that could already
   read every Foodswipe profile via this handler's existing `GET`. No new
   role, no new caller population, no elevation. Before this diff the
   handler was 100% read-only; it is now read+write on exactly one
   business-process label.
3. **What new data does this expose, and to whom?** The existing `GET`
   response gains one field, `foodswipe_stage_override`, to the same
   admin/sub-admin audience that already receives name/email/phone for
   every row in that response. Not a new sensitivity tier — a nullable
   enum mirroring a value the response already computed and returned as
   `stage`.
4. **What breaks if this component is fully compromised?** A compromised
   admin/sub-admin token could already read every Foodswipe profile's PII
   in full. This diff adds the ability to overwrite one enum field on
   those same rows — an integrity/business-process risk (a listing's
   displayed pipeline stage could be set to something wrong), not a
   confidentiality or financial one. No new table, no new role, no
   cross-tenant reach beyond what `source = 'foodswipe'` already scoped
   for the pre-existing read.
