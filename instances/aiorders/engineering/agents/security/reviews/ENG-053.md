# Security review — ENG-053

## Threat model

1. **What new input can an attacker control?** An authenticated restaurant
   staff member (real Bearer JWT, verified access to `restaurant_id`) now
   controls `code` (the diner's redemption code — `platform_customers.id`
   verbatim, a bearer credential by design, `ADR-022`), `points`, and
   `idempotency_key` on a new `redeem_points` action. All four are
   read straight from `req.json()`'s payload with no upstream trust —
   `restaurant_id` is checked first via `requireRestaurantAccess`, before
   `code`/`points`/`idempotency_key` are even looked at.
2. **What new capability does this grant, and to whom?** A restaurant staff
   member with confirmed access to a specific restaurant gains the ability to
   debit a diner's loyalty balance at that restaurant, over HTTP. Before this
   ticket, `redeem_points_if_eligible` (`ENG-052`) existed but was reachable
   by no HTTP caller at all — `service_role`-only. This is exactly the
   intended capability (PRD/design), gated the same way its two siblings
   (`record_dine_in_earn`, `get_loyalty_balance`) already are.
3. **What new data does this expose, and to whom?** The response carries a
   redemption outcome (`invalid_code` / `not_enrolled` / `insufficient_balance`
   / `redeemed`) and, on the latter two, the diner's post-action balance at
   that restaurant — the same shape `get_loyalty_balance` already returns to
   the same caller class. No new data class, no cross-restaurant leak (every
   read is scoped to `restaurant_id`).
4. **What breaks if this component is fully compromised?** A caller who
   already holds valid restaurant-staff credentials for a specific restaurant
   could redeem any diner `code` they obtain against that restaurant's
   balance. This is the PRD's own accepted, deferred bearer-credential risk
   (design's Risks, `ADR-022`) — unchanged and not widened by this diff — and
   is bounded to the one restaurant the compromised account has real access
   to, per `requireRestaurantAccess` (independently verified below, not
   taken on trust).
