# Security review — ENG-048

## Threat model

1. **What new input can an attacker control?** `credit_order_if_eligible(p_order_id
   uuid, p_fulfillment_reason text)` takes two parameters, but post-fix
   `EXECUTE` is restricted to `service_role` (verified below) — no
   anon/authenticated caller can invoke it at all, so there is no direct
   attacker-controlled input into this diff. `p_fulfillment_reason` is
   further constrained to `'reported'`/`'window_elapsed'` by an explicit
   raise. The real attacker-facing input (the CloudWaitress webhook payload
   that eventually drives a call to this function) belongs to `ENG-049`,
   which this ticket does not touch.
2. **What new capability does this grant, and to whom?** `service_role`
   gains the ability to credit loyalty points for any order via one
   function; `pg_cron` gains a new scheduled job that POSTs to a fixed,
   non-user-controlled URL every 15 minutes using a Vault-sourced bearer
   token. No capability is granted to `anon`/`authenticated`.
3. **What new data does this expose, and to whom?** `loyalty_ledger_entries`
   is new, RLS-enabled, zero policies — deny-by-default to
   `anon`/`authenticated`, same pattern `ENG-006`/`ENG-007` already
   established. The two new `orders` columns (`cw_order_id`,
   `loyalty_processed_at`) ride on `orders`' existing RLS/access model,
   unchanged by this migration; neither is PII or secret (a
   CloudWaitress-internal id and a processing timestamp) — Internal
   classification, consistent with the table's existing fields.
4. **What breaks if this component is fully compromised?** Bounded even
   under misuse: the function derives *who* gets credited entirely from the
   order's own recorded identity link (`orders.customer_id` →
   `platform_customer_legacy_links` → `platform_customer_id`), never from a
   caller-supplied identity. Even a call made with a legitimate but
   attacker-influenced `p_order_id` (e.g. a future bug in `ENG-049`'s
   webhook handler that trusted an unverified payload) could only credit
   that order's actual owner once — it has no path to divert points to a
   different account. A full compromise of `service_role` itself is an
   existing, project-wide risk this ticket neither introduces nor worsens.

## Verified directly, not taken on the ticket's or any prior gate's word

Both round-1 findings (B1: no effective grant restriction; B2: unfloored
negative amount) were already found by code review, fixed by database, and
independently re-confirmed by both principal-engineer and QA in round 2. Per
this gate's own standard of re-proving rather than inheriting a verdict, B1
— the access-control finding, and the one this gate owns most directly —
was re-run from scratch, a fourth independent time, rather than accepted on
three matching accounts:

- Fresh disposable replica (`supabase/postgres:15.8.1.073`, same image every
  prior verification on this ticket used), own minimal fixture (five
  tables covering every FK/reference the migration and function touch),
  the real migration file applied unmodified via `psql -f` — no edits, no
  shortcuts. Independently confirmed the mechanism *before* applying the
  migration: `pg_default_acl` on this image's `public` schema already
  carries a function-object (`defaclobjtype = 'f'`) entry naming `anon`,
  `authenticated`, and `service_role` directly with `EXECUTE` at
  function-creation time — the same project-specific root cause round 2's
  writeup names, confirmed here independently rather than read off that
  writeup.
- `has_function_privilege` for all four roles on the corrected function
  post-migration: `anon → false`, `authenticated → false`, `service_role →
  true`, `postgres → true` — matching all three prior accounts exactly.
- Went one step further than a catalog read: **attempted the actual RPC as
  both roles.** `set role anon; select credit_order_if_eligible(...)` and
  the same as `authenticated` both fail with `ERROR: permission denied for
  function credit_order_if_eligible` — a real rejection, not an inferred
  one.
- Confirmed the fix doesn't over-restrict the legitimate caller either: `set
  role service_role` on a seeded fixture order (`cart 100, discount 10`,
  5% rate) returns `credited`, ledger row `amount 90.00, points 4.5000,
  rate_applied 5.00` — identical to every prior party's numbers, so the
  grant/revoke edit changed nothing about the function's own logic.
- Container removed immediately after (`docker rm -f`); confirmed nothing
  left running.
- **Secrets — diff and full branch history.** `git diff origin/main..HEAD`
  is 265 insertions / 0 deletions on one new file (confirmed via
  diffstat), so the final file *is* the full history for this path — no
  add-then-remove is possible. Grepped for
  `key|secret|password|token|bearer|AKIA|BEGIN (RSA|EC|PGP|OPENSSH)|api[_-]?key`:
  every hit is either a Postgres constraint name ending in `_key`
  (`..._order_id_key`) or a Vault secret referenced *by name*
  (`vault.decrypted_secrets where name = 'service_role_key'`) — no literal
  credential anywhere. Per-commit stats confirm the same: `9fccdad`
  (250 insertions, new file) + `60fa06e` (16 insertions / 1 deletion,
  exactly the two named fix spots) sum to the total — nothing removed and
  hidden in between.
- **`security definer` hardening, checked explicitly** (a classic
  privilege-escalation footgun for this function type): `set search_path =
  'public'` is pinned on the function, *and* every table reference inside
  the body is schema-qualified (`public.orders`,
  `public.loyalty_ledger_entries`, `public.platform_customer_legacy_links`,
  `public.restaurant_loyalty_configs`) regardless — belt-and-suspenders
  against a search-path hijack even though the pin alone would suffice.
