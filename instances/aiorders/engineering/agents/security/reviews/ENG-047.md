# Security review — ENG-047

## Threat model

1. **What new input can an attacker control?** One boolean UI toggle
   (`filters.openNow`), serialized via `URLSearchParams.append('open_now',
   params.openNow.toString())` — always the literal string `"true"` or
   `"false"`, never free text. Nothing in this diff parses or trusts any
   *incoming* value; the only new inbound field, `restaurant.status`, is read
   from the existing discovery response and only ever rendered, never used
   as a selector, path, or condition beyond a truthy check. An attacker can
   already call the discovery endpoint directly with any `open_now` value
   regardless of what this frontend sends — that surface belongs to
   `aiorders-api`'s own handler (`ENG-045`, reviewed and passed under its own
   gate: `agents/security/reviews/ENG-045.md`), and this diff does not change
   what that handler accepts.
2. **What new capability does this grant, and to whom?** None. Any visitor
   of the public, unauthenticated FoodSwipe discovery UI could already fetch
   the restaurant list; this diff only adds a client-side filter chip and a
   label render on top of the same read-only response. No new route, no new
   caller, no privilege change.
3. **What new data does this expose, and to whom?** `restaurant.status` (a
   short server-computed string, e.g. a closed/hours label) to the same
   anonymous marketplace visitor who already sees the restaurant's cuisine,
   address, distance, and price on the same card. Business open/closed
   status is not sensitive — it's information a caller phoning or opening
   the restaurant's own listing would learn anyway — and `ENG-045`'s own
   gate already classified this field the same way on the read side. The
   three new `has_order_food`/`has_dine_in`/`has_catering` fields added to
   the `RestaurantCard` type are confirmed dead weight today (verified
   directly: `aiorders-api`'s shipped `ENG-045` discovery/list handler never
   populates them on a list row, only `handleRestaurantDetail`'s separate
   response does, and no consumer of this type is the detail page) — zero
   exposure from this diff regardless.
4. **What breaks if this component is fully compromised?** Unchanged from
   today. This is an unauthenticated, read-only discovery page with no
   session, no write path, and no elevated capability; a compromised build
   of this frontend could already show attacker-controlled content to
   visitors before this ticket. Nothing in this diff raises that ceiling.
