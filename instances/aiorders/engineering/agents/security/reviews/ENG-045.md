# Security review — ENG-045

## Threat model

1. **What new input can an attacker control?** `mode` (pre-existing query
   param, now also drives `p_channel`) and `open_now` (new query param, this
   diff). Both are strictly bounded before use: `channelForMode(mode)` maps
   through a fixed 3-entry lookup (`CHANNEL_BY_MODE`) and returns `null` for
   anything else — the caller never controls the literal channel string that
   reaches the RPC argument or the `.eq()` column lookup. `openNow` is parsed
   as `param === 'true' ? true : param === 'false' ? false : undefined` in
   `validation.ts` — no free-text, no type confusion. Neither value is
   interpolated into a query string anywhere.
2. **What new capability does this grant, and to whom?** A finer-grained
   filter on an already-public, already-unauthenticated discovery endpoint
   (confirmed directly against `restaurant-marketplace/index.ts`: no auth
   check on any route in this function, before or after this diff — this
   handler has always been open to anonymous callers, same as its existing
   `hasOffers`/`rating4Plus`/`orderingLink` filters). No new audience, no new
   read/write capability — only which already-visible rows come back changes.
3. **What new data does this expose, and to whom?** `status` (a closed/hours
   label string) on each discovery row, and `has_order_food`/`has_dine_in`/
   `has_catering` on the detail endpoint — to the same anonymous/public
   audience already reading name, address, rating, and price level from this
   endpoint. Restaurant hours and staff-set discoverability flags are
   operational metadata, not PII, and are already client-visible elsewhere in
   the product (`ENG-044`'s own review reached the same conclusion for the
   underlying columns).
4. **What breaks if this component is fully compromised?** Unchanged from
   today. This diff adds a filter and a label computation in the handler
   layer; it does not touch how `utils/database.ts`'s `supabase` singleton
   authenticates, does not change any grant, and does not introduce a new
   privilege boundary. A compromised handler gets exactly the same DB access
   it already had.

## Verified directly, not taken on the ticket's word

- **No authentication exists on this route, and that is pre-existing, not
  introduced here.** Read `restaurant-marketplace/index.ts` directly: `GET
  /restaurants` and `GET /restaurants/:id` dispatch to
  `handleRestaurantDiscovery`/`handleRestaurantDetail` with no token check
  anywhere in the request path. This is why the security-baseline's A01
  negative-case bar (wrong-tenant/wrong-role/no-token) does not apply here —
  there is no tenant or role concept on a public restaurant-browse endpoint,
  and this diff does not add one. The *correct* negative case for this
  ticket's own feature is "a channel-disabled restaurant never appears",
  which is tested (see A01 below).
- **The channel gate cannot be used to select an arbitrary column.**
  `CHANNEL_COLUMN[channel]` (used in the fallback path's `.eq(...)`) is only
  ever indexed by `channelForMode`'s own output, which is restricted to
  `order_food`/`dine_in`/`catering`/`null` by construction — read both maps
  side by side in `restaurants.ts` to confirm there is no path from request
  input to an arbitrary object key. The RPC path passes the same bounded
  value as `p_channel`, a typed `text` parameter compared with native `=` in
  the already-shipped `20260907120001_...sql` (re-read directly: `p_channel
  is null or (p_channel = 'order_food' and r.has_order_food) or …` — no
  dynamic SQL, confirmed at `ENG-044`'s own gate and re-confirmed here since
  this ticket is the first caller of that parameter).
- **Secrets — diff and full branch history.** `git diff origin/main...HEAD`
  and `git log -p origin/main..HEAD` (all three commits, `b647508`, `a9693b6`,
  `5f35b92`) scanned for key/secret/password/token/bearer/PEM/service-role
  patterns: the only match is an unrelated local variable named `token` inside
  `openingHours.ts`'s day-name parser. No credential, no key, nothing to
  rotate.
- **No new dependency.** `git diff origin/main...HEAD --stat -- '*.json'
  '*.lock'` against the tracked diff: empty — the two `deno.lock` files
  present in the worktree are untracked (confirmed via `git status`), not
  part of any of the three commits. The one new import
  (`deno.land/std@0.177.0/testing/asserts.ts`, test file only) matches the
  exact pin already used by every other test file in this repo
  (`brand-portal/website.test.ts`, `admin-portal/handlers/restaurants.test.ts`,
  and 15+ others) — not a new or divergent dependency, just this ticket's
  first test file following the established convention.
- **Bounded parsing, no DoS vector from request input.** `toWeekdayLines`
  truncates to 14 lines of ≤200 chars each before any regex runs, and the
  regexes involved (`RANGE_SEPARATOR`, `CLOCK_PATTERN`, `ODD_SPACES`) are
  simple, anchored, non-nested patterns with no catastrophic-backtracking
  shape. Moot in any case: `opening_hours` is DB-authored data via the
  existing staff-facing admin surface, not attacker-supplied in this request
  path, and per-request row count is already capped at 100
  (`Math.min(parseInt(...), 100)`, pre-existing, unchanged).
