# Security review — ENG-032

## Threat model

1. **What new input can an attacker control?** None reaching a new code path.
   The two new pipeline-stage strings (`'Quote Generated'`, `'Contact
   Requested'`) are static literals added to hardcoded arrays/objects in eight
   files — not derived from any input. The itemized-selections block renders
   `request.selections`/`request.action_type`, both already flowing through
   the existing `get_catering_requests` → `verifyRestaurantAccess` →
   `select('*')` path since `ENG-031`'s migration shipped; this diff adds no
   new fetch, only a new render of data already returned to the client.
2. **What new capability does this grant, and to whom?** None. No new route,
   no new Supabase call, no new write path — confirmed directly:
   `git diff origin/main...HEAD` touches only `.tsx`/`.ts`/`.css` files in
   `restaurant-portal`, and zero `supabase.from(` calls are added or changed
   anywhere in the diff (grepped). The status-change write
   (`StatusUpdateModal`, the kanban drag handler, `CateringDetailModal`'s own
   update) still sends only `{ status }`, unchanged by this diff, and
   `catering.status` remains a plain-text column with no enum or server-side
   validation, same as before this ticket.
3. **What new data does this expose, and to whom?** The itemized order
   (quantity/name/note per selection, grouped by category) becomes visible in
   the owner's detail modal for the first time. Exposed only to whoever
   `get_catering_requests` already authorizes today — the restaurant's own
   staff, per `verifyRestaurantAccess`. `selections.note`/`.name` are
   customer-authored freeform text at the same sensitivity as the pre-existing
   `requirements` field (per `ENG-031`'s own classification, unchanged here) —
   not a new PII or Restricted-tier class.
4. **What breaks if this component is fully compromised?** No change from
   today. `restaurant-portal` is a browser client with no credentials of its
   own beyond the logged-in user's session; a compromised build serves
   attacker-controlled JS into that session's own already-authorized data,
   exactly as it could before this diff.

   read against `origin/main`. But no `catering.test.ts` exists anywhere in

   three has a regression test proving the wrong-tenant case actually stays
   denied — unlike 5 of its 9 sibling handler files, which `ENG-022` covered
   with exactly this shape of test in `feedback.test.ts`/`customers.test.ts`/
   `hiring.test.ts`/`website.test.ts`/`offers.test.ts`.

   **Not blocking ENG-032:** this diff adds no code to `aiorders-api` at all,
   and doesn't change what `get_catering_requests` returns or who it's
   returned to — see Negative-case test coverage above. **Newly relevant

   access-check regression on this call site would have been lower-stakes; as
   of this diff shipping, the same call site's return value is rendered
   directly to the owner, which is exactly the condition under which a silent
   regression would first become visible to a real user (the good case) or
   exploitable (the bad one).
