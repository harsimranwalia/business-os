# Security review — ENG-031

## Threat model

1. **What new input can an attacker control?** None. This diff is one
   migration file — two `alter table ... add column if not exists`
   statements plus column comments. No endpoint, no handler, no parser
   reads or writes either column yet. Confirmed, not assumed:
   `grep -rln "action_type\|selections" supabase/functions/` returns zero
   hits in the worktree, so there is no reachable code path for an attacker
   to reach these columns through until `ENG-033` ships.
2. **What new capability does this grant, and to whom?** None. No new
   route, function, or write path is added anywhere in this diff.
3. **What new data does this expose, and to whom?** None yet — both
   columns are nullable, unpopulated, and unread by any existing code.
   Once `ENG-033` starts writing to them, they inherit whatever read
   protection already applies to every other column on `public.catering`
   (see Finding #1 below for the one open question about what that
   protection actually is).
4. **What breaks if this component is fully compromised?** No change from
   today. A compromised `aiorders-api` service-role credential already has
   full read/write on `public.catering`; two more nullable columns on a
   table it can already reach add nothing to that blast radius.

This is close to the smallest possible security surface a schema change
can have: additive, nullable, no default, no constraint, no index, no
reachable code path yet.

## Findings — non-blocking

1. **A01-adjacent: RLS activation on `public.catering` is unverified from
   this repo — second occurrence of this exact class today** (first:
   `agents/security/reviews/ENG-015.md` Finding #1, `public.restaurants`).
   `20250729143357_initial_restaurant_rls.sql` defines seven policies
   against `public.catering` (owner/manager SELECT, public INSERT,
   owner/manager UPDATE/DELETE, admin ALL) and the design's own AC-13
   argument — "zero new authorization code" for these two new columns —
   rests entirely on those policies being enforced. But no migration in
   tracked history runs `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` on
   `catering` — checked directly: `grep -rniB2 "ENABLE ROW LEVEL SECURITY"
   supabase/migrations/*.sql` matches seven other tables (`proxy_sessions`,
   `audit_logs`, `restaurant_activations`, `restaurant_claim_documents`,
   `restaurant_feedback_dedupe_archive`, `platform_customers`,
   `platform_customer_legacy_links`, `api_keys`, `restaurant_loyalty_configs`)
   and never `catering` or `restaurants`. Both predate tracked migration
   history (no `CREATE TABLE` for either anywhere in `supabase/migrations/`
   either), so whatever enabled RLS on them — if anything did — happened
   before this repo's migration history starts.

   **Not asserted as a live defect.** The same `20250729143357` migration
   *drops* three named pre-existing policies on `catering`
   ("Enable read access for all users", "Enable insert for authenticated
   users only", "Update by only authenticated users") before replacing
   them. A Postgres policy has zero effect on a table where RLS is
   disabled — there would be no reason for whoever created those original,
   already-restrictive policies to write an "authenticated users only"
   INSERT guard at all if RLS were off, since table-level GRANTs would
   govern access instead and the policy would be dead text. Their
   existence is indirect but real evidence that RLS has been enabled on
   `catering` since at least the table's un-tracked origin — the same
   style of inference `ENG-015`'s finding drew from `restaurants`' own
   progressive-lockdown history. Separately: `catering`'s own public
   INSERT (`WITH CHECK (true)`) is *meant* to be open to anyone — that is
   this table's actual product requirement, an unauthenticated lead form —
   so even in the worst case, RLS being off would not "newly" open the one
   surface this ticket's design leans on being closed; what it would
   expose is SELECT/UPDATE/DELETE, which is the part actually unverifiable
   from the repo.

   **Not blocking:** pre-existing (predates this ticket by five-plus
   weeks, arguably by the table's entire history), not worsened by this
   diff (the two new columns ride on whatever protection level already
   covers every other column on this table — `name`, `phone`, `email`,
   `requirements`, `restaurant_id` — none of which this ticket touches),
   and not safely fixable blind in this ticket's scope (a defensive
   `ENABLE ROW LEVEL SECURITY` would be a platform-wide behavioural change
   touching every existing caller of this table, not a two-column
   addition — same reasoning `ENG-015`'s Finding #1 used and rejected for
   the same reason). No live Postgres/Supabase session reachable this
   session to check `pg_class.relrowsecurity` directly — the same standing
   host limitation every other hop on this ticket has already recorded.

   **Recommendation, routed forward rather than folded in here:** this
   ticket has nothing live to smoke-test (both columns are null and
   unread until `ENG-033` ships), so unlike `ENG-015` there is no
   already-planned staging step to attach this to yet. The empirical check
   — attempt a `catering` SELECT/UPDATE as a non-owning authenticated
   account and confirm it is actually rejected — belongs at `ENG-033`'s
   own QA/security gate instead, the first point where these columns'
   data is actually reachable through a real path. Logged here and in
   `agents/security/notebook/2026-09-03-findings.md`, which
   `ENG-033`'s security gate reads as a matter of course
   (`skills/security-gate/SKILL.md` → Inputs), so it surfaces there
   without a separate proposal. Two occurrences of this class in one day
   (this table and `restaurants`) is worth a third pass noticing the
   pattern, not yet a standards promotion — the three-strike mechanism is
   for code-review-catchable defects, and "confirm RLS is on" isn't
   something code review can check without the same live-DB access this
   session doesn't have either.
