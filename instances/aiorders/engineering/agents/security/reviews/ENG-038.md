# Security review — ENG-038 (round 2 — verifying round 1's two blocking findings)

Round 1 (this same date) failed on two blocking findings. This round re-reads
the fix commits directly against the code and the schema — not against the

## Threat model (re-run against this round's diff only)

1. **What new input can an attacker control?** Less than before this fix, not
   more. Pre-fix, `sendBroadcastMessage`'s `data` accepted attacker-controlled
   `customerId`/`restaurantId`/`emailSubject`/`emailBody`/`smsBody` on an
   unauthenticated path. Post-fix it accepts exactly one field, `recipientId`
   — and that value is only useful if it names a row already in `status =
   'claimed'`, a state a caller cannot self-assign (`claimRecipients`'
   `UPDATE ... WHERE status = 'pending'` is the only writer of that status,
   and it always targets rows this dispatcher itself selected). Confirmed by
   reading `consumers.ts`'s new body and `dispatch.ts`'s `claimRecipients`/
   `resolveRecipient` directly, not from the fix notebook's account of them.
2. **What new capability does this grant, and to whom?** None — this is a
   capability *removal*. Before: anyone with network access could trigger an
   arbitrary-content send to an arbitrary customer, impersonating an
   arbitrary restaurant. After: the same unauthenticated endpoint can only
   replay a send this platform's own dispatcher already decided to make, with
   content and recipient it cannot influence.
3. **What new data does this expose, and to whom?** None. `sendBroadcastMessage`
   still reads `customers`/`restaurants`/`broadcast_campaign_steps`, same
   tables as before the fix, server-side only.
4. **What breaks if this component is fully compromised?** Unchanged from
   round 1's own analysis of the surrounding system: a compromised
   service-role credential already has full read/write on this database. This
   fix narrows what an *uncompromised, credential-less* caller can do to that
   same endpoint — it doesn't change the compromised-service-role case either
   way.

## Findings — non-blocking

1. **A04-adjacent, low severity: TOCTOU race in `tooSoonSinceLastCampaign`.**
   `brand-portal/broadcasts.ts`, `createBroadcast`. The interval check reads
   the restaurant's most recent non-cancelled campaign's `created_at` with a
   plain `SELECT`, not a lock or a conditional write. Two `create_broadcast`
   calls for the same restaurant, arriving close enough together, can both
   read "no campaign within the last 24h" before either has inserted its own
   row, and both proceed — one restaurant getting two campaigns inside the
   cooldown window instead of one. **Exploit path:** an already-authenticated
   restaurant owner (or a compromised owner credential — the same
   prerequisite Finding 2 itself assumed) fires two `create_broadcast`
   requests back to back. **Blast radius is bounded, which is why this
   doesn't block:** each resulting campaign is still independently capped at
   `MAX_RECIPIENTS_PER_CAMPAIGN` (10,000) by the *other* new check, which has
   no equivalent race (it's a point-in-time count, not a decision about
   whether to allow a state transition); the race only defeats the "wait
   24h between sends" half of Finding 2, not the "cap this campaign's size"
   half, and winning it repeatedly at scale is impractical (it requires
   precisely-timed concurrent requests, not a single crafted payload). **Fix,
   if picked up:** a partial unique index or a `SELECT ... FOR UPDATE` on the
   restaurant's own campaign row (or an advisory lock keyed on
   `restaurant_id`) around the check-then-insert sequence in
   `createBroadcast`. Logged here and in
   `agents/security/notebook/2026-09-04-findings.md`; not filed as a
   proposal — it's specific to this ticket's own new code, not a systemic
   pattern, and `eng_build_loop.md` step 3 reserves `proposals.md` for the
   latter.
