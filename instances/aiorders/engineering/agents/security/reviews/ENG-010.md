## Threat model

1. **What new input can an attacker control?** Two new routes,
   `GET /admin-portal/influencer-notes?influencer_id={id}` and
   `POST /admin-portal/influencer-notes` (body: `influencer_id`, `body`).
   Both sit behind the router's unmodified `authenticate()` allowlist
   (`admin`, `sub-admin`, `partner-admin`, `partner-user` — confirmed by
   reading `admin-portal/index.ts` line 95 directly; `influencer` is not in
   this list), then this ticket's own `hasInfluencerAdminAccess` check
   (narrower: `admin`/`sub-admin` only), reused unmodified from
   `influencers.ts` rather than reimplemented.
2. **What new capability does this grant, and to whom?** Write access to a
   brand-new, previously-nonexistent data type (freeform staff notes about a
   named person) for callers already holding `admin`/`sub-admin` — the same
   population that already reads/writes every other influencer field on this
   same page. `author_id` is taken exclusively from the authenticated
   session (`auth.user.id`), never the request body — verified directly in
   `createInfluencerNote` and independently re-run via the dedicated test
   (`POST takes author_id from the session, never the request body`,
   asserting on the captured `.insert()` argument, not the response echo).
3. **What new data does this expose, and to whom?** The single risk this
   ticket's own PRD names as the one thing it cannot get wrong: staff
   commentary about a named, real person (an influencer with their own
   AIOrders login), readable by that same person. Two independent layers now
   close it — the router excludes `influencer` from `admin-portal` entirely
   (confirmed, line 95), and, as of this ticket's own round-2 fix, the table
   itself carries RLS scoped to `admin`/`sub-admin` (confirmed by reading the
   migration directly, see Data layer below) — so the finding round 2's code
   review raised (an influencer's own valid session reaching the table
   directly via PostgREST, bypassing the edge function entirely) is closed at
   the layer that actually matters for that attack, not only at the handler.
4. **What breaks if this component is fully compromised?** Identical answer
   to every prior ticket on this handler family: `adminSupabase` is a
   service-role client (`admin-portal/index.ts` lines 51–58, confirmed,
   constructed from `SUPABASE_SERVICE_ROLE_KEY` via `Deno.env.get`, never a
   literal), bypasses RLS by definition, and a compromised admin/sub-admin
   token could read or forge notes for any influencer — an
   integrity/internal-data risk already accepted at this same blast radius
   for the sibling `influencers` handler (`ENG-008`/`ENG-009`), not a new
   architecture or a new confidentiality tier.

## Data layer — the round-2 fix, re-verified from the file itself

`supabase/migrations/20260902120000_create_influencer_notes.sql` (read
directly, not from the ticket log's account):

```sql
alter table influencer_notes enable row level security;

create policy "Admins can manage influencer notes"
on influencer_notes
for all
using (exists (
  select 1 from public.profiles
  where id = auth.uid() and role in ('admin', 'sub-admin')
))
with check (exists (
  select 1 from public.profiles
  where id = auth.uid() and role in ('admin', 'sub-admin')
));
```

Compared directly against `supabase/migrations/20250926000000_proxy_sessions_audit_logs.sql`
(read in full this pass): identical policy shape, keyword casing only differs
(uppercase there, lowercase here, matching each file's own surrounding
convention). Went one step further than that single comparison: grepped
`supabase/migrations/20250729143357_initial_restaurant_rls.sql`, this
project's foundational RLS migration, and confirmed the same
`EXISTS`-against-`profiles` shape already gates `restaurants` and `catering`
— this is the codebase's established house pattern for admin-only RLS, not a
one-off precedent being copied a second time on faith. Also independently
confirmed the named, pre-existing, repo-wide gap this pattern carries
everywhere it's used: `grep -rl additional_roles supabase/migrations/`
returns zero hits — every RLS policy of this shape in this codebase checks
`profiles.role` only, never `additional_roles`, so a user granted admin
*only* via `additional_roles` would pass the handler's own check but not this
RLS policy in isolation. Not a new gap and not exploitable through this
feature's actual code path: the only reader is the service-role client, which
bypasses RLS entirely and applies the wider (`role` **or** `additional_roles`)
check. Named for the record, not blocking, not this ticket's to fix.

No live Postgres reachable from this host (no `docker`, `psql`, or `supabase`
CLI) — the `alter table`/`create policy` statements have not been executed
anywhere, the same standing gap every migration doc on this board already
carries. Not re-litigated as a new gap; closed as far as static verification
can close it.
