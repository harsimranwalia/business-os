# Security review — ENG-006

## Threat model

1. **What new input can an attacker control?** One new endpoint,
   `POST platform-customer-auth/verify`, taking an `Authorization: Bearer
   <token>` header and nothing else — no request body is parsed. The token
   is not trusted as an identity claim; it is handed to
   `admin.auth.getUser(token)`, Supabase's own verification, before anything
   else happens.
2. **What new capability does this grant, and to whom?** To a caller holding
   a *valid* Supabase session token: the ability to (a) upsert exactly one
   `platform_customers` row, keyed to that token's own `auth.uid()` — never
   an arbitrary id — and (b) trigger a lookup/link of `customers` rows whose
   `phone` matches that same token's own verified phone. A caller cannot
   name a different user, a different phone, or a different legacy customer
   id to act on — every write is keyed off what `getUser` returns for the
   caller's own token, not off anything the request body supplies (there is
   no request body). To a caller with an invalid/expired/missing token: 401,
   nothing else happens.
3. **What new data does this expose, and to whom?** A caller learns their
   own `platform_customers` row and the legacy `customers` rows now linked
   to it — every one of those legacy rows shares the caller's own verified
   phone number, so this discloses nothing that isn't already
   phone-equivalent to something the caller just proved they own via OTP.
   RLS backs this up independently of the endpoint's own logic: `select` on
   both new tables is scoped to `auth.uid() = id` /
   `auth.uid() = platform_customer_id`, so even a caller who somehow read
   the tables directly (bypassing this function) sees only their own rows.
4. **What's the blast radius of this endpoint being fully compromised?**
   Bounded by RLS + the `id = auth.uid()` keying: a compromised or malicious
   caller can create/update their own `platform_customers` row and cause
   linking against their own verified phone's legacy matches — the same
   thing a legitimate call does. It cannot write another user's row (no
   client insert/update policy exists for `platform_customer_legacy_links`
   at all — service-role only — and `platform_customers`'s own update
   policy is `auth.uid() = id`). It cannot modify or delete anything in
   `customers` — no code path in this diff writes to that table, confirmed
   by grep (`.update(`/`.delete(`/`.insert(` against `customers`: zero
   matches).

## PII handling

New PII surface: `platform_customers.phone` (already-collected data,
now additionally stored keyed to a platform-wide identity rather than
per-restaurant) and the fact of a cross-restaurant link itself (which
restaurants/brands a given phone has ordered from). Both are:
- Protected by RLS scoped to the owning `auth.uid()` — no other authenticated
  user can read them.
- Not newly *collected* — every linked phone already existed in `customers`
  under the restaurant it was originally captured by; this ticket links
  existing records rather than gathering new ones.
- **Consent for the new cross-restaurant correlation use is not yet
  captured** — `consent_recorded_at` exists as a column but nothing in this
  diff writes to it. Named in the design doc as deferred to the
  approver/counsel, restated here because "PII handling matches the
  project's data classification" is a literal Definition-of-Done line item
  and an honest answer here is "not yet, and by design not this ticket's
  call to resolve."

## Verdict: PASS

No exploitable vulnerability, no access-control gap, no secret, no injection
surface, no OWASP finding requiring a code change. Every write is keyed to
the caller's own verified identity, both in application logic and
independently at the RLS layer. The two design-level risks that exist

the architect before this code was written, not discovered here — this
review confirms the code matches that scoping rather than silently
expanding or quietly dropping it.
