# Security review — ENG-022

## Threat model

1. **What new input can an attacker control?** None new. `restaurant_id` was
   already attacker-controllable before this diff — a plain UUID visible
   client-side in `restaurant-portal`'s own context, sent on every request.
   This diff adds no new input; it makes the existing input's validation
   actually run.
2. **What new capability does this grant, and to whom?** None — the diff
   *revokes* a capability rather than granting one: cross-tenant read
   (`feedback`, `customers`, `offers`, `website`, `hiring`) and cross-tenant
   **write** (`offers`, `customers`, `website`, `hiring`) for an authenticated
   brand-portal user who does not own the target restaurant, previously
   granted by the two defeated-check bugs (wrong argument order + truthy-object
   check; discarded return value).
3. **What new data does this expose, and to whom?** None — narrows exposure.
   Confirmed by reading `index.ts` directly (unchanged by this diff, not in
   the diffstat): every `brand-portal` handler runs on a **service-role**
   Supabase client ("Create Supabase client with service role key for admin
   operations", `index.ts:39`) — RLS is bypassed at the database layer for
   this entire function, on every action, not only the five this ticket
   touches. `verifyRestaurantAccess`/`requireRestaurantAccess` is therefore
   not one layer of defense-in-depth on top of RLS; it is the **only** access
   control between an authenticated brand-portal user and any restaurant's
   data. There is no RLS backstop to fall back on if the in-code check is
   wrong — which is exactly what made the five broken call sites a full P0
   rather than a partial one, and exactly why fixing the call sites (this
   diff) is sufficient to close the hole rather than a partial mitigation
   awaiting a second layer.
4. **What breaks if this component is fully compromised?** Same answer as
   before this diff, restated for completeness: a compromised or malicious
   brand-portal session already carries service-role-backed reach over these
   nine files' tables via `verifyRestaurantAccess`'s own admin/sub-admin/
   partner-admin/partner-user bypass (`utils.ts`, unchanged by this diff — see
   Findings below). That bypass is pre-existing and out of this ticket's
   scope (PRD non-goals: "Redesigning `verifyRestaurantAccess` itself... it is
   correct; every failure is at the call site").

## Findings — both non-blocking, neither introduced by this diff

1. **A05, verbose error message.** `verifyRestaurantAccess`'s catch-all
   (`utils.ts`, unchanged by this diff) returns `` `Access verification
   failed: ${error.message}` `` on its own internal-error path, reachable by
   the client via `offers.ts`'s `access.error` (200 body) or via the thrown
   `Error`'s message propagating to `feedback.ts`/`customers.ts`'s top-level
   500 `details` field. This is the same finding class already three-struck
   on `ENG-009` (2026-09-02,
   `agents/principal-engineer/notebook/2026-09-02-security-proposal-verbose-error-response.md`)
   and carried again on `ENG-010` without a new proposal. Same disposition
   here: **not re-proposed** — logged to the notebook as another occurrence,
   the existing proposal already covers this class and remains unactioned.
   Not blocking: pre-existing, unchanged by this diff, and this diff's own
   fallback (`access.error || 'Access denied to this restaurant'`) only
   reaches the verbose branch when `verifyRestaurantAccess`'s own DB lookup
   errors — a low-frequency path, not the ordinary denial case (which returns
   the clean fallback string).
2. **Scoping question, not a confirmed defect.** `verifyRestaurantAccess`'s
   admin/sub-admin/partner-admin/partner-user role bypass (`utils.ts`, lines
   27–37, unchanged by this diff) grants full access to **any** restaurant for
   all four roles, with no further scoping — the same "any elevated role
   trusts too much" shape as this ticket's own root cause, in the same file,
   one function up. May well be intentional (an internal admin console
   plausibly wants exactly this), and redesigning it is explicitly out of
   this ticket's scope (PRD non-goals). Filed as a proposal (below), not a
   blocking finding — no evidence this is a defect, only that it's worth a
   deliberate look given the file's own history this ticket just fixed.
