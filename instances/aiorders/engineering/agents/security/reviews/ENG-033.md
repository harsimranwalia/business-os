# Security review — ENG-033

## Threat model

1. **What new input can an attacker control?** `action_type` (string, checked
   against exactly two literals, else nulled) and `selections` (array, ≤200
   elements, each `{category, item_id, name, quantity, note}` —
   `quantity`/`name`/`note` boundary-validated; `category`/`item_id` pass
   through unvalidated, by `validation.ts`'s own documented choice). Both
   arrive through `catering-request`'s pre-existing, intentionally
   unauthenticated public POST — no new entry point.
2. **What new capability does this grant, and to whom?** None beyond storing
   an itemized order and a customer-declared action type. `status` — the one
   field the design itself names as the load-bearing case ("the one place
   this ticket lets external input influence a field the owner acts on") — is
   explicitly derived server-side by `deriveActionStatus` and never read from
   the request body; confirmed directly in the diff, not assumed from the
   design's account.
3. **What new data does this expose, and to whom?** None to a new audience.
   `selections`/`action_type` join the existing `catering` row; every read
   path (`brand-portal/catering.ts::verifyRestaurantAccess`,
   `CateringDetailModal`'s RLS-scoped direct query) is unchanged — confirmed
   via `git diff origin/main...HEAD --stat`, neither file appears in this
   diff.
4. **What breaks if this component is fully compromised?** No change from
   today. `catering-request` already writes freeform, unauthenticated input
   into this table; this ticket adds two more validated fields to the same
   insert, same trust boundary, same blast radius.

## Findings — non-blocking

**1. Pre-existing HTML-injection gap in the owner-notification email, found
while reading `catering-request/index.ts` in full for trust-boundary
context — not part of this diff.**
- **Category:** A03 Injection — missing output encoding for an HTML sink.
- **Severity:** Medium. **Confidence:** High that the gap is real and
  reachable (read the exact code and traced the exact path); not
  independently tested end-to-end against a real email client, so the
  practical rendering behavior (most clients strip `<script>`/inline event
  handlers, fewer strip a plain `<a href>` or layout markup) is inference,
  not measurement.
- **Exact location:** `supabase/functions/catering-request/index.ts:348-378`
  (unchanged by this diff — confirmed via `git diff origin/main...HEAD`)
  builds `message_html`/`message` via raw template-literal interpolation of
  `full_name`, `phone`, `email`, `event_type`, `event_location`,
  `event_timings`, `number_of_guests`, `normalizedDeliveryMethod`, and
  `requirements` — every one attacker-controlled, since this endpoint is
  intentionally unauthenticated — with zero HTML-escaping.
  `supabase/functions/send-notification/index.ts:142-162` forwards
  `message_html`/`message` verbatim as fields in a POST to a third-party
  workflow webhook (Pabbly Connect), which is what actually emails/SMS/
  WhatsApps the restaurant owner.
- **Exploit path:** unauthenticated POST to `catering-request` with
  HTML-bearing free-text fields (e.g. `full_name` or `requirements`
  containing `<a href="...">`/formatting markup) → stored nowhere, but
  forwarded live into `message_html` → Pabbly webhook → the owner's actual
  email/SMS/WhatsApp inbox renders the attacker's HTML inside an otherwise
  legitimate "New Catering Request" notification — a phishing/content-
  spoofing vector against a real business owner, reachable by anyone, zero
  cost, zero authentication.
- **Specific fix:** HTML-escape each interpolated value at the two
  `message_html` template-literal call sites (a small `escapeHtml()` helper
  is enough — this isn't user-facing markup, just untrusted text landing in
  an HTML sink); the plain-text `message` field needs no change.
- **Not blocking `ENG-033`:** the vulnerable lines are untouched by this
  diff, and this ticket's own two new fields (`action_type`/`selections`)
  are not included in either template — confirmed directly, not assumed.
  Filed as a proposal (`agents/eng-manager/proposals.md`, 2026-09-04,
  security, `aiorders-api`), same routing `ENG-032`'s own review used for an
  analogous pre-existing/out-of-diff finding. Logged in
  `agents/security/notebook/2026-09-04-findings.md`.

**2. `selections[].name` has no length cap.**
- **Category:** A04 Insecure Design.
- **Severity:** Low. **Confidence:** High that the gap exists as described;
  low confidence it matters in practice.
- **Exact location:** `catering-request/validation.ts::isValidSelections` —
  checks `typeof name !== 'string'` but no `.length` bound, unlike `note`'s
  explicit 500-char cap in the same function.
- **Exploit path:** bounded by the existing 200-element cap and whatever
  request-size ceiling Supabase edge functions apply platform-wide; grants no
  capability beyond amplifying this endpoint's already-accepted, pre-existing
  spam/abuse profile (unauthenticated by design, no rate limit today,
  unrelated to this ticket).
- **Specific fix:** mirror `note`'s cap (e.g. 200 chars, generous for a dish
  name) if the inconsistency is worth closing.
- **Not blocking, not filed as a proposal** — logged as an observation
  (`agents/eng-manager/observations.md`, 2026-09-04): the design's own
  validation table doesn't call for a `name` cap either, so this is a minor
  consistency nit, not a gap the ticket was supposed to close.
