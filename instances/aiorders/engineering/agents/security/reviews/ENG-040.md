# Security review — ENG-040

## Threat model

1. **What new input can an attacker control?** `content.faqs` in
   `update_website_content`'s payload — but the caller is already
   authenticated and already scoped to a restaurant they manage; nothing
   unauthenticated reaches this handler. The array's *contents* are new in
   the sense that they now reach a public sink (see A04/A03 below).
2. **What new capability does this grant, and to whom?** A restaurant owner
   (via `restaurant-portal`/`brand-portal`) can now write `restaurant_website.faqs`
   through this handler. Not a new *class* of writer for the column itself —
   staff already write it via `aiorders-admin-hub`'s whole-row upsert
   (design's own "two editors, one column" risk) — this diff adds a second,
   narrower writer using the same authz mechanism already governing
   `catering`/`careers`.
3. **What new data does this expose, and to whom?** `get_website_content` now
   also returns `faqs` — to the restaurant's own owner/managers, the same
   audience already authorized to read `catering`/`careers` from the same
   response. No new audience.
4. **What breaks if this component is fully compromised?** Same answer
   `ENG-022`'s review already gave for this handler and unchanged by this
   diff: every `brand-portal` action runs on a service-role client
   (`index.ts`, not touched here), so `requireRestaurantAccess` is the *only*
   access control, not one layer over RLS. Confirmed still true — `index.ts`
   and `utils.ts` are not in this diff's changed-files list.

## Findings — both non-blocking

1. **A04, no shape or size validation on `EDITABLE_PAGES` payload values.**
   `updateWebsiteContent`'s loop (`content[page]`) is typed
   `Partial<Record<EditablePage, unknown>>` and writes whatever it's given —
   true for `catering` and `careers` already, and `faqs` inherits the same
   gap rather than introducing a new one. A restaurant owner could write an
   arbitrarily large or malformed value to their own restaurant's row.
   **Not blocking:** confined to the caller's own tenant row — no shared
   resource, no cross-tenant blast radius, and not usable to spend budget
   against a third party (unlike the broadcast recipient-cap class fixed on
   `ENG-038`/`ENG-039`, which this is not the same mechanism as). First
   occurrence of this specific class — checked `agents/security/reviews/`
   and `agents/security/notebook/` for a prior instance, found none — so not
   a three-strike yet. Logged to the notebook; not filed as a proposal on its
   own, since a malformed `faqs`/`catering`/`careers` value only degrades the
   writer's own restaurant's public page, which the owner can also just
   re-edit. Worth folding into whatever ticket eventually gives this handler
   real schema validation, if one is ever opened.
2. **A05, verbose error message, pre-existing, not introduced by this diff.**
   `requireRestaurantAccess` (`utils.ts`, unchanged by this diff) throws
   `result.error || 'Access denied to this restaurant'`, and both
   `getWebsiteContent`/`updateWebsiteContent`'s catch-alls return
   `error.message` verbatim to the client. Same finding class already
   three-struck on `ENG-009`
   (`agents/principal-engineer/notebook/2026-09-02-security-proposal-verbose-error-response.md`)
   and carried again on `ENG-010`/`ENG-022`. Same disposition here: **not
   re-proposed** — logged as another occurrence, the existing proposal
   already covers this class and remains unactioned. Not blocking: low-
   frequency path (only reachable when `verifyRestaurantAccess`'s own DB
   lookup errors, not the ordinary denial case), unchanged by this diff.
