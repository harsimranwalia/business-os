# Security review — ENG-007

## Threat model

1. **What new input can an attacker control?** The `POST` body
   (`restaurant_id`, `online_earn_pct`, `dine_in_earn_pct`,
   `redemption_value_per_point`, optional `effective_from`) and the `GET`
   query param `restaurant_id`. Both require a valid Supabase session
   already verified by `admin-portal/index.ts`'s existing `authenticate()`
   middleware (unmodified by this diff) — no anonymous or unauthenticated
   path exists to this handler at all.
2. **What new capability does this grant, and to whom?** To a caller whose
   token resolves to `role === 'admin' || 'sub-admin'` (checked in this
   handler itself, narrower than the router's own broader
   admin/sub-admin/partner-admin/partner-user gate): read the full
   rate-change history of *any* restaurant, and insert a new rate config for
   *any* restaurant_id. Not scoped to "restaurants this admin manages" — but
   that matches this router's own established model everywhere else
   (`restaurants.ts` lets any admin/sub-admin update any restaurant,
   `brands.ts` lets `role === 'admin'` delete any brand); admin/sub-admin
   are platform-wide staff roles in this system, not restaurant-scoped, so
   this is consistent with existing, already-reviewed precedent rather than
   a new IDOR-shaped gap.
3. **What new data does this expose, and to whom?** Per-restaurant loyalty
   rate configuration (two earn percentages, one redemption value,
   effective-dated) — business-internal, revenue-adjacent, not PII and not
   payment-instrument data. Exposed only to already-privileged admin/sub-admin
   staff, same trust tier that already sees restaurant financials via
   `billing.ts`/`analytics`.
4. **What breaks if this component is fully compromised?** A compromised
   admin/sub-admin token could set arbitrary rates for any restaurant. Today
   this has **no live effect** — no ledger, no points, no redemption exists
   yet (tickets 3/4, explicitly out of this ticket's scope), so a bad rate
   sits inert until a later ticket's code reads it. The blast radius is
   bounded by, and comparable to, what admin/sub-admin can already do
   platform-wide in this router (edit any restaurant, delete any brand) —
   not a new risk tier this ticket introduces.

## Negative / degraded-auth cases, traced rather than assumed

Read `loyalty-config.ts` top to bottom:

| Case | Behaviour | Where |
|---|---|---|
| No `Authorization` header / invalid token | 401 — handled entirely by `index.ts`'s existing `authenticate()`, unmodified by this diff; this handler is never reached | `admin-portal/index.ts` (pre-existing, out of this diff) |
| Valid token, role not `admin`/`sub-admin` (including `partner-admin`/`partner-user`, which the *router's* own gate admits) | 403, `"Admin access required to manage loyalty configuration"` | `hasLoyaltyConfigAccess`, first check in `handleLoyaltyConfig` — before any method dispatch, any DB call. **Tested**: `rejects a partner-admin with 403, regardless of method` |
| `GET` with no `restaurant_id` | 400 | Tested |
| `POST` with a missing/wrong-type/negative/over-100/NaN numeric field | 400, field-specific reason, before any DB write | `validateLoyaltyConfigInput`, called before the insert. **Tested**, 21 cases |
| `POST` with a backdated or non-increasing `effective_from` | The trigger rejects at insert time (belt-and-suspenders — even if application validation were bypassed, the database itself refuses); mapped to 400 | `mapLoyaltyConfigInsertError` — **mapping tested**; the live insert-time rejection itself is hand-traced, not automated (see QA test plan gap) |
| Any other DB failure | 500, logged server-side, generic message + the DB driver's own `.message` returned to the caller | Matches `restaurants.ts`/`brands.ts`'s own existing pattern of returning `details: error.message` in a 500 — see A05 below |
| Unexpected exception anywhere in the handler | 500 via the outer `catch`, logged | Same shape as every other handler in this router |
