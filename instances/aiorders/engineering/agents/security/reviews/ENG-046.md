# Security review — ENG-046

## Threat model

1. **What new input can an attacker control?** Two more boolean toggle
   states (`has_order_food`, `has_catering`) in an already-authenticated
   staff admin form, plus a rename of the existing toggle's bound field
   (`dine_in` → `has_dine_in`). Same input class as the six sibling toggle
   rows already in this card (`show_in_marketplace`, `cafe`, `bar`,
   `party_hall`, `live_catering`, `food_truck`, ...) — a UI `Switch` bound to
   a `boolean` field on local state, submitted through the same save path.
   No new input type, no new parsing, no free text.
2. **What new capability does this grant, and to whom?** Nothing new to any
   new actor. The same already-authenticated admin-hub staff who could
   already toggle `dine_in` and the six other flags can now also toggle
   `has_order_food`/`has_catering`. `handleSave` (unchanged by this diff)
   already serialized the entire `restaurant` state object; the endpoint it
   calls (`PUT /admin-portal/restaurants/:id`) already accepted and persisted
   arbitrary keys before this ticket (confirmed directly — `updateRestaurant`
   does `const { brand_owner, ...updates } = body; ... .update(updates)`,
   no field allow-list, in `aiorders-api`, untouched by this diff). This
   ticket adds a legitimate UI affordance for two fields that the backend
   was already willing to accept from this same authenticated caller; it
   does not widen who can reach the endpoint or what the endpoint accepts.
3. **What new data does this expose, and to whom?** None. `has_order_food`,
   `has_dine_in`, `has_catering` are already returned to this same caller by
   the existing `getRestaurantById`'s `select('*')` (confirmed at `ENG-045`'s
   own gate, re-confirmed here by reading the handler) — this ticket only
   starts *rendering* fields already present on the wire response, to the
   same staff audience already reading every other field on this page.
   Business discoverability flags, not PII — same classification `ENG-044`'s
   gate gave the underlying columns.
4. **What breaks if this component is fully compromised?** Unchanged from
   today. `RestaurantDetails.tsx` is a page component with no elevated
   authority of its own; a compromised session already had write access to
   every other flag on this card (and, per the pre-existing gap below, to
   any column on `restaurants` via the same unconstrained endpoint). This
   diff adds two fields to an already-exposed blast radius; it does not
   create a new one.
