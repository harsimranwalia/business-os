# Security review — ENG-020 (round 1)

First security-gate run on this ticket. Code review (3 rounds, PASS) and the
quality gate (3 rounds, PASS, all five ACs) are both complete and are not
re-litigated here; this gate reviews the full diff on its own terms.

## Threat model

1. **What new input can an attacker control?** Directly: `restaurant_id`,
   `from`, `to` on the new `get_acquisition_report` action — all validated
   (UUID regex, parseable dates, `from <= to`, range capped at 3 years) before
   any query runs. Indirectly, and more interesting: the *content* of
   `first_touch_source`/`first_touch_medium`/`first_referrer`, which five
   public, unauthenticated capture endpoints let any visitor set to
   arbitrary text before this ticket ever touches them. This report is the
   first thing that reads those columns back to a human. Checked what that
   buys an attacker: the value can land in the response as an `other:<raw
   source>` channel label, rendered by React as plain text (no
   `dangerouslySetInnerHTML`, no raw-HTML sink anywhere in `Index.tsx`/
   `ChannelBreakdown.tsx`) — stored-but-inert, not stored XSS.
2. **What new capability does this grant, and to whom?** A restaurant
   owner/manager (or brand-level admin role) can now read their own
   restaurant's aggregated acquisition/revenue breakdown. Same population,
   same ownership model as every other `brand-portal` read action.
3. **What new data does this expose, and to whom?** Counts, sums, and a
   referrer *host* string, scoped to the caller's own restaurant — never a
   customer id, name, email, phone, or full referrer URL. Confirmed by
   reading `acquisition.ts` and the migration's returned columns directly:
   no field carries anything beyond `first_touch_source`/`first_touch_medium`/
   `referrer_host`/three numeric aggregates. This is a narrower export of data
   than `analytics/database.ts` already returns to the same dashboard family.
4. **What breaks if this component is fully compromised?** Bounded by the
   same architecture already on record for this directory
   (`agents/security/notebook/2026-09-03-findings.md`, ENG-022 entry):
   `brand-portal` runs on the service-role client, so `verifyRestaurantAccess`
   is the entire access control, not one layer among several. A compromised
   service-role credential already has full read/write on this database
   regardless of this ticket; this diff adds one more read path behind the
   same existing checkpoint, not a new one.

## Negative-case test coverage

Read the actual test, not just its name or count: `acquisition.test.ts`'s
`"get_acquisition_report denies a restaurant the caller does not manage"`
builds a fake `restaurant_managers` resolver that returns a row only when the
filtered `restaurant_id` matches the fixture's *managed* restaurant, then
requests a *different* restaurant id and asserts the exact clean denial
(`{success: false, error: 'Access denied to this restaurant'}`) — a real
wrong-tenant case, not a trivially-true stub. Code review's own round-1
mutation test (forcing `access.hasAccess` to always be `true` and re-running)
confirmed this is the only test that fails when the check is removed — the
assertion has real teeth. `restaurant_id`-missing and non-UUID cases are
separately tested. No wrong-role or no-token case is needed at this layer:
those are the router's own job (401/403, verified directly above under A01)
and are unchanged, pre-existing behaviour this ticket doesn't touch.

## Findings — non-blocking

1. **A01-adjacent, low severity: `verifyRestaurantAccess` answers an
   existence question this design says it doesn't.** The design's Interfaces
   table states a denied request reveals "nothing about that restaurant,
   including its existence." In practice `utils.ts`'s shared helper (
   unchanged by this diff) returns a *distinct* string for a restaurant row
   that doesn't exist at all (`'Restaurant not found'`) versus one that
   exists but isn't the caller's (`'Access denied to this restaurant'`), and
   `acquisition.ts` forwards `access.error` verbatim
   (`return { success: false, error: access.error || 'Access denied to this
   restaurant' }`) — so an authenticated brand-portal caller can distinguish
   "that UUID isn't a restaurant" from "that UUID is a restaurant I don't
   manage." **Not blocking:** the helper and this exact behaviour are
   pre-existing, shared verbatim by every other consumer in this directory
   (`menus.ts`, `catering.ts`, `restaurants.ts`, `onlineOrders.ts` all forward
   the same `access.error`), so this is not introduced or worsened by
   `ENG-020` — fixing the shared helper's message granularity for one new
   caller while every sibling caller keeps the old behaviour would be the
   half-guarded-function shape `ADR-011` already declined for a different
   reason on this exact ticket. Exploit value is marginal: a restaurant UUID
   is not a credential, and confirming one exists exposes no data about it —
   the denial response is identical in every other respect. **Not filed as a
   proposal** — narrower than the observation/proposal bar
   (`eng_build_loop.md` step 8b: "if you would be disappointed that nobody
   acted on it, it is a proposal"); logged here so a future review of this
   directory, or of `utils.ts` itself, starts from the fact rather than
   re-deriving it.
