# Security review — ENG-005

## Threat model

1. **What new input can an attacker control?** None. The diff adds no route,
   endpoint, form, or parsed input — it renders an already-built component
   with props sourced entirely from data the page already fetches under its
   existing authorization.
2. **What new capability does this grant, and to whom?** The diff itself
   grants nothing new — but it makes a previously-unreachable, already-built
   component reachable for the first time, so its own runtime behavior is
   in scope even though its source isn't part of this diff. Traced the actual
   call path: `A4PosterGenerator` (`src/components/A4PosterGenerator.tsx`,
   untouched by this ticket) reads the caller's own Supabase session
   (`supabase.auth.getSession()`) and calls `aiorders-api`'s `url-shortener`
   edge function with `action: 'list'` / `action: 'create'`. Read that
   function directly (`supabase/functions/url-shortener/index.ts`,
   `aiorders-api` `origin/main`, `git fetch` first): every action other than
   the public `redirect` action requires a Bearer token, resolves it via
   `supabase.auth.getUser(token)`, and gates on `profiles.role === 'admin'`
   (`verifyAdminAccess`), failing closed (401 on missing/invalid token, 403 on
   non-admin) before reaching `list`/`create`/`update`/`delete`. So the new UI
   section grants nothing beyond what any other already-authenticated,
   already-admin-gated admin-hub screen already has — it reuses an existing
   admin-gated capability, it doesn't add one.
3. **What new data does this expose, and to whom?** None beyond what the same
   page's existing cards already display (`restaurant.name`, `.website`,
   `.logo_url`, `.id`) to the same already-authenticated admin-hub audience.
   The QR code itself encodes a public ordering URL
   (`{websiteUrl}/links/{restaurantId}`) meant to be scanned by end customers
   off a printed poster — that link's own target is deliberately public
   (the `redirect` action is the one action the edge function leaves
   unauthenticated, by design, for exactly this reason), not something this
   ticket newly exposes.
4. **What breaks if this component is fully compromised?** No new blast
   radius: the component only reads already-visible restaurant fields and
   calls an endpoint gated the same way every other admin-hub call to it
   already is. A compromised render of this card cannot reach anything the
   rest of the page's session couldn't already reach.

## Negative / degraded-auth case, traced rather than assumed

Read `fetchQr()` directly (`src/components/A4PosterGenerator.tsx`): the
session-token read, both `fetch` calls, and the response parsing are all
inside one `try`/`catch`, and every `.data` access uses optional chaining with
a `?? null` fallback. So a missing session (`token` undefined → early
`return`), an expired/invalid token (edge function's 401), or an
authenticated-but-non-admin caller (edge function's 403) all resolve the same
way: `qrDataUrl` never gets set, the poster still renders without a QR, and
nothing throws. This is the correct fail-closed shape for an admin-gated
capability being surfaced in a new place — a caller who shouldn't have the
capability gets a quietly incomplete poster, not an error that leaks *why*,
and not a crash.
