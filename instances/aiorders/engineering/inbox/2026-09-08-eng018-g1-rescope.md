# G1 — ENG-018 rescope, after your `changed` answer

## What changed since the last G1

You answered `changed`:

> It has to be fast simulated like show the autopilot 90 day process in 15
> minutes. And 1 complete experience per session.

Two clauses. The first redirects the demo's core mechanic away from the
original PRD's static, click-around seed and toward a scripted,
time-compressed playback of a real ~90-day customer-lifecycle sequence,
shown in ~15 minutes. The second scopes concurrency: each session gets its
own single, complete, start-to-finish run — not a shared clock every rep
and prospect watches the same slice of.

## What we checked against live code before writing anything below

**"The autopilot 90 day process" is real, live code, not a figure of
speech — `restaurant-portal`'s `Autopilot` section**
(`src/pages/autopilot/Automations.tsx`, `.../Broadcasts.tsx`), backed by
`aiorders-api`'s `autopilot` function. This is the actual thing AIOrders
sells restaurants: automated customer-lifecycle messaging. Checked its
trigger model before promising anything: `TriggerType`
(`supabase/functions/autopilot/utils/triggers.ts`) is ten hardcoded events
— `new_customer_welcome`, `first_order`, `welcome_offer`, `every_order`,
`order_completed`, `abandoned_cart`, `order_feedback`, `feedback_received`,
`birthday`, `new_catering_lead` — each with its own
`email_delay_minutes`/`sms_delay_minutes` on the template row. **There is
no single documented "90-day sequence" anywhere in the code** — "90 day"
is read as your own approximate framing of what a realistic run through
this trigger set looks like across a new customer's first few months
(welcome, first order, repeat/abandoned-cart nudges, eventually a
birthday or win-back message), not a literal spec to reproduce
move-for-move. Named as interpretation, correctable here.

**Two ways to make ~90 real days visible in ~15 real minutes, and we're
proposing the cheaper, safer one.** (a) Give the live `autopilot` function
a virtual clock instead of `now()`, so its real trigger/delay pipeline
actually fires early on the demo restaurant. (b) A demo-only scripted
timeline: a fixed, ordered set of pre-written rows (communications
"sent," orders, loyalty points, a catering enquiry) tagged to the demo
restaurant with backdated timestamps spanning ~90 days, revealed to the
viewer on a compressed schedule during the session. **(b) is proposed** —
it's cheaper, and (a) is the one mechanism this ticket's own isolation
requirement (no real sends, nothing in real analytics) exists to rule
out.

## The one thing worth getting right before we build this

**"1 complete experience per session" is read as: one demo restaurant,
shared as before, but a playback state scoped to whoever's watching it** —
two reps demoing at once, or one rep restarting mid-pitch, never see or
affect each other's progress. The practical question that follows: does
"start a new session" now *replace* the original "reset" control, or does
staff still want a separate manual reset button independent of opening a
fresh session (e.g. to clear a botched multi-rep state)? Proposed default:
opening the demo always starts one fresh run — no separate reset step —
covered below in Acceptance criteria 5. Say so here if you want the manual
control too; it's a small addition, not a rescope.

## Recommendation

**Build your version now, one ticket, `L`** — unchanged size. What would
have pushed this to `XL` — virtualizing time inside the real send/trigger
engine — is exactly what's rejected above. What's added instead is a
bounded, demo-only asset: a scripted set of backdated seed rows plus a
playback/reveal UI scoped to one session at a time. Still four repos, no
new vendor, still `$0`/month.

**One rider:** if the architect finds session-scoping needs a real
cross-repo session-identity mechanism rather than a client-side timer over
static seed data, that's a bigger, structural call and may come back as
its own G2 — flagged now so it isn't a surprise later.

## Problem

Restated, not changed: there is still no working example of the AIOrders
platform a sales rep or reseller can show a prospective restaurant owner.
What's changed is what "working example" means — a guided, time-compressed
story of a customer's first ~90 days with the restaurant, not a static
snapshot to click around.

## Acceptance criteria

Full six in the PRD; the ones this answer rewrote:

1. `[stated]` Unchanged — one clear entry point to the demo restaurant's
   portal and public site.
2. `[stated]` Rewritten. Given a rep starts a demo session, then it plays
   one complete, scripted run of the demo restaurant's Autopilot
   customer-lifecycle sequence (welcome, first order, a repeat or
   abandoned-cart nudge, a birthday/win-back message) on a compressed
   timeline reading as roughly 90 days of activity, finishing in roughly
   15 minutes.
3. `[proposed]` Unchanged, now explicitly covering the playback too — no
   real email/SMS is ever sent to a real recipient, at any point.
4. `[proposed]` Unchanged — excluded from `platform_analytics_cron`
   rollups.
5. `[proposed]` Rewritten. Opening the demo starts a fresh, complete run
   automatically — no separate manual reset step — and two sessions open
   at once never see or affect each other's progress.
6. `[inferred]` Unchanged — a non-authorised caller can't reach the
   demo's session/management controls; the public site stays open.

## Non-goals

**Superseded by this answer:** the original "no live-simulated activity"
non-goal is narrowed, not dropped — the compressed playback *is* a form of
simulated activity, but only while a session is open; there's still no
24/7 background clock running between pitches. **New:** virtualizing time
inside the real `autopilot` engine so it actually fires early — the
playback never touches the real send pipeline.

**Unchanged:** reseller-branded demo clones; a prospect-facing shareable
link usable without staff present; a second, fully isolated
database/environment.
