# P0 — a second function, `outgoing-communications`, sends real messages to anyone who asks, no login or key needed

**What's wrong.** While designing `ENG-035`'s fix (the `autopilot` bug
already reported), reading how the legitimate caller reaches
`outgoing-communications` found the same shape of hole in that function
too: it skips authentication entirely whenever the caller's request sets a
plain true/false flag themselves — and here it's wider, covering every kind
of message this function sends, not just three marketing offers.

**What that means concretely.** Anyone, with no app key and no login at
all, can make the system send a real email — built from a real order's live
data — to an address of their choosing, or trigger a real campaign
notification to a restaurant's actual owners/managers. Same shape of harm
as `ENG-035` (a stranger makes the system take a real action, at your cost),
on a wider surface.

**Why this is reaching you now instead of Friday's report.** Same rule
`ENG-022`/`ENG-029`/`ENG-035` used — a live exploit in production is one of
the two things allowed to interrupt you directly
(`agents/eng-manager/config/security-baseline.md`).

**What's already happening.** This doesn't need your approval to start —
`security`-typed tickets skip the approval step by design. `ENG-036` is
filed and handed to the architect for the design step; full evidence is on
the ticket:
`agents/eng-manager/board/ENG-036-outgoing-communications-systemtriggered-auth-bypass.md`.

**How this was found.** Not a security sweep — a second-order byproduct:
`ENG-029`'s design work found `ENG-035`; designing `ENG-035`'s own fix, in
turn, found this one while reading the function it calls into.

**What would help from you, if anything.** Nothing is required. If you want
this to jump ahead of everything else in flight, you can set `priority: now`
on `ENG-036` — that's the one thing only you can do here. Otherwise it
proceeds at its own severity's normal speed.

**Processed 2026-09-04**, `decision` event pass (context this file) — checked
the premise against work already done, rather than filing the requested
ticket on the word of the incident notice alone. `ENG-036`'s own design
(`agents/architect/designs/ENG-036-outgoing-communications-systemtriggered-auth-bypass.md`,
`ADR-017`) enumerated every caller of `outgoing-communications` across all
five of this instance's registered repos, not just the one caller the PRD
happened to find first. Result: three call sites set `systemTriggered:
true` (`autopilot/marketing/utils.ts`'s `scheduleWithQStash` and
`sendViaOutgoingComms` in `aiorders-api`, and `aiorders-admin-hub`'s
`cloudflare-workers/queue-consumer/index.ts`) — the only ones this fix's new
`else` branch puts a credential check in front of — and all three already
send exactly the credential the check requires
(`Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY`), confirmed by reading
each call site's own source directly, not inferred. The other three known
callers (`visit_scheduled`, `bag_insert_shared`, `campaign_created`) don't
set `systemTriggered` and stay on the function's existing, untouched
user-session auth path — this fix adds no `else` on that branch, so they
are unaffected regardless. **No caller of this function, as far as this
codebase's own source shows, requires a code change to keep working.**

So there is no callers-to-update work to put in a ticket — filing one
anyway would carry no actionable content. Named plainly rather than quietly
declined, same as this board's own precedent for a premise the code doesn't
support (`ENG-027`'s "if not cancelled or deleted" condition, vacuous as the
code stood, named rather than built as decorative). The one residual risk
in this area — whether the deployed `SUPABASE_SERVICE_ROLE_KEY` value
actually matches between the Cloudflare Worker environment and Supabase's
own secret store, which is a configuration fact no source read can confirm
— is already carried in the design's own Rollout section as a mandatory
manual post-deploy log check, not left to this incident to also cover.

This is reversible if wrong: if a caller this enumeration missed turns up
later — in the post-deploy log check above, or in any future code — that is
its own new finding at that time, same as every other gap this board has
caught, not something being foreclosed by closing this item now. Flagged
as an observation (`observations.md`) rather than left implicit: the
incident notice itself doesn't carry the design's own caller-safety
evidence, since the notice is written before design happens, so a
plausible-sounding "this will break things" reaction to the notice alone is
expected and not a sign anything here was rushed.

`ENG-036` itself is unaffected by this decision — re-verified fresh, not
assumed: still `designed`, `owner: architect`, still held by the machine-WIP
cap (`1/1`, the `ENG-016` family — `ENG-016` `building`, `ENG-034` `ready`,
neither yet `shipped`). No ticket filed, no design change. Full reasoning:
`ENG-036`'s own board-file log. Journaled in
