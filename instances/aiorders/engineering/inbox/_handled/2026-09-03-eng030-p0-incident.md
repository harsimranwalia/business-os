# P0 — the analytics API is exposing any restaurant's revenue and customer data right now

**What's wrong.** The `analytics` edge function (the API behind the brand
portal's dashboard revenue/order numbers) never checks that the caller
actually owns the restaurant they're asking about — it has no access-check
code of any kind — and it doesn't require a logged-in session, only the
app's own public API key.

**What that means concretely.** Anyone who can reach this endpoint — which
needs only the same public key every visitor's browser already has, not a
real login — can pull up any restaurant's yearly revenue, order count, tip
totals, and customer counts by supplying a different restaurant ID. No
special tools needed.

**Why this is reaching you now instead of Friday's report.** Same rule
`ENG-022` and `ENG-029` used — exposed data, live, in production, is one of
the two things allowed to interrupt you directly
(`agents/eng-manager/config/security-baseline.md`).

**What's already happening.** This doesn't need your approval to start —
`security`-typed tickets skip the approval step by design. `ENG-030` is
filed and handed to the architect for the design step; full evidence is on
the ticket:
`agents/eng-manager/board/ENG-030-analytics-function-restaurant-scoping-broken.md`.

**How this was found.** Not a security sweep — a byproduct of `ENG-020`'s
own tech-design research (marketing ROI/traffic-source reporting), which was
pointed at this same function as a proposed extension point.

**Third one this week.** `ENG-022` (`brand-portal`, a check called wrong)
and `ENG-029` (`autopilot`, a check never wired in) were the first two —
this is the same underlying bug class, a third function, a third failure
shape. Worth knowing about as a pattern, not just three separate tickets,
if you want to ask for a dedicated sweep rather than waiting for a fourth to
turn up on its own.

**What would help from you, if anything.** Nothing is required. If you want
