# P0 — brand-portal API is leaking customer data across restaurants right now

**What's wrong.** The `brand-portal` edge function (the API `restaurant-portal`
talks to) is supposed to check that a logged-in user actually owns the
restaurant they're asking about. On 5 of its 9 handler files, that check is
broken by a coding mistake — it always says yes, no matter who's asking.

**What that means concretely.** Any restaurant owner/manager logged into the
brand portal can currently pull up another restaurant's customer feedback
(name, email, phone, message) and customer list (name, email, phone) —
read-only — and can also read *and edit* another restaurant's promotional
offers and public website content. No special tools needed — just a
different restaurant ID in an already-logged-in request.

**Why this is reaching you now instead of Friday's report.** Per this
department's own rule, "exposed data" is one of the two things that's
allowed to interrupt you directly, the other being a leaked credential or a
live exploit (`agents/eng-manager/config/security-baseline.md`). This is
exposed data, live, in production.

**What's already happening.** This doesn't need your approval to start —
`security`-typed tickets skip the approval step by design, because "should we
fix a live hole" isn't a real question. `ENG-022` is filed and handed to the
architect for the design step; full evidence (exact files, exact broken
lines, exactly which ones are fine for contrast) is on the ticket:
`agents/eng-manager/board/ENG-022-brand-portal-tenant-isolation-broken.md`.

**What would help from you, if anything.** Nothing is required. If you want
this to jump ahead of everything else in flight, you can set `priority: now`
on `ENG-022` — that's the one thing only you can do here. Otherwise it
proceeds at its own severity's normal speed.
