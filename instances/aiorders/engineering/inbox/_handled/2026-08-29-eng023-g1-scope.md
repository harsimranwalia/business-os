# G1 — Add status and internal notes to each brand-portal feedback item

## Readback

**You said:** "the feedback board on the brand portal does not have status or
notes

what to do with the feedback, any actions taken is this frequent what are
the bottomline issue that need to be resolved by the restaurant location."

**Understood as:** The brand portal's Feedback page shows customer feedback
but is pure read-only display — a restaurant can see a complaint or review
but has no way to mark what's being done about it or record what the actual
issue was. This ticket adds a status and an internal notes field to each
feedback item so a restaurant can track it item-by-item: where it stands,
what action was taken, what the real underlying issue was.

**Requirements:**
1. `[stated]` A restaurant can set a status on each feedback item; it
   persists and displays correctly on return.
2. `[stated]` A restaurant can write and save an internal note on each
   feedback item; it persists and displays on return.
3. `[inferred]` Scoped to the restaurant's own feedback only — same tenant
   scoping already required for reading feedback at all (depends on
   `ENG-022`'s fix landing correctly, not a new requirement invented here).
4. `[inferred]` Pre-existing feedback items show a plain default/empty
   status, not an error or a blank crash.

**Assumed, and worth correcting if wrong:**
- Status/notes are set by the restaurant's own staff on the brand portal —
  not something only AIOrders' internal admin tool shows (`aiorders-admin-hub`
  has no feedback view of its own today).
- Notes are internal only, for the restaurant's own tracking — not a reply
  channel back to the customer.
- The exact status vocabulary (e.g. new / in progress / resolved) is a
  design decision, not dictated by the literal request.

**Evidence checked, not assumed.** `restaurant_feedback` (confirmed in
schema) has no `status` or `notes` column at all — the data has nowhere to
live yet, not just missing from the UI. Every new item already triggers a
real-time email to the restaurant, so nothing is missed on arrival, but
there's no durable record afterward of what happened to it. The only
existing write-shaped precedent in the same file
(`brand-portal/feedback.ts`'s own `getFeedback`) has a confirmed broken
tenant-isolation check — filed separately as `ENG-022` (a P0 security
ticket, already in flight) rather than folded into this one; this ticket's
new `update_feedback` action must instead model `catering.ts`'s
confirmed-correct `update_catering_request`.

**Second reading (blind architect, no repo access) converged on the core** —
independently, unprompted: "the feedback board is a dead-end inbox...
turning raw feedback into an operating loop: triage, act, record." **One
material divergence**, not blocking: whether "is this frequent" /
"bottomline issues" also wants a built cross-item aggregation view. Raised
separately as a non-blocking standing question
(`inbox/_handled/2026-08-29-eng023-frequency-question.md`), already answered
("reading b, frequent is same restaurant over time") and shaped into its own
ticket (`ENG-025`, now `designed`, sized `S`). This ticket ships the
confirmed core regardless of that answer. Full PRD:
`agents/product-manager/specs/ENG-023-feedback-status-and-notes.md`.

**Non-goals:** cross-item frequency/pattern analysis (→ `ENG-025`); any
customer-facing reply channel; a staff-facing (admin-hub) mirror of this
view; AI-generated summarization or categorization.
