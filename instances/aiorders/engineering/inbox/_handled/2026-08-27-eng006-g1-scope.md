# G1 — Unified cross-restaurant customer identity, phone/OTP auth, and legacy-customer mapping

## Readback

**You said:** "I want to be able to give the customers points for online
ordering and dine in they do at a restaurant and the points would be
restaurant specific only but all of them would have the same naming in the
frontend. For now we are just going to build the backend to support this. ...
We are also introducing the concept of a foodswipe customer who will be
identified by a unique phone number and they will be authenticated through an
sms otp and session would be maintained. Currently each restaurant has its own
customer even though its the same physical human being which will now be
identified in the system as a xxx customer (do no use the name xxx anywhere in
db and code thats more for branding). We can map the new foodswipe customer to
the legacy restaurant customer but for loyalty it will be one user... Define
the feature and we may have to split this into multiple tickets that can be
delivered individually one after another..." (full verbatim text in the
ticket's own `## Input`, `agents/eng-manager/board/ENG-006-unified-customer-identity.md`)

**Understood as:** A cross-restaurant loyalty program, backend only for now.
One platform-level identity per human — phone + SMS OTP + a maintained
session — mapped onto today's existing per-restaurant customer records
without replacing them, so a diner has one account and one QR across every
AIOrders restaurant, while points themselves stay restaurant-specific under
one shared display name. This is too large for one ticket; **this G1 covers
only the identity/auth/mapping foundation** — the rest is proposed shape, not
yet built or filed.

**Requirements for this ticket:**
1. `[stated]` Phone number + SMS OTP authentication, with a maintained
   session.
2. `[stated]` One identity per physical person, across every restaurant.
3. `[stated]` Maps to existing legacy per-restaurant customer records rather
   than replacing them.
4. `[inferred]` Many-to-one mapping: one identity can link several legacy
   records, one per restaurant the person has ordered from.
5. `[inferred]` Phone numbers normalized to one canonical form before being
   used as the matching key.
6. `[proposed]` OTP is rate-limited and expires.
7. `[inferred]` The technical name avoids the branding word entirely, per
   your own instruction — this PRD uses "platform customer" as a neutral
   placeholder; the architect names it for real at design time.
8. `[proposed]` Ambiguous phone matches (conflicting name on the same number,
   more than one legacy record at one restaurant sharing a number) are
   surfaced, not silently guessed.

**Assumed, and worth correcting if wrong:**
- Dine-in spend has no existing record — points come from a restaurant staff
  member entering an amount by hand at the scan, not an integrated POS. If a
  POS integration is actually expected, ticket (3) below grows substantially.
- Redemption needs its own configured value (not just the earn percentage you
  named) — proposed as a second per-restaurant config field, symmetric with
  the earn rate.
- Points never move between restaurants — earned and spent only where
  earned; the shared UI is a view over separate balances, never a shared one.
- Legacy customer records are kept as-is, not merged or deleted.
- No points expiry in this phase.
- "Restaurant" means one location, not a multi-location brand — the
  architect confirms this against the live schema rather than this PRD
  asserting it.
- Frontend (all three repos) is out of scope for every ticket in this
  sequence, not just this one, per your own "separate discussion, later."

**Not doing (this ticket):** points, balances, the ledger, redemption, QR
codes, per-restaurant config, admin endpoints, or any frontend work — see
Non-goals below. Those are the other four proposed slices.

## Recommendation

**Build ENG-006 now.** It's the one piece every later slice depends on, it's
cleanly scoped standalone, and it's invisible to diners and restaurants until
later work lands on top of it — so building it first carries no half-built
user-facing risk.

**The proposed shape for the rest of the initiative** (none of these are
filed — no ticket IDs allocated, nothing built or sized beyond a one-line
guess):

1. **ENG-006 (this G1)** — identity, OTP auth, session, legacy mapping.
2. Per-restaurant loyalty config — earn % (online, dine-in) + redemption
   value, effective-dated. No dependency on (1); could run in parallel.
3. Points ledger, balances, earn API (online accrual + manual dine-in entry),
   history. Depends on (1) and (2).
4. Redemption API + QR issuance/scanning, restaurant-scoped. Depends on (1)
   and (3).
5. Admin/support surfaces (lookup, cross-restaurant view, manual
   adjustment/void). Depends on (1) and (3).

Frontend across restaurant-marketplace, restaurant-portal, and admin-hub is
deliberately left out of this sequence — you named it as a separate, later
discussion.

**If this shape or order is wrong, this is the moment to say so** — before
(2)–(5) get filed as real tickets against it.

## Problem

Every restaurant on AIOrders holds a separate customer record for the same
diner — nothing recognizes one physical person across restaurants, so there's
no way to run a reward program broader than a single restaurant, and dine-in
spend is entirely invisible to the platform today.

## Acceptance criteria

1. `[stated]` Given a phone number with no existing platform customer, when
   OTP is correctly completed, then a platform customer is created and a
   session issued.
2. `[stated]` Given a phone number with an existing platform customer, when
   OTP is completed again (new device, cleared session), then the existing
   customer is reused — no duplicate — and a new session issued.
3. `[inferred]` Given a verified phone number matches existing legacy
   per-restaurant customer records, when the platform customer is created or
   first logs in, then those records are linked without being modified or
   deleted.
4. `[inferred]` Given two legacy records at different restaurants share a
   normalized phone number, when both are linked, then they resolve to one
   platform customer, readable together with its linked restaurants.
5. `[inferred]` Given a valid session, when a later API call is made, then
   the platform customer is identified from the session alone — no repeat
   OTP.
6. `[proposed]` Given a wrong or expired OTP, when submitted, then it's
   rejected, nothing is created or linked, and repeated failures against one
   phone number are rate-limited.
7. `[proposed]` Given a phone number that can't be normalized, when OTP is
   requested, then the request is rejected with a clear reason rather than
   creating an inconsistent identity.

## Non-goals

Points balances, the earn/redeem ledger, redemption or spend history
(ticket 3); per-restaurant earn/redemption config (ticket 2); QR generation
or scanning (ticket 4); admin-hub endpoints (ticket 5); any frontend work in
any repo; automatic merging of conflicting legacy records; the customer-facing
brand name for the identity or the points currency.

## Risks and unknowns

- **Positioning tension, named rather than assumed away:** a single identity
  shared across competing independent restaurants sits structurally closer
  to what a marketplace owns than to "you own your customer" — worth being a
  deliberate choice on the record.
- Phone number recycling (a reassigned number inherits someone else's
  identity and history) — flagged for the architect, not solved here.
- Legacy phone data is likely messy (missing, unnormalized, family-shared) —
  this ticket's mapping is a best-effort claim, not a guaranteed backfill.
- SMS OTP has a real recurring cost via a vendor not yet chosen — see Cost.
- PIPEDA (Canada) applies to phone storage and a cross-merchant dining
  profile — consent/opt-out needs designing in, not bolting on.
- Possibly a one-way door (new customer auth model) — flagged for the
  architect to evaluate for G2, not decided here.
