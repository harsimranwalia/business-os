# G1 — Per-restaurant loyalty configuration — earn rates and redemption value

## Readback

**You said:** "Per-restaurant loyalty configuration — earn % (online,
dine-in) and a redemption value, per restaurant, effective-dated so a later
rate change doesn't rewrite the meaning of past ledger entries. No
dependency on `ENG-006`; could build in parallel. Backend and migrations go
in `aiorders-api`, same as `ENG-006`. Frontend is out of scope for this
whole sequence, same as `ENG-006` — a separate, later discussion." (full
filed request in the ticket's own `## Input`,
`agents/eng-manager/board/ENG-007-per-restaurant-loyalty-configuration.md`)

**Understood as:** Item 2 of the five-ticket loyalty sequence you already
reviewed the shape of at `ENG-006`'s G1. A per-restaurant configuration
surface — online earn %, dine-in earn %, and one redemption value — each
effective-dated so a rate changed tomorrow never alters what a transaction
from last month meant. Pure configuration data: no ledger, no points, no
dependency on the identity work `ENG-006` built. This unblocks ticket 3
(points ledger/earn API) and ticket 4 (redemption/QR), both of which need a
rate to compute against and have none today.

**Requirements for this ticket:**
1. `[stated]` Online earn % and dine-in earn %, per restaurant,
   independent of each other.
2. `[stated]` One redemption value per restaurant — what a point is worth
   on redemption.
3. `[stated]` All three values effective-dated: a later change never
   rewrites what an earlier ledger entry's rate was.
4. `[stated]` No dependency on `ENG-006` — keyed on restaurant alone.
5. `[stated]` Backend and migrations only, `aiorders-api`. No frontend
   anywhere in the sequence.
6. `[inferred]` A rate change is a new effective-dated record, never an
   edit to the old one.
7. `[inferred]` Redemption value is one figure per restaurant, not split
   online/dine-in.
8. `[inferred]` This ticket exposes at least a read path for tickets 3/4
   to look up the effective rate, even though nothing consumes it yet.
9. `[proposed]` A minimal internal write path exists to set a new
   effective-dated rate, since nothing in the sequence has a frontend to
   drive it.
10. `[proposed]` An unconfigured restaurant reads as "not enrolled," not an
    error and not a silent platform-wide default.
11. `[proposed]` Earn % and redemption value can't be negative.

**Assumed, and worth correcting if wrong:**
- The unit basis for earn % and for redemption value (percentage of what;
  currency per point vs. a flat credit) is unresolved — left for the
  architect to fix at design time.
- Whether a rate change can be backdated or only ever takes effect in the
  future is unresolved and materially affects write-path validation.
- "Restaurant" carries forward `ENG-006`'s same single-location assumption.

**Not doing (this ticket):** the points ledger, earn/redeem history
(ticket 3); redemption execution or QR codes (ticket 4); admin/support
surfaces (ticket 5); any frontend; deciding real $/% numbers for any
restaurant.

## Recommendation

**Build ENG-007 now.** It's independent of `ENG-006` per your own scoping,
small (`S` — a config table and a minimal read/write surface, no auth or
identity work), and invisible to restaurants and diners until tickets 3 and
4 land on top of it — so it carries no half-built user-facing risk, same
reasoning as `ENG-006`.

## Problem

Tickets 3 and 4 of the sequence both need a per-restaurant rate to compute
against, and nothing in the system stores one today.

## Acceptance criteria

1. `[stated]` Given a restaurant with no configuration yet, when a new
   online earn %, dine-in earn %, and redemption value are set with an
   effective date, then those become the restaurant's current effective
   configuration.
2. `[stated]` Given a restaurant with an existing effective configuration,
   when a new rate is set with a later effective date, then the new record
   becomes current as of that date and the prior record's values remain
   readable, unchanged, for any earlier point in time.
3. `[inferred]` Given a query for a restaurant's effective rate as of a
   past timestamp before a later rate change, then the rate actually in
   effect at that timestamp is returned — never the current one.
4. `[inferred]` Given a restaurant never configured, when its effective
   rate is queried, then it reports as not enrolled, not a default rate or
   an error.
5. `[proposed]` Given a negative earn % or redemption value submitted,
   then it's rejected with a clear reason.
6. `[proposed]` Given two effective-dated records for one restaurant with
   overlapping date ranges, when the second is submitted, then it's
   rejected rather than silently creating an ambiguous history.

## Non-goals

Points balances, the ledger, earn/redeem history (ticket 3); redemption or
QR (ticket 4); admin-hub endpoints (ticket 5); any frontend work in any
repo; the actual $/% numbers for any real restaurant.

## Risks and unknowns

- Retroactive vs. future-only rate changes — unresolved, flagged for the
  architect.
- Concurrent writes to the same restaurant's config need an explicit
  design answer (e.g. an overlapping-range constraint).
- No stated deadline — sequencing work you already scoped the shape of,
  not a restaurant asking for this today.
- Genuinely independent of `ENG-006` — a candidate to build in parallel
  with anything else in flight; the EM's sequencing call at `ready`, not
  decided here.
