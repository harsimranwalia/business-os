# G1 — Foodswipe funnel page — staff-settable pipeline stages

## Readback

**You said:** "for the foodswipe SALES funnel page we are not able to or
the sales staff is not able to update or have proper peipleine stages /
sales, onboarding staff is not able to do anything with the funnel page
of foodswipe on admin panel"

**Understood as:** The admin panel's Foodswipe funnel page
(`FoodswipeListings.tsx` — a real, existing kanban tracking restaurant
onboarding progress) is entirely read-only today. You want sales and
onboarding staff to be able to set or correct a listing's stage, and
you're also questioning whether the stages shown are the right ones.

**Requirements:**
1. `[stated]` Staff can update a listing's pipeline stage — today there
   is no way to do this at all.
2. `[inferred]` Both sales and onboarding staff use this one page and
   both need this capability.
3. `[proposed]` This is a missing capability, not a regression — nothing
   suggests it ever worked and broke.
4. `[proposed]` The existing six-stage set (Account Created → Profile
   Updated → Listing Claimed → Menu Uploaded → GBP Shared → Website
   Interest) stays as-is for this ticket; making it staff-**settable** is
   the fix. Whether the stage names themselves are wrong is a separate,
   standing question (below), not assumed into this ticket.

**Assumed, and worth correcting if wrong:**
- "Update" means setting/overriding which stage a listing sits in, not
  editing the underlying lead/restaurant details (name, phone, email).
  Editing details is a non-goal for this ticket — the literal text ties
  "update" to "pipeline stages" specifically.
- A manual stage-set should stick (not get silently overwritten by the
  next automatic reload), with a way to reset back to automatic.

**Evidence checked, not assumed.** Read both the frontend
(`aiorders-admin-hub`'s `FoodswipeListings.tsx`) and the backend
(`aiorders-api`'s `admin-portal/handlers/foodswipe.ts`) directly: the
page has no click/drag/edit affordance and no mutation call anywhere;
the handler's `classifyStage()` is a pure read-only function over
existing columns, with no stored stage, no override column, and no write
branch despite technically accepting `POST`. Searched the whole API repo
for any staff-assignable status concept (`assigned_to`, `lead_status`,
`crm_stage`, `sales_stage`, `contact_status`, `owner_id`) — none exist
anywhere. This is confirmed net-new, not a small extension of something
partially there.

**Second reading (blind architect) agreed on direction, surfaced one
thing worth flagging separately** — it independently guessed that
"sales" and "onboarding" might need two different stage vocabularies
covering two different phases (pre-sale and post-sale), and that the
current stages might only cover one. Checked against the code: true —
all six existing stages describe a restaurant that has *already* signed
up. Whether a pre-signup layer is also wanted is genuinely unresolved
from the text, and swings cost by a lot if yes (a new record type, not
an extension of this one) — split out as a separate, non-blocking
standing question
(`inbox/2026-08-29-eng013-presignup-leads-question.md`) rather than
folded into this G1 or guessed at. Full PRD:
`agents/product-manager/specs/ENG-013-foodswipe-funnel-stage-control.md`.
