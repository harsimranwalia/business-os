# G1 — Staff-configurable Foodswipe pipeline stage set (ENG-028)

## Readback

**Your words this time, but no fresh two-reading run — deliberately.** You
already told us what you want, and the only genuine ambiguity in it (how it
should ship) was asked and answered rather than guessed at.

**You said,** replying to `ENG-013`'s merge request on 2026-09-01:

> "You added manual update of stage to the card what about the funnel
> stages itself on the page, if I want custom pipeline flow stages not
> just per card. This ticket was meant to allow custom pipeline stages for
> the whole foodswipe funnel, the stage updates per card can be manual or
> automatic."

**And you chose how it ships:** **"Reading a approved"** (2026-09-03) on
`inbox/2026-09-02-eng013-stage-config-question.md` — merge `ENG-013`'s two
PRs now, file stage-taxonomy configuration as its own ticket on top. This
is that ticket. That question also said the actual design — the admin
screen, ordering, whether stages can be deleted once in use — is this
ticket's own next round, so nothing below prescribes a screen or a schema.

**Understood as:** `ENG-013` made a card movable inside a board whose
columns are fixed in code. You want the columns themselves. Add a stage,
rename one, reorder them, remove one — and the funnel page shows your
pipeline, not engineering's, with no deploy. The six that exist today
survive intact (same names, same order, same cards in them) and keep
classifying automatically exactly as they do now. Per-card stage setting
is unchanged from what just shipped.

**One thing I need you to check, because it's the assumption that decides
the size of this ticket:**

**Can a stage you invent ever be assigned automatically?** Checked in code
rather than guessed: `classifyStage()` is a fixed if/else chain over
specific database columns — has a name and phone, has a restaurant row,
has menus, has Google Business Profile shared, has website interest. Each
of the six stages maps to one hardcoded real-world signal. **There is no
generic rule mechanism anywhere in the system.** So a stage you make up
has no signal attached to it and nothing could put a card there on its
own.

**Proposed:** the original six keep their automatic classification;
anything you add beyond those is set by hand (using the control `ENG-013`
just built). That's the most plausible reading of "the stage updates per
card can be manual or automatic" — but it is a reading. **If you also want
to define the conditions under which a custom stage gets assigned
automatically, that's a rules engine, not a config screen** — say so and
it comes back to be split into its own ticket rather than quietly absorbed
into this one and blowing the estimate.

**Two other things checked against live code, not assumed:**

1. **A database constraint has to change, and it predicted this itself.**
   The column `ENG-013` added carries a `CHECK` listing the six stage
   names as literals. Its own migration comment says: *"If a future
   ticket changes that stage set, this constraint needs updating in the
   same change or an override could reference a stage that no longer
   classifies automatically."* A constraint hardcoding six names can't
   coexist with a stage set you can edit. That's the single concrete
   reason this is `L` and not `M`.
2. **The stage set is hardcoded in four separate places across two
   repos** — a TypeScript union type and a validation array in the API
   handler, the database constraint, the classifier's if/else chain, and
   a display array in the admin frontend that hand-authors a label, an
   icon and four colour fields per stage. Changing the pipeline today
   means touching all of them and shipping two deploys. That's what this
   ticket removes.

**Not doing** (this ticket): making the automatic classifier itself
configurable; changing how a card's stage is set (that's `ENG-013`,
unchanged); deciding what your stages should actually be; a
pre-signup/cold-lead pipeline or nurture automations (both `ENG-017`);
editing listing details; per-user or multiple pipelines; the Brands page's
separate client-stage concept; an audit trail of who changed the stage
set.

## Recommendation

**Build now, one ticket, `L` — several days to a week or more, and expect
a G2 on deletion semantics.**

The tempting move is to build something smaller. It should be resisted:
the smaller thing is exactly what `ENG-013` was, and you've already said

than the size difference.

**Two things I'd rather flag than bury.** First, the manual-only
assumption above is the one answer worth giving at this gate — getting it
wrong sends this ticket from `L` to a split. Second, this isn't the most
urgent item on the board: `ENG-022` is `type: security`, `severity: P0`,
cross-tenant PII and write exposure across five live handlers, already
`designed` and owing only a G2. And `ENG-013`'s two PRs (`aiorders-api#5`,
`aiorders-admin-hub#4`) should land on `main` before anyone builds on top
of them. Approving the scope here and sequencing the build behind
`ENG-022` costs nothing.

## Problem

Sales and onboarding staff can now move a Foodswipe listing between
stages, but the stages themselves are fixed in code — six names, bound in
four places across two repos, changeable only by an engineer and a
deploy. You've said twice that this set isn't right for how your team
works. Until the taxonomy is yours to define, the funnel page tracks
engineering's model of onboarding rather than your actual pipeline.

Worth naming plainly: nobody has said *which* stages are missing. This
ticket ships the capability; choosing the pipeline is yours afterwards.

## Acceptance criteria

1. `[stated]` Given the funnel, when an authorised staff member defines a
   new stage, then it appears for all staff with no code change and no
   deploy.
2. `[stated]` Given an existing stage, when it is renamed, then the page
   shows the new name everywhere and no listing's assignment changes.
3. `[stated]` Given the configured stages, when their order is changed,
   then the page presents them in that order for all staff.
4. `[proposed]` Given the six stages that exist today, when this ships,
   then all six are present with current names and order, and every
   listing sits where it sat before — a migration, not a reset.
5. `[proposed]` Given one of the six originals and a listing with no
   manual override, when its data meets that stage's existing condition,
   then it is still classified there automatically, exactly as today.
6. `[proposed]` Given a staff-defined stage, when any listing without a
   manual override is classified, then it is never assigned that stage
   automatically — reachable only by hand.
7. `[inferred]` Given a listing whose stage was set manually under
   `ENG-013`, when the stage set changes afterwards, then it still
   resolves to a stage that exists — nothing anywhere references an
   undefined stage.
8. `[proposed]` Given a stage with listings in it, when removal is
   attempted, then either it is refused or every affected listing is
   moved to a defined stage in the same action — nothing is stranded.
   (Which one is a design question, not answered here.)
9. `[proposed]` Given a staff-defined stage, when the page renders, then
   it is visually distinguishable as its own column without an engineer
   authoring anything for it.
10. `[inferred]` Given a request to define, rename, reorder or remove a
    stage from a caller without admin access, then it is rejected by the
    same authorisation gate the funnel page's existing endpoints use.

## Non-goals

Making the automatic classifier itself configurable; changing per-card
stage setting (`ENG-013`, unchanged); deciding what the stages should be;
a pre-signup/cold-lead pipeline; stage-triggered automations or nurture
sequences (`ENG-017`); editing listing details; per-user, per-role or
multiple parallel pipelines; the Brands page's separate client-stage
concept; a history/audit trail of stage-set changes; reclassifying
existing listings beyond preserving where they sit. Full list in the PRD.

## Risks and unknowns

- **A custom stage has no signal to be assigned by** — the classifier is a
  fixed if/else over specific columns, not an engine. The manual-only
  proposal above is a reading, and correcting it here is free.
- **The override column's CHECK constraint can't stay a hardcoded
  six-name list** — its own migration comment predicted exactly this. How
  integrity is preserved instead is the architect's call; that it changes
  is not optional.
- **Deletion with live data is genuinely unspecified** — refuse, reassign,
  or archive each behave differently. Criterion 8 constrains the outcome
  without picking the mechanism. Expect this to be G2's substance.
- **`ENG-017` gets a moving target** — it nurtures leads "to next stages"
  and is already `designed`; an editable taxonomy means a rule can point
  at a stage that gets renamed or deleted. Worth sequencing the two
  consciously.
- **`ENG-013` isn't merged yet** — building on an unmerged sibling branch
  is a blind spot this loop's review tooling doesn't catch (it diffs
  against `main`, not against the sibling).
- **The strongest case against this ticket:** if what's really needed is
  three specific extra stage names, adding three literals is hours and
  this is days. Building the cheap thing on an inference is what produced
  this ticket in the first place, which is why the recommendation is
  still "build."
- **`aiorders-admin-hub` had 64 uncommitted files in the human checkout**
  as of the last registry check — merge friction expected on a page
  `ENG-013` has just also rewritten.
