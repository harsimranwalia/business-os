# G1 — Sales demonstration account (ENG-018)

## Readback

**You said:** "no autopilot on admin panel for our sales staff/ resellers to
use . how can we demonstrate to a client what we sell if we dont have it
for us. have a proper fully demonstration account on how all aiorders work.
also autopilot nurturing for resellers/sales/admin staff on admin panel
which works based on stages update/ auto nurturing ."

**Understood as:** this raw request bundles two separable asks — this G1
covers only the "demonstration account" half; the autopilot-nurture half is
`ENG-017` (its own G1, already past `designed`). Today there is nothing a
sales rep or reseller can actually show a prospective restaurant owner — no
seeded, working example of a restaurant's ordering site, portal, loyalty,
and marketing running end to end. You want one demonstration setup — a fake
but fully-populated restaurant — any sales rep or reseller can pull up
mid-pitch and click through as if it were real.

**Second reading:** this PM's reading, grounded in a live search across all
five repos, plus a blind architect reading (subagent, raw request +
`knowledge/business-profile.md` only, no repo access) — both independently
arrived at "a seeded, fully working fake restaurant," no material
divergence. The architect's reading additionally, unprompted, flagged
send/analytics isolation and reseller-branding, folded into this PRD's
acceptance criteria and Non-goals respectively.

**Assumed, correctable here:**
- "What we sell" is the restaurant-facing product (`config-site-builder`'s
  public site, `restaurant-portal`'s owner portal) — not `aiorders-admin-hub`
  itself, which restaurants never see.
- One shared demo tenant, neutrally branded, not a per-rep or per-reseller
  clone — a reseller-branded copy is real (named in your own text) but
  proposed as later work once this one exists.
- Believable, not transactional: real-looking orders/loyalty/catering
  activity, but no real SMS/email to a real recipient, and none of it
  reaches platform-wide revenue/analytics rollups (a live pipeline,
  `platform_analytics_cron`, already aggregates every restaurant's orders
  today — isolation is load-bearing, not a nicety).
- Resettable to a known-good state on demand, reachable from one entry
  point in the admin panel for `admin`/`sub-admin`/`partner-admin`/
  `partner-user`.

**Not doing (this ticket):** reseller-branded demo clones, a
prospect-facing shareable link usable without staff present, a second
fully isolated database/environment, or a live-simulated demo that
generates its own fresh activity over time. All named as later, separate
work in the PRD's Non-goals, not dropped.

Full detail, evidence, and the six acceptance criteria (isolation from
sends and analytics stated as criteria, not implementation nicety — see
Risks):
`agents/product-manager/specs/ENG-018-sales-demonstration-account.md`.

## Recommendation

Build now, scoped as above. `L` — seed data across menu/orders/loyalty/
catering, a flag/mechanism excluding that data from real sends and
analytics (`aiorders-api`), an access/reset entry point
(`aiorders-admin-hub`), and confirming the public site
(`config-site-builder`) and portal (`restaurant-portal`) render correctly
for a flagged demo restaurant. Four repos touched, no new vendor, $0/month
expected. Full PRD:
`agents/product-manager/specs/ENG-018-sales-demonstration-account.md`.
