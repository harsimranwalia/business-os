# G1 — Reconcile aiorders-admin-hub's deleted-but-uncommitted migration history

## Readback

**You said:** "Six aiorders-admin-hub migrations are deleted from the working
tree and exist nowhere else... The deletion was not committed... Establish
what the real migration history is and make the repo match it. The
underlying question the department should answer first: is
`aiorders-admin-hub/supabase/migrations` still authoritative at all, or did
migrations move to `aiorders-api`... and only get half-moved? Nothing here is
urgent." (`inbox/requests/2026-08-23-admin-hub-migration-history.md`)

**Understood as:** Before touching the pending deletion, confirm from the
live Supabase project itself — not either repo's tracked files — which repo
(if either cleanly) is authoritative for this database's migration history.
Then make that repo's tracked migrations replay cleanly from empty to the
live schema, without dropping the five RLS/`search_path`-hardening migrations
or breaking the `restaurant_activations` chain a later, already-committed
migration depends on.

**Requirements:**
1. `[stated]` Establish the real migration history using the live Supabase
   project as ground truth before committing the pending deletion.
2. `[stated]` Answer whether `admin-hub`'s migrations are still authoritative,
   or moved (possibly half-moved) to `aiorders-api`.
3. `[stated]` Make the authoritative repo's tracked migrations replay
   cleanly, preserving the security-hardening content.
4. `[inferred]` Confirming which Supabase project each repo actually targets
   is a precondition, not assumable from either tree's contents.
5. `[proposed]` Investigation completes before remediation starts — doing
   both at once risks committing a fix to the wrong understanding, which is
   the exact mistake the source request warns against.

**Assumed, and worth correcting if wrong:**
- That you want this investigated with a recommendation brought back, not
  investigated-and-executed autonomously — both repos are `Autonomy L1` (a
  human merges either way), but the security-hardening content makes this
  PRD treat "bring the answer back" as the safer default.
- That "nothing here is urgent" is your own working assessment for
  sequencing, not independently verified against the live ledger — the
  investigation step should confirm it, not just inherit it.

**Not doing:** assuming the answer to "which repo is authoritative" going in;
touching `aiorders-api`'s own nine migrations beyond what's needed to confirm
or complete a consolidation; re-auditing RLS policy *logic* itself; touching
any of the other 64 uncommitted files in `admin-hub`'s human checkout;
committing to a full migration-ownership move as part of this ticket even if
the investigation points that way (that's a possible one-way door for the
architect to size and escalate via G2 separately, not decided here).

## Recommendation

**Approve as scoped.** The investigate-first sequencing is the one thing this
G1 exists to lock in — the request itself warns against committing a fix to
the wrong understanding of the problem, and splitting investigation from
remediation is what prevents that. Sized `L` correctly: not because any one
step is large, but because getting it wrong has real cost (a broken
from-scratch replay, or silently dropped RLS hardening) on tables holding real
operator and customer data.

## Problem

Six migration files — five RLS/`search_path` security-hardening migrations
and the one that creates `restaurant_activations` — are deleted from
`admin-hub`'s working tree but uncommitted; committing that deletion as-is
would break a from-scratch replay, since a later, already-committed migration
alters the table one of the six creates. Whether `admin-hub` is even still
the authoritative source for this database's migrations, versus
`aiorders-api`, is unconfirmed — `config/projects.md` names a Supabase
project ref for `aiorders-api` but not for `admin-hub`.

## Acceptance criteria

1. `[stated]` Confirmed (not assumed) whether `aiorders-admin-hub` and
   `aiorders-api` target the same Supabase project.
2. `[stated]` Established, from the live migration ledger, which repo's
   `supabase/migrations` is authoritative today.
3. `[stated]` The six deleted files content-diffed (not filename-diffed)
   against `aiorders-api`'s nine migrations, to rule out a renamed
   consolidation.
4. `[stated]` The authoritative repo's migration chain replays from empty
   without error and without omitting the RLS/`search_path` hardening.
5. `[inferred]` The pending uncommitted deletion is resolved deliberately —
   restored, formally moved, or documented — not left sitting.

## Non-goals

Assuming the authoritative repo going in; changing `aiorders-api`'s own nine
migrations beyond consolidation confirmation; RLS policy-logic review beyond
restoring what the six files specify; the other 64 uncommitted files in
`admin-hub`; executing a full migration-ownership move as part of this
ticket. Full detail in the PRD.
