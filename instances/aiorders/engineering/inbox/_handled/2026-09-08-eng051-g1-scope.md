# G1 — Redemption API and QR issuance/scanning (ENG-051)

## Readback

**Raw input** — there isn't one to quote. This is item 4 of the five-ticket
loyalty sequence you reviewed and approved the shape of at `ENG-006`'s G1
(2026-08-28). Its scope is already stated precisely, in your own words from
that G1's `## Decision`, on the sequencing note itself:

> **Redemption API and QR issuance/scanning** — generates the customer's QR
> code, enforces that a scan only ever touches the scanning restaurant's own
> balance for that customer, and performs the redemption. Depends on ENG-006
> and (3).

**Understood as:** `ENG-006` gave diners one identity across every
restaurant; `ENG-007` gave every restaurant a redemption value nothing has
read since it shipped; `ENG-027` (verified today) gave diners a
points balance that only ever goes up. This ticket lets a diner spend it: a
code identifies them platform-wide, a restaurant resolves that code plus an
amount at the point of sale, and only that diner's balance **at that
restaurant** is debited, converted to value at that restaurant's own rate.

**No fresh two-reader run** — same call `ENG-027` made and logged: nothing
raw or ambiguous to run two blind readings against. The reading that
matters was run once, at `ENG-006`, and has since been independently
corroborated, unprompted, by `ENG-007`'s and `ENG-027`'s own PRDs both
naming this same boundary in their own non-goals at different times. Full
reasoning: `agents/product-manager/notebook/2026-09-08-eng051-prd.md`.

**Two things worth you confirming, not blocking on:**

1. **The code is data, not an image.** This ticket issues whatever a QR
   code would encode (a platform-wide identifier for the diner); it does
   not render an actual QR bitmap, because there's still no frontend
   anywhere to display one — frontend stays deferred for this whole
   sequence, same as every ticket so far. If you actually need a real,
   scannable image produced now with nothing to show it on, say so — that's
   different, smaller-scoped work than what's below.
2. **The code doesn't expire or rotate** — it behaves like a standing
   loyalty card, reused indefinitely, not a one-time code. The risk (anyone
   holding a copy of it can trigger a redemption) is named below rather than
   solved, on the reasoning that a restaurant staff member is physically
   present for every redemption today, same as `ENG-027`'s own accepted
   dine-in-earn risk.

Neither changes whether to build this — only some details of how, and both
default to the smaller, already-deferred-frontend-consistent reading if you
say nothing.

## Recommendation

**Build it, sized `M`.** Both dependencies (`ENG-006`, `ENG-027`) are
shipped and verified; `ENG-007`'s redemption value has sat unused since
2026-08-30. Narrowed from the intake stub's provisional `L`: unlike
`ENG-027`, this ticket needs no new external integration and no cron — it
reuses `ENG-006`'s identity/session, `ENG-007`'s rate lookup, and
`ENG-027`'s ledger and restaurant-scoped-action pattern
(`requireRestaurantAccess`) directly. The one thing that could push it back
to `L` — whether the diner's code needs its own stored/revocable row — is a
design call, left to the architect rather than guessed here.

## Problem

Diners can earn points but nothing lets them spend what they've earned — a
balance that only goes up isn't a loyalty program a restaurant can point to.

## Acceptance criteria

Full eleven in the PRD; the one this gate turns on:

- `[stated]` A redemption only ever touches the diner's balance at the
  restaurant doing the redemption — never another restaurant, never another
  diner. This project's own history (`ENG-022`, `ENG-029`, `ENG-030`,
  `ENG-035`, `ENG-036`, `ENG-050` — all missing-authorization P0s on
  `aiorders-api`) is why this is called out here instead of assumed.

## Non-goals

Any frontend anywhere (deferred for the whole sequence); rendering the code
as an actual QR image; admin/support surfaces and manual ledger
adjustment/void (ticket 5); migrating existing Walletly balances (unresolved,
carried from `ENG-027`); changing how points are earned; rate-limiting or
fraud detection beyond the restaurant-scoping itself; rotating or expiring
the code (Risks, not solved here).

## Cost

**Build `M`** — half a day to a couple of days. **Run `$0`/month** — no new
vendor, runs inside the existing `aiorders-api` Supabase project. Displaces
nothing at build time — this hop is shaping only, no machine slot involved.
