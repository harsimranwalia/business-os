## Five things checked against live code — the third overturns our own last G1

1. **The order's `status` in your database is written once and never
   again.** `external-integrations/handlers/cloudwaitress.ts`,
   `createOrder()` (line 188) copies it from the webhook payload at line
   195. That's the whole story of that column.

2. **Nothing anywhere updates or deletes an order.** Eleven places read the
   orders table; one writes it, once, at insert. No `.update(`, no
   `.delete(`, anywhere in the repo. This ticket would add the first
   write-after-insert on that table the codebase has ever had.

3. **But the completion and cancellation events are already arriving at
   your production endpoint and being thrown on the floor.** The handler
   ignores everything that isn't `order_new` (line 238), and last time we
   read that as "there is no completion signal." Wrong. Your **own webhook
   registration subscribes to nine events** —
   `cloudwaitress-middleware/handlers/restaurant.ts`, `AIORDERS_WEBHOOK`
   (line 6) — including `order_completed_updated`, `order_cancelled_updated`,
   `order_cancel` and `order_update_status`, and `handleAddWebhook()` (line
   93) is what writes that into each restaurant's CloudWaitress account.
   **The signal you're asking for doesn't have to be built. It has to stop
   being ignored.** That's a branch where there is currently a `return`.

4. **An "auto-complete after X hours" job is not new infrastructure here.**
   `pg_cron`/`pg_net` are already enabled and already running two scheduled
   jobs (`platform-analytics-hourly`; a monthly review snapshot). Closer
   still: the same `order_new` handler already sets a **per-order delayed
   callback** — the feedback queue, default delay **three hours**
   (`utils/cloudflare-queue.ts` line 73). You already run this shape, twice.

5. **The live status is also readable on demand.**
   `cloudwaitress-middleware` proxies CloudWaitress's own order API — fetch
   one order, list them filtered by status, or write status back — with
   per-restaurant tokens that auto-refresh. So a missed webhook is
   recoverable through shipped code.

## The problem with "if not cancelled or deleted" — please read this one

As the code stands today, **your condition is always true.** Nothing in the
system can mark an order cancelled or deleted (fact 2). So a timer-only
sweep would credit points on *every single order*, X hours after placement,
no exceptions — the same accrual-integrity exposure as the placement-based
accrual you just rejected, delayed by a fixed window. We'd rather tell you
that than build it and report the clause as satisfied.

**Cancellation is fixable, and cheaply** — that's fact 3. Stop discarding
`order_cancel` / `order_cancelled_updated` and the condition becomes real on
the day it ships. That is what we recommend, and it is lighter than the
alternatives: cheaper than building a cancel-marking capability from
scratch, and unlike a forward-compatible-but-inert check it isn't
decorative. (We considered writing the condition now as a no-op that
becomes true later. Rejected: `ENG-007`'s empty rate table was
inert-but-correct, nothing read it. A cancellation check that can never
fire is worse than inert — it looks like a safety property while being
none.)

**"Deleted" is not fixable.** There is no delete event in the subscription
and no deletion path at any layer. That half of your condition can't be
built as stated, and the auto-complete window is the only thing standing
between a deleted order and its points. Saying so rather than folding it
quietly into "cancelled."

**And one thing we can't answer from code and won't pretend to:** whether
your restaurants' staff actually mark orders complete or cancelled in the
CloudWaitress dashboard. The events are subscribed; whether they *fire* is
a production-log question. **If they never fire, the timer becomes the only
mechanism and "if not cancelled" never once evaluates false** — landing
where a timer-only build would have, just honestly. Worth a look at the
logs; it doesn't change whether to build.

## Recommendation

**Build your version now, one ticket, `L`** — several days to a week.
Accrual on fulfilment, driven primarily by the completion and cancellation
events you already subscribe to, with the auto-complete timer as the
fallback for orders that never get a terminal event. That combination is
what makes "if not cancelled" mean something.

**Sized `L` fresh, not rubber-stamped either way.** Not the `M` it was, and
not the old `M → L` warning's reasoning either — that warning priced
building a signal that turns out to already exist, so the honest number is
below what it implied. What actually earns the `L` is what sits on top of
the original `M`: the first write-after-insert path on `orders` in this
codebase's history, on the live production webhook; a scheduled sweep with
its own idempotency and failure semantics; and moving the accrual trigger
point, which is where double-crediting bugs live. Not `XL` — one project,
one new data model, no new vendor, no cross-repo surface — so it proceeds
whole rather than going back to be split the way `ENG-016`'s rewrite did.

**Four riders to answer here rather than at a second gate:**

1. **How long is "x hours"?** It's a literal placeholder in your message.
   **Proposed: 24 hours.** With the terminal events live, the timer only
   catches orders whose restaurant never marked them anything — and those
   same restaurants won't send a cancellation either, so a longer window
   buys the only protection available. Costs nothing visible: points can't
   be spent until ticket 4 and no screen shows a balance. If you'd rather
   have points same-day, the anchor is **3 hours**, which is what your
   feedback queue already uses on this same webhook.
2. **What does the earn % apply to?** **Still open.** The last G1 asked
   this and your answer addressed timing instead. We don't read silence as
   approval, so it's carried forward rather than dropped or assumed.
   **Proposed, unchanged: the pre-tax, post-discount food subtotal** —
   excluding tax, fees, delivery and tip.
3. **Which moment's rate applies?** New, created by your change: placement
   and accrual used to be the same instant and now they're hours apart.
   **Proposed: the rate in effect when the order was placed.** Smallest of
   the four.
4. **Does the order's own status become true, or does loyalty keep a
   private view of "settled"?** **Proposed: the order's own status.** Two
   disagreeing answers to "was this completed" is worse than one, and it
   fixes something real — `brand-portal`'s order lists show that frozen
   column, so every restaurant owner is currently reading a status that was
   correct once, at placement, and has never moved since. The cost, stated
   plainly: this ticket then writes to a table eleven read sites depend on.

**Unchanged and still true:** this is not the most urgent item on your
board. `ENG-022` (`type: security`, `severity: P0`, cross-tenant PII and
write exposure, already `designed`) outranks it — more so now that this one
costs `L`.

## Acceptance criteria

Re-derived where the change touches them. Criteria 1, 6 and 9 of the old
set assumed accrual at order recording; criterion 2 (dine-in) needed no
change, since dine-in has no fulfilment step. Full list of eighteen in the
PRD; the ones your answer created or rewrote:

1. `[stated]` Given a diner with an identity placed an online order at a
   configured restaurant, when that order is reported **fulfilled**, then
   points are credited at the **online** rate.
2. `[stated]` Given an order is reported **cancelled**, when that is
   processed, then no points are credited for it, then or ever — including
   after the window elapses.
3. `[stated]` Given an order with neither a fulfilment nor a cancellation
   report, when the auto-complete window has elapsed since placement, then
   it is treated as fulfilled and credited.
4. `[proposed]` Given an order already credited on a fulfilment report,
   when its window later elapses, then nothing further is credited.
5. `[proposed]` Given any sequence of repeated, duplicated or out-of-order
   reports for one order, when all are processed, then it has been credited
   **at most once, ever** — and zero times if a cancellation appears
   anywhere in that sequence.
8. `[proposed]` Given the rate changed between placement and crediting,
   when points are computed, then the rate used is the one in effect at
   **placement** (rider 3).
13. `[proposed]` Given accrual or status reconciliation fails for any
    reason, when an order arrives, then the order is still recorded —
    neither can ever block order recording.
14. `[proposed]` Given a report for an order the platform has no record of,
    when processed, then it is ignored without error.
15. `[proposed]` Given the sweep fails on one order, when it continues,
    then the rest are still processed and a later run retries the failure
    without double-crediting anything.
16. `[proposed]` Given a cancellation arrives after points were credited,
    when processed, then the entry is not deleted or rewritten — correction
    stays a manual opposite entry (ticket 5).
