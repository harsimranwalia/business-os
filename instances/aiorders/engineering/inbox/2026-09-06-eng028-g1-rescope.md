## What we checked against live code before writing anything below

**The nine names you gave don't correspond to the six stages this ticket
was going to make editable — not one of them.** `aiorders-api`
`admin-portal/handlers/foodswipe.ts`'s `Stage` type and `VALID_STAGES`,
mirrored in the `foodswipe_stage_override` `CHECK` constraint and in
`aiorders-admin-hub`'s `STAGES` display array, are: `account_created`,
`profile_updated`, `listing_claimed`, `menu_uploaded`, `gbp_shared`,
`website_interest`. Those name **data a listing accumulates
automatically** — has a name and phone, has a restaurant row, has menus,
shared their Google Business Profile, showed website interest. Yours name
**a sales conversation's progress** — waitlisted, contacted, a meeting
scheduled, followed up, onboarded, not interested, on hold, activated,
upsold. Nothing in `profiles`, `restaurants`, or the listing data this
handler already reads could ever detect "a meeting got scheduled." This
isn't a rename of the same six ideas — it's a different pipeline replacing
them.

**"Brand portal['s] autopilot" is real, live code, not a figure of speech —
`restaurant-portal`'s `Autopilot` section** (`src/pages/autopilot/
Automations.tsx`, a trigger → message → review wizard) **backed by
`aiorders-api`'s `autopilot` function.** Checked its trigger model before
promising anything: `TriggerType` is a closed, hardcoded enum of
restaurant/customer-lifecycle events (`order_completed`, `abandoned_cart`,
`birthday`, `new_catering_lead`, six more), each with its own hardcoded
template variables (`customer_name`, `restaurant_name`, `order_number`).
None of that applies to a Foodswipe listing, which frequently has no
restaurant yet and never has an order. Same finding `ENG-017`'s own design
already made for the presignup-leads pipeline: **the reusable part is the
send layer (`sendEmail`/`sendSMS`), not the trigger/template data model.**
`ENG-042` below builds a parallel, Foodswipe-scoped trigger set on top of
that same send layer — it does not, and structurally cannot, plug into the
existing `autopilot` function as a new trigger type without changes there
too.

## The one thing worth getting right before we build this

**Proposed: automatic classification is retired outright, and every
existing listing starts at `Waitlisted`.** That's the most literal reading
of "let's hardcode stages," and it's a bigger change than it sounds —
`classifyStage()`'s if/else chain gets deleted, not kept dark behind a
column nobody computes from; `foodswipe_stage_override` stops being an
*override* of a computed default and becomes the only stage a listing has;
and every listing's displayed stage moves on ship day, where the original
PRD promised the opposite ("a migration, not a reset"). There's no honest
alternative mapping — nothing connects "shared their Google Business
Profile" to "Meeting Scheduled" — so resetting to the pipeline's own first
stage is the straight answer, not a guess dressed up as one.

**If instead you want the old six to keep auto-classifying alongside the
new nine**, that's a dual-taxonomy system: `classifyStage()` stays alive,
and something has to decide precedence between an automatic milestone and
a manual sales stage on the same listing. That's a materially bigger,
different ticket — say so here and it comes back re-scoped rather than
built on the assumption above.

**One rider, matching the question above:** confirm retire-and-reset over
dual-taxonomy before we build it — it's the one answer that changes the

**Casing and order**, decided rather than asked, since neither changes
what gets built: the nine stages ship as Title Case labels
(`Meeting Scheduled`, not `meeting scheduled`) over snake_case keys,
matching the existing six's own convention, in the order you gave them.
`Not Interested` and `On Hold` will most likely read better as visually
distinct off-ramps rather than sequential columns — the architect's call
at `designed`, not this gate's.

## Acceptance criteria

Full seven in the PRD; the ones this answer rewrote:

1. `[stated]` Given the Foodswipe funnel, when this ships, then the nine
   named stages (Waitlisted, Contacted, Meeting Scheduled, Follow Up,
   Onboarding, Not Interested, On Hold, Activated, Upsell) are present, in

   no longer determines any listing's stage, staff do.
4. `[inferred]` Given the nine-stage list hardcoded in this change, when
   the API's type and validation array, the database constraint, and the
   frontend's display array are compared, then all four agree — and so
   does `ENG-042`'s own trigger vocabulary, once that ticket builds.

Unchanged from the original set: authorised staff can still set a
listing's stage by hand using `ENG-013`'s existing control; a non-admin
caller is still rejected by the existing gate.
