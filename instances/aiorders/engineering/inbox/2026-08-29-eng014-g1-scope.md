# G1 — Brand portal self-service: restaurant QR codes and marketing media downloads

## Readback

**You said:** "on the brand portal restaurant is not able to see or genereate
the qr codes or the media downloads they have

nor are they able to make changes to timing or anythings related to their
website from the brand portal. all of this has be be done from admin portal
which the restaurant owners dont have access to. aware that these are
onboarding task but there can be no self onboarding if the restaurant
owner/user is not able to do this."

**Understood as:** The brand portal (restaurant-facing) has no QR code or
marketing-media surface at all today — that capability exists only in the
staff-only admin portal, backend included. You want restaurant owners to be
able to see, generate, and download their own QR codes and marketing
materials from the brand portal directly, without needing admin access
(which they don't have, by design). A separate, related gap — website
settings including hours — is real but named as a follow-on item rather than
bundled into this one; see below.

**Requirements:**
1. `[stated]` Restaurant owners can see and download their own restaurant's
   QR codes and marketing media (bag insert, A4 poster) from the brand
   portal.
2. `[stated]` Restaurant owners can generate a QR code themselves if one
   doesn't exist yet.
3. `[inferred]` This applies per-restaurant — an owner or brand manager sees
   only what they manage, same scoping the brand portal already uses
   everywhere else.
4. `[proposed]` The onboarding checklist reflects self-service completion
   without a staff member marking it done by hand. Not literally stated;
   it's the direct fulfillment of the request's own "self onboarding" framing.

**Assumed, and worth correcting if wrong:**
- "Media downloads" means the two marketing-collateral generators that
  already exist for staff (bag insert flyer, A4 poster) — not something
  broader like raw menu photography or logo files.
- No new QR type beyond what's already produced today (dine-in, bag-insert).

**Evidence checked, not assumed.** Read the brand portal
(`restaurant-portal`), the admin hub, and the backend directly before
writing anything: the brand portal's `Website` page only edits `catering`/
`careers` content, its `Settings` page is a literal unimplemented stub, and
neither has any QR/media surface anywhere in `src/`. The admin hub's
`Activation.tsx` onboarding checklist already generates a Dine-in QR and
Bag-Insert QR and has a step literally titled "Share Bag Insert & QR with
Owner" — the manual workaround, in the code. `aiorders-api`'s
`url-shortener` function — which creates the link and QR — checks
`profile.role === 'admin'` exactly, with nothing else recognized: this is a
real backend authorization gap, not only a missing frontend screen. The QR
image itself comes from a free public API (`api.qrserver.com`) — no
recurring cost.

**Second reading (blind architect, no repo access) agreed on direction** —
independently read the same two-portal, same-audience split, the same "QR/
media already exist, this is an access gap" shape, and the same "timing =
hours" reading. It also independently flagged that "anythings related to
their website" has no natural boundary in the text and that some
admin-editable fields must stay staff-only regardless (pricing, payouts,
domain) — a joint gap with this reading, not a disagreement, so it doesn't
block this ticket. Full PRD:
`agents/product-manager/specs/ENG-014-restaurant-qr-media-self-service.md`.

**Feature shape: this is item 1 of 2.** The website-settings/hours half of
the same request is named in the PRD as a proposed item 2, to be filed once
this ticket verifies — the same incremental-sequence pattern
`ENG-006`/`ENG-007`/`ENG-008` already used on this board. Its own scoping
question (how far website-settings parity should extend) is deferred to
when item 2 is actually shaped, since it doesn't gate this ticket.
