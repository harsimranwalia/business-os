# G1 — Influencer relationship notes — staff log for personality, preferences, and off-platform conversations

## Readback

**You said:** "potentially add notes by the staff to collaborate on the
influencer and see how their personality is or what they want/like or what
conversations have happened with them off the platform. we want our
community mangers(staff) to be able to more easily use these influencers
for our restaurant campaings." (a rider on your `ENG-009` G1 approval)

**Understood as:** A shared, running notes log on each influencer's admin
record — any staff member can add a note (personality, preferences, a
conversation that happened off-platform) and every staff member can read
the full history, so relationship knowledge survives staff turnover or a
change in who's running a campaign. Not a single field one person
overwrites — a growing, authored, timestamped log.

**Requirements:**
1. `[stated]` Staff can add a note to an influencer's record; it's saved
   with who wrote it and when.
2. `[inferred]` Staff can read every note left on an influencer's record,
   newest first, each showing its author and timestamp.
3. `[inferred]` Notes accumulate — nothing is overwritten or removed.
4. `[inferred]` An influencer's own session cannot read or write these
   notes — staff-only, same authorization boundary as the rest of the
   admin portal.

**Assumed, and worth correcting if wrong:**
- Any staff member can add/read notes on any influencer — no
  per-influencer or per-manager restriction.
- Freeform text only, no structured categorization.
- Manual entry only — nothing here connects to Meta, email, or any
  external system.
- **Whether brand/agency/reseller admin-hub roles (distinct from AIOrders
  staff) should also see these notes is genuinely open** — the request
  says "staff" and "community managers" throughout, which this PRD reads
  as internal employees only. Defaults to AIOrders-staff-only until you
  say otherwise.

## Recommendation

**Build ENG-010 now.** It's the third and final piece of the same
influencer-management request — `ENG-008` covers admin-side preference/
rating/collaboration data, `ENG-009` covers activity/engagement signals,
this covers relationship notes. Small, no new vendor, no new auth model —
it reuses the same admin-auth gate the other two already reuse. Sequenced
to build after `ENG-008` and `ENG-009` since all three touch the same
admin-UI file.

## Problem

Community managers build up real knowledge about an influencer, but today
it lives only in individual memory or private messages — it doesn't
transfer when someone else needs to activate that influencer for a
campaign.

## Acceptance criteria

1. `[stated]` Given an influencer's admin record, when a staff member adds
   a note, then it's saved with that staff member's identity and a
   timestamp.
2. `[inferred]` Given an influencer with existing notes, when any staff
   member opens that influencer's admin record, then they see every prior
   note, newest first, each showing its author and when it was added.
3. `[inferred]` Given multiple staff members over time, when each adds a
   note, then all notes accumulate — no note overwrites or removes a
   previous one.
4. `[inferred]` Given an authenticated influencer session (not staff),
   when that request reaches the notes read or write path, then it's
   rejected — same authorization boundary as the rest of the admin
   portal.

## Non-goals

Editing/deleting another staff member's note; structured/typed note
categories; automated ingestion from any external system; notifications
or mentions; whether brand/agency/reseller roles can read notes (open —
defaults to no); search over note contents.

## Risks and unknowns

- **Influencer-visibility is the one thing this can't get wrong** —
  influencers hold real AIOrders accounts, so a leak here means a person
  reading staff commentary about themselves.
- Whether brand/agency/reseller admin-hub roles should see these notes —
  unresolved, defaulted to no.
- Notes describe a real, identifiable person in Canada — worth the
  architect naming a deletion path, even for this small a ticket.
