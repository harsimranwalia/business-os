# G1 — Foodswipe funnel stage-triggered autopilot (ENG-042)

## Readback

**Raw input** — the second half of your `changed` answer on `ENG-028`'s G1,
verbatim:

> "Can we have autopilot email/sms setup on admin panel like brand portal
> for each stage update"

**Understood as:** when a Foodswipe listing moves into a stage staff have
configured with a template, it automatically emails and/or texts that
listing's own contact — the same "define a trigger, write a message, turn
it on" shape `restaurant-portal`'s own `Autopilot` section already gives
brand managers for their customer lifecycle, just pointed at the Foodswipe
sales pipeline instead.

**Checked in code before promising reuse.** `restaurant-portal`'s
`Autopilot` wizard is backed by `aiorders-api`'s `autopilot` function,
whose trigger set (`order_completed`, `abandoned_cart`, `birthday`,
`new_catering_lead`, six more) is closed and shaped entirely around
restaurants and orders — a Foodswipe listing has neither at its early
stages. So this reuses the platform's send primitives (`sendEmail`/
`sendSMS`), the same way `ENG-017` already found for the presignup-leads
pipeline, but needs its own trigger/template model rather than plugging
into the existing one.

**A second, independent reading (blind subagent, your sentence alone plus
the business profile, no repo access) landed on the same core ask** — no
material disagreement about what you want. It raised four specifics worth
you confirming rather than us guessing:

1. **Who receives the message?** Read as the listing's own contact
   (external) — matching every other "autopilot" in this codebase, all of
   which message the customer, never staff. **If you actually meant an
   internal alert to whichever staff member owns the listing, say so** —
   that's a notification feature, materially smaller and different from
   what's scoped below.
2. **Consent.** Nothing on file confirms a Foodswipe contact agreed to be
   emailed or texted — the same gap `ENG-017`'s design already found and
   fenced off for the presignup-leads pipeline (a global switch plus a
   per-contact flag, both defaulted **off**). Proposed here the same way,
   not re-litigated.
3. **Does re-entering a stage re-send the message?** A listing can move
   `On Hold` and back to `Follow Up` under the new pipeline — proposed:
   each stage fires its message **once per listing, ever**, not once per
   entry.
4. **A listing with no verified email or phone.** Proposed: skip that
   channel and log it, never error, never block the stage change itself.

None of the four changes whether to build this. The first two would change
*what* gets built if the proposed default is wrong.

## Recommendation

**Shape and size now — this G1. Build only after `ENG-028` ships**. This
ticket's trigger vocabulary is the stage names `ENG-028` is still
confirming (its own fresh G1 is open alongside this one); `depends_on:
[ENG-028]` covers build order, so nothing here jumps ahead of that
decision. Sized `L` — several days to a week — anchored to `ENG-017`'s own
near-identical shape (new admin UI, new trigger/template model, consent
plumbing) rather than guessed fresh.

## Problem

Foodswipe listings move through the sales pipeline entirely by staff
memory — nobody is told a stage changed, and no follow-up goes out unless
a person writes and sends one. `restaurant-portal` already gives brand
managers this for their own customers; the admin panel's sales staff have
no equivalent.

## Acceptance criteria

Full seven in the PRD; the two that carry this gate's open questions:

- `[proposed]` A stage with no template configured sends nothing —
  silence is the default, never an error.
- `[proposed]` Consent gates every send independently of the global
  switch — both must be on, not either.

## Non-goals

Building into the existing `autopilot` function's own trigger/template
tables (data model doesn't fit); a rules engine beyond one trigger, one
message; deciding whether Foodswipe listings have standing consent at all
(fenced off, not answered, same as `ENG-017`); a reporting/audit screen;
internal staff notifications (flagged above, not assumed); which stages
exist or what they're named (`ENG-028`'s).

## Cost

**Build `L`** — several days to a week. **Run `$0`/month** — reuses
`sendEmail`/`sendSMS` and their already-contracted vendor; no new vendor.
Displaces nothing at build time (blocked on `ENG-028` for build order, not
for shaping).
