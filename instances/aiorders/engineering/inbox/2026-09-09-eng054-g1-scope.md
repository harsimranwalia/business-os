# G1 — Loyalty admin/support surfaces (ENG-054)

## Readback

**Raw input** — there isn't one to quote. This is item 5 — the last one — of
the five-ticket loyalty sequence you reviewed and approved the shape of at
`ENG-006`'s G1 (2026-08-28). Its scope is already stated precisely, in your
own words from that G1's sequencing note:

> **Admin/support surfaces** — internal lookup, cross-restaurant view for
> support, and manual ledger adjustment/void. Depends on ENG-006 and (3).

**Understood as:** Every loyalty path built so far — identity (`ENG-006`),
balance (`ENG-027`), redemption (`ENG-051`) — is diner- or restaurant-staff-
initiated. This ticket gives AIOrders' own support staff a way to look up a
diner across every restaurant they're linked to, see phone-match conflicts
`ENG-006`'s own linking logic already detects but has never surfaced
anywhere (`needs_review`), and reverse a wrong ledger entry (a double-scan,
a bad redemption) as a new, attributed entry — never by altering what
already happened.

**This closes the sequence** — no item 6 exists on `ENG-006`'s own
sequencing note.

**No fresh two-reader run** — same call `ENG-027` and `ENG-051` both made
and logged: nothing raw or ambiguous to run two blind readings against. The
reading that matters was run once, at `ENG-006`, and has since been
independently corroborated by `ENG-007`'s, `ENG-027`'s, and `ENG-051`'s own
PRDs, each naming this exact boundary in their own non-goals at different
times. Full reasoning:
`agents/product-manager/notebook/2026-09-09-eng054-prd.md`.

**One thing worth you confirming, not blocking:** if a void reverses points
a diner already partly spent elsewhere at that restaurant, should the
balance be allowed to go negative, capped at zero, or should the void itself
be blocked? No default is assumed here — this one needs an actual answer,
not a silent-default reading like the last G1 offered. If you say nothing,
this is left for the architect to propose a specific mechanism against, not
silently resolved either way.

## Recommendation

**Build it, sized `M`.** Both dependencies (`ENG-006`, `ENG-027`) are
shipped and verified, and `ENG-051` — item 4 — verified the same pass this
was filed. No new external integration or cron: this reuses `ENG-006`'s
identity/legacy-link tables and `ENG-027`'s/`ENG-051`'s ledger table and
restaurant-scoped-action pattern directly. The one thing that could push it
to `L` — how much the negative-balance question above and the ledger's
missing database-level UPDATE/DELETE protection (Risks) end up shaping the
design — is a technical-design call, left to the architect rather than
guessed here.

## Problem

Support has no way to see a diner's loyalty activity across restaurants, no
way to see the match conflicts `ENG-006` already flags and defers, and no
way to correct a bad ledger entry once one exists. A support agent facing a
dispute today has no tool — the only way to look would be a direct database
query.

## Acceptance criteria

Full ten in the PRD; the two this gate turns on:

- `[stated]` A void/adjustment posts as a new, attributed, reason-carrying
  ledger entry — the original entry is never modified or deleted. The
  ledger's append-only contract is enforced by comment/convention only, not
  the database (open proposal, `principal-engineer`, 2026-09-07, naming this
  exact ticket) — this ticket is the first one able to break it.
- `[inferred]` A caller without internal staff authority — a diner, a
  restaurant staff member on their own restaurant-scoped access, or an
  unauthenticated request — is rejected from all three capabilities.
  Restaurant-scoped access, the shape every prior ticket in this sequence
  authorized on, is explicitly not enough here. This project's own history
  (`ENG-022`, `ENG-029`, `ENG-030`, `ENG-035`, `ENG-036`, `ENG-050` — all
  missing-authorization P0s on `aiorders-api`) is why this is called out
  instead of assumed.

## Non-goals

Any frontend anywhere (deferred for the whole sequence); a UI for the
`needs_review` queue; migrating existing Walletly balances (unresolved,
carried from `ENG-027`); changing how points are earned or redeemed; point
expiry or pooled/cross-restaurant balances; auto-resolving a flagged match;
restaurant- or diner-facing dispute tools; database-level UPDATE/DELETE
protection on the ledger (Risks, already has its own open proposal); bulk/
batch adjustment tooling; rate-limiting on these endpoints themselves.

## Cost

vendor, runs inside the existing `aiorders-api` Supabase project. Displaces
nothing at build time — this hop is shaping only, no machine slot involved.
