# G1 — Agency/reseller users: brand-scoped locations and a working add-location path

## Readback

**You said:** "admin portal is not optimized for new agency users/ resellers
of aiorders.

they are not able to add locations , security issue if they go to
/restaurant they can see all locations. they dashboard data is super admin
data not just their brands. same for other tabs like influencer they are
able to see all or user ."

**Understood as:** Agency/reseller staff — the `partner-admin`/`partner-user`
roles that already exist, each tied to specific brands via
`brands.partner_id` — should only ever see and act on their own brand(s)'
data, never platform-wide data, and should be able to add a new restaurant
location under their own brand themselves.

**Requirements:**
1. `[stated]` A partner-admin/partner-user sees only restaurants belonging
   to their own assigned brand(s) on the Restaurants page — enforced
   server-side.
2. `[stated]` A partner-admin/partner-user can add a new restaurant under
   one of their own brands; the write is rejected for a brand not assigned
   to them.
3. `[proposed]` A partner-created restaurant is held for staff review rather
   than auto-approved the way an admin-created one is today. Bare approval
   of this G1 accepts that default — say so explicitly if you'd rather
   partner-created restaurants auto-approve the same as staff-created ones.

**Assumed, and worth correcting if wrong:**
- **Confirmed real, exactly as you described:** the Restaurants page and
  add-restaurant both leak/reject respectively — traced to precise code
  (see PRD Evidence: `getRestaurants()` always uses the service-role client
  with no role check at all; the `restaurants` table's insert policy only
  names `admin`/`sub-admin`).
- **Confirmed NOT currently true on this branch:** the Dashboard already
  hard-blocks partner roles with a "coming soon" placeholder (no data shown,
  let alone super-admin figures), and the Influencers tab already hard-blocks
  them with an explicit "Access Denied" screen (hidden from the sidebar
  too). `/users` — read as your "or user" — is also already admin-only,
  both frontend and backend. If you're still seeing super-admin data on the
  Dashboard or full access on Influencers/Users right now, that's likely a
  different/older deployed version than this branch — worth a one-line
  correction so it doesn't get silently skipped.
- Super-admin (`admin`, `sub-admin`) access and workflow are unchanged.

**Second reading agreed / diverged on:** No material divergence — the
architect's blind reading (raw request + business profile only, no code
access) independently converged on the same shape: a systemic, data-layer
scoping gap implying an agency→brand→location ownership relationship,
confirmed live in the schema (`brands.partner_id`). Full PRD:
`agents/product-manager/specs/ENG-015-agency-reseller-brand-scoping.md`.
