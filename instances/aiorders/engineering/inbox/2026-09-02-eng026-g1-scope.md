# G1 — FoodSwipe channel-visibility toggles and capability-based discovery (ENG-026)

## Readback

**You said** (original title): "on the brand portal i want option to make
the restaurant visible on order food, dine in and catering separately" —
with a body describing three other tasks (time-clocks, smart filters, promo
badges) that never actually added the toggle the title asked for. Flagged as
a standing question; you answered:

> MASTER CAPABILITY TOGGLES... `has_order_food` (default: true),
> `has_dine_in` (default: false), `has_catering` (default: false)...
> CONSUMER DISCOVERY... display all merchants where the corresponding
> toggle is true. Do NOT automatically hide closed restaurants...
> "OPEN NOW" USER FILTER (OPT-IN ONLY)... API QUERY LOGIC... [full text on
> `inbox/_handled/2026-09-01-eng026-visibility-toggle-question.md`]

**Understood as:** a complete, unambiguous specification — three
independent boolean flags per merchant, consumer discovery gated on the flag
(never on open/closed status), an opt-in "Open Now" filter that's the only
thing that ever hides a closed merchant, and exact query semantics for both
states.

**Requirements** (full detail and provenance tags in the PRD):
1. **Stated/Confirmed** — three flags, exact defaults, exact discovery and
   query behavior, all taken directly from your answer.
2. **Proposed** — staff set these flags via `aiorders-admin-hub` (the
   existing internal admin surface), not restaurant self-service via
   `restaurant-portal`. Your original request's own second half frames this
   as internal staff-management work, and it matches how `ENG-008`/`009`/
   `010` are all staff-managed rather than owner-self-service. **Correct
   this if you actually want restaurant owners setting these themselves** —
   it would change this ticket's shape (a new self-service form, restaurant-
   scoped write access), not just a detail.
3. **Named, not resolved here** — existing merchants have no current value
   for these flags. A naive migration default would silently drop any
   merchant that already does dine-in/catering today out of those tabs the
   moment this ships. This needs a real look at live data before `building`
   starts; not guessed at PRD stage.

**Assumed, and worth correcting if wrong:**
- That the three deferred capabilities (status engine, smart filters, promo
  badges) really are separable follow-on work, not something that has to
  ship in the same release as the toggle. Nothing in your answer suggested
  urgency on those three; said so only because you didn't ask for them by
  name in this reply.

**Not doing** (this ticket): the operational time-clock/cutoff engine, the
dine-in/catering smart filters, the promo badge overlay, or restaurant
self-service editing of the flags. All four un-dropped, just not in this
ticket — see the PRD's Non-goals.

## Recommendation

Build now, scoped as above. Likely this board's first **three-repo** ticket
(`aiorders-api` for schema/query, `aiorders-admin-hub` for the staff toggle
UI, `restaurant-marketplace` for consumer discovery) — one more than
`ENG-011`'s two, named up front rather than discovered mid-build. Full PRD:
`agents/product-manager/specs/ENG-026-foodswipe-channel-visibility.md`.
Estimated half a day to a day.
